# 10. Практика: пишем код по образцу проекта

Задания — на **написание** кода. Сложность растёт. Правила:

1. Сначала попробуйте сами (10–30 мин на задачу), потом сравнивайте с ответом.
2. Ответы почти всегда лежат **в уже существующем коде** — это и есть
   «обратная связь».
3. Лёгкие задачи можно проверять в отдельном crate-«скретчпаднике»
   (scratchpad — черновик для экспериментов; `docs/labs/` с собственным
   `main.rs`), средние — прямо в тестах проекта (добавить `#[cfg(test)] mod
   lab` и удалить после проверки).
4. После каждой задачи — пара вопросов «в лоб по коду», на которые вы должны
   уметь отвечать без подглядывания.

## Уровень 1 — основы (байты и функции)

### 1.1 Свой `to_hex` без формата на каждый байт

`crc::to_hex` (`crc.rs:36-45`) использует `format!("{:02X}", b)` на каждый
байт — просто и читаемо, но медленно. Напишите вариант на битовых операциях:
для каждого байта берутся старший и младший полубайты, каждый мапится в
цифру через строку `"0123456789ABCDEF"`.

**Проверка:** `to_hex_fast(&[0x01, 0x84])` == `"01 84"`.

**Где ответ:** ваш код должен давать тот же результат; быстрый вариант —
через `char::from_digit` или lookup-строку.

### 1.2 `crc16` с таблицей

Алгоритм из `crc.rs:4-17` считает по биту за проход — для изучения понятно,
для продакшена медленно. Реализуйте табличный вариант:

```rust
fn crc16_table(data: &[u8]) -> u16 {
    // 1) построить таблицу из 256 значений (индексы 0..=255, форма та же)
    // 2) для каждого байта: crc = (crc >> 8) ^ table[(crc ^ byte) as usize & 0xFF]
}
```

Формула построения таблицы: `tab[i]` = результат `crc16` для одного байта `i`
(реализуйте через уже существующий бит-цикл). Проверьте на
`01 03 00 00 00 01` → `0x0A84` (тест `crc_known_values`).

**Где ответ:** логика одинакова с `crc.rs`; таблица — это просто кэш побитовой
функции.

### 1.3 `fc_name` в одну строку

`master.rs:37-49` — это `match` на 8 функций + fallback (запасной вариант).
Напишите свою версию, которая возвращает `&'static str` без `String` (кроме
fallback — верните `String` через `format!`).

**Проверка:** `fc_name(0x04)` == `"READ INPUT REGISTERS (0x04)"`,
`fc_name(0x7F)` == `"FUNCTION 0x7F"`.

### 1.4 `verify` через `append`

`master.rs::transact` и `frames::parse_response` уже используют `crc::verify`
(`crc.rs:20-27`). Напишите перевёрнутую пару:

```rust
fn append_my(frame: &mut Vec<u8>) { ... }   // добавить crc16 в конец
fn verify_my(frame: &[u8]) -> bool { ... }  // сравнить с crc16(body)
```

реализовав обе исключительно через `crc16` и `to_le_bytes`/`from_le_bytes` —
это и есть эталонные `append`/`verify` проекта.

## Уровень 2 — PDU и парсеры

### 2.1 `read_pdu` вручную

`frames::read_pdu` (`frames.rs:104-109`) использует `to_be_bytes()`. Напишите
эквивалент через сдвиги `(start >> 8) as u8` и `(start & 0xFF) as u8` без
аллокации `Vec` — верните `[u8; 4]`.

**Проверка:** для `start=0x1234, count=0x0005` — `[0x12, 0x34, 0x00, 0x05]`.

### 2.2 `parse_read_bits` с лишними байтами

Посмотрите `frames::parse_read_bits` (`frames.rs:133-151`): он читает
`byte_count` байт и режет по `expected`. Теперь представьте, что у вас 5
катушек, а сервер ответил `[len=1][0b0011_1100]` (6 бит данных). Должно
вернуться `[true,true,true,true,true]` (5). Напишите тест, проверяющий, что
лишний 6-й бит отбрасывается.

### 2.3 Реверс `float_from_regs`

`frames::float_from_regs(hi, lo)` склеивает регистры в f32 (`frames.rs:201-204`).
Напишите обратную функцию `regs_from_float(v: f32) -> (u16, u16)`, которая
разбирает f32 на старший/младший регистр (используйте `v.to_bits()`).

**Проверка:** `float_from_regs(hi, lo) == v` для `v = 101.325`.

### 2.4 write-multi coils по-своему

`frames::write_multi_coils_pdu` (`frames.rs:166-183`) упаковывает катушки в
байты (младший бит — первая). Задайте `values = [true, false, true, true]`
— должны получить `byte_count=1, бит-байт=0b1101` (младший бит = первая
катушка). Напишите свою реализацию и сверьте с существующей в тесте
(добавьте ассерт).

## Уровень 3 — встраивание в проект

Эти задания модифицируют проект локально. Совет: выносите код в отдельный
модуль-«лабораторию» (`src/lab.rs` + `mod lab;` в `main.rs`), чтобы при
неудаче легко удалить.

### 3.1 Новый тип датчика

`DataType` (`emulator.rs:11-32`) имеет 6 значений. Добавьте
`VoltageMV` (милливольты, label `"Voltage (mV)"`), единицу `"mV"` в
`worker.rs:309-316` и поддержку клавиши `7` в `main.rs` (рядом с `1..6`,
`main.rs:166-174`). Напишите тест-ассерт вида
`scenario_creates_devices` → `device(0).sensors` не меняется.

*Замечание:* это меняет публичный код — не забудьте удалить `lab`, если не
собираетесь оставлять.

### 3.2 Новый метод эмулятора

Посмотрите, как устроены `read_coils`/`read_holding_regs` у `Emulator`
(`emulator.rs:230-256`). Напишите симметричный метод:

```rust
pub fn read_input_chunk(&mut self, slave: u8, start: u16, count: u16) -> Result<Vec<u16>, u8>
```

(поиск устройства по slave, `Err(0x02)` если нет, `unwrap_or(0)` на пропуски —
ровно как у соседей) и протестируйте на устройствах из `default_scenario()`.

### 3.3 Средняя точка RTU: транзакция через канал

`master.rs::transact` связывает всё воедино. Напишите **без порта** функцию,
которая повторяет весь путь RTU-кадра на «виртуальном слейве»:

```rust
/// Возвращает ответ, который устройство «вернуло бы» на кадр.
fn fake_slave(frame: &[u8]) -> Vec<u8> { /* разобрать адрес/fc/pdu; сгенерировать эхо (echo) */ }
```

Идея: это почти `tcp_server::handle_pdu`, но для RTU. Сверьте с тестами
`frames::tests` — для запроса `01 03 00 00 00 01` слейв-функция должна вернуть
`01 03 02 00 00` + CRC от `[01 03 02 00 00]`.

### 3.4 Эмулятор как «мастер» для TUI-мастера

Задание на понимание трёх китов: `build_request` + `parse_response` +
`tcp_server::handle_pdu` эквивалентны `Read Holding` на эмуляторе. Проверьте
экспериментом: соберите кадр запроса, скормите его `emu.read_holding_regs`,
ответ — снова через `parse_response`. Кто в этой цепочке выступает «слейвом»?
(эмулятор). Куда девается CRC? (никуда не добавляется: эмулятор внутри
процесса, CRC нужен только для кабельного RTU — это хорошо видно в
`tcp_server::handle_pdu`, где CRC нет вовсе).

## Уровень 4 — мини-проекты

### 4.1 RTU-круг: полноценный автотест

Напишите интеграционный тест, который:

1. берёт `default_scenario()`;
2. готовит состояние slave 1: `emu.write_coil(1, 0, true)` и
   `emu.write_holding_reg(1, 0, 0x1234)`;
3. **отдельной функцией** (ваша реализация из 3.3) строит RTU-запрос
   `read_holding_registers(0, 1)` для slave 1;
4. прогоняет его через «слейв-функцию», которая проверяет адрес/fc и отвечает
   значением из `emu.read_holding_regs`;
5. разбирает ответ через `frames::parse_response` и проверяет значение `0x1234`.

По сути это RTU-аналог `tcp_master_polls_own_tcp_server`.

### 4.2 Второй канал в Bus

`emu_traces` (`worker.rs:460-527`) делает 3 образцовые RTU-транзакции на
устройство. Добавьте 4-ю — `WRITE SINGLE COIL` для `coil0=true`:
1) request `[slave][0x05][addr][0xFF00][crc]`; 2) response — эхо `[slave][0x05][addr][0xFF00][crc]`.
Сверьте, что Bus на эмуляторе теперь показывает и записи.

### 4.3 Дренаж как в `drain_tcp_trace`

`app.rs:436-447` — чистый дренаж `VecDeque` под `Mutex`. Напишите ту же идею
для RTU-мастера: метод `SharedMasterTrace::drain()` (Share `Arc<Mutex<VecDeque>>`,
который поллер наполняет, а UI забирает). Подумайте: почему здесь не нужен
`Event`-канал? (потому что мастер уже держит `trace` внутри; канал — для
других событий).

### 4.4 Простое «плюсование» в poller

`poll_serial` жёстко читает `input 0..60` (`worker.rs:364-366`). Замените на
конфигурируемую константу `INPUT_REGS` и добавьте ассерт, что `channels.len()
== INPUT_REGS/2`. Это упражнение — показать, где «магические числа» в проекте
и как их выносить.

## Чек-лист понимания (проект целиком)

Если можете **объяснить** каждый пункт без подглядывания — вы понимаете проект.

### `src/crc.rs`
- Почему полином `0xA001`, как устроен бит-цикл, почему CRC кладётся младшим
  байтом вперёд.

### `src/frames.rs`
- Как строится/парсится RTU-кадр; порядок проверок в `parse_response`;
  что такое exception `[fc|0x80][code]` и как он мапится в `ModbusError`;
  зачем `as_chunks::<2>()`; как склеиваются float32 из двух регистров;
  зачем в проекте «мёртвые» PDU-билдеры multi-write.

### `src/master.rs`
- Пул одного запроса в сериал: flush → write → дедлайн → чтение до таймаута →
  CRC → parse. Зачем DTR/RTS выключаются. Как транзакция попадает в `trace`.

### `src/emulator.rs`
- Карта регистров через `BTreeMap` (разрежённость); где живут float32
  (чётный/нечётный регистр); формула `value() = base + amp·sin(t/T)`;
  троттлинг `tick` vs темп поллера; авто-поиск свободной пары регистров.

### `src/worker.rs`
- Два потока и их развязка через `Event`-канал; зачем `poll_port` общий;
  когда и почему пробуется порт (один раз/сеанс); чем `poll_serial` от
  `poll_tcp` отличается; как `emu_traces` делает «обучение на реальных байтах».

### `src/discover.rs`
- VID-список и как определяется `is_esp_like`; `probe_modbus` (slave 1..15);
  JTAG-пропуск.

### `src/tcp_master.rs` и `src/tcp_server.rs`
- MBAP-поля и как их разбирает мастер и собирает сервер; зачем `tid`;
  лимиты `read_count` (2000 регистров, 1..1968 катушек, 123 регистра записи);
  почему сервер сажает соединение в собственный поток и как `stop()` его гасит.

### `src/app.rs`
- Где лежит единственное состояние; как `handle_event` разбирает `TaskDone`
  (3 вида `TaskPayload`); горячие пути регистра чтения/записи для эмулятора и
  мастеров; защита последнего устройства; `reconnect_after`.

### `src/ui.rs` и `src/main.rs`
- Цикл из `draw` + `poll(50ms)` + `try_recv`; приоритеты хэндлеров клавиш;
  клик по вкладке/списку; `Space` vs клик на дашборде; откуда `ui.rs` берёт
  данные (только из `App`).

### `src/firmware.rs`
- Subprocess-подход, esptool vs espflash, `run_progress`/`parse_pct`,
  ошибочная формула 16МБ→4МБ.

**Самопроверка на проекте:** пройдите мысленно путь от «нажал `[e]`» до
«кадр во вкладке Bus». Если все шаги (`app.connect_emulator` →
`worker.set_source` → `poll_devices` → `emu_snapshot` → `Event::Snapshot` →
`app.handle_event` → `ui::draw`) понятны — вы знаете всё, что нужно.
