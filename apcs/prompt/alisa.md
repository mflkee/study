## Что обязательно знать про архитектуру Modbus (Client/Server = Master/Slave)

В терминологии Modbus исторически было Master/Slave, сейчас в спецификациях всё чаще пишут Client/Server. Для понимания спецификации это одно и то же:

- **Инициатор всегда клиент (Master)**. Ведомое устройство (сервер) не может само слать запросы. Оно только отвечает на запросы клиента.
- В твоём случае: ты делаешь **сервер (Slave)**, а кто-то (SCADA, тестовый клиент, другой контроллер) будет мастером.
- Диапазон адресов устройств: **1–247**. 0 — broadcast (в TCP почти не используется), 248–255 — зарезервировано.

**Что из спецификации взять:** раздел про модель взаимодействия и адресацию. Это база, без неё нельзя правильно обрабатывать входящие запросы.

## ADU и PDU: самое важное для реализации

- **PDU (Protocol Data Unit)** — это «ядро» сообщения: код функции + данные. Одинаково для RTU и TCP.
- **ADU (Application Data Unit)** — PDU плюс «обёртка» под конкретный транспорт.

### Modbus RTU (последовательная линия, RS‑485)

ADU: `[Device Address (1 байт)] [Function Code (1 байт)] [Data (N байт)] [CRC-16 (2 байта)]`.

Критичные моменты из спецификации:

- **CRC-16 Modbus**: алгоритм, полином, начальное значение, отражение/инверсия битов, порядок байт. Без точного совпадения CRC пакеты будут отвергаться.
- **Тайминги и разделение кадров**: между кадрами должна быть пауза не менее 3,5 символов. Это важно для RTU, потому что нет явного поля длины — кадры разделяются паузами.
- **Скорость, чётность, стоп‑биты**: это не часть протокола, но обязательно согласуется между устройствами.

**Что взять из спецификации:** формат кадра RTU, алгоритм CRC, правила разделения кадров.

### Modbus TCP (Ethernet поверх TCP)

ADU: `[MBAP Header (7 байт)] [PDU]`.

MBAP Header:

- Transaction Identifier (2 байта) — нужен, чтобы сопоставлять запросы и ответы при параллельных соединениях.
- Protocol Identifier (2 байта) — почти всегда 0.
- Length (2 байта) — длина оставшейся части ADU (PDU).
- Unit Identifier (1 байт) — аналог Device Address из RTU. В TCP часто используют как идентификатор устройства внутри шлюза/туннеля.

Критичные моменты:

- В TCP **нет CRC** — целостность обеспечивает TCP.
- Кадры разделяются по полю `Length` в MBAP, а не по паузам.
- Порт по умолчанию — **502**.

**Что взять из спецификации:** структура MBAP Header, назначение полей, правила формирования длины, поведение Unit Identifier.

## Адресация и «человеческие» номера (1xxxx, 3xxxx, 4xxxx)

Часто в документации устройств пишут «адрес 40001» — это **человеческая нотация** (Modicon). Внутри протокола адресация всегда **0‑based**:

- Coil 0 → «10001»
- Discrete Input 0 → «20001»
- Input Register 0 → «30001»
- Holding Register 0 → «40001»

Ты должен либо:

- принимать адреса в 0‑based (как в спецификации) и документировать это, либо
- делать конвертацию «человеческих» адресов в 0‑based внутри своего сервера.

**Что взять из спецификации:** описание адресного пространства и правил интерпретации адресов.

## Исключения и коды ошибок

Если сервер не может выполнить запрос, он отвечает пакетом исключения:

- Устанавливается старший бит кода функции (например, 0x03 → 0x83).
- Второй байт — код исключения (1, 2, 3, …).

Частые коды:

- 01 — Illegal Function
- 02 — Illegal Data Address
- 03 — Illegal Data Value
- 04 — Failure in Associated Device

**Что взять из спецификации:** таблица кодов исключений, правила формирования ответов‑исключений.

## Порядок байт (Endianness) и упаковка данных

- Регистры — 16‑битные.
- При чтении/записи нескольких регистров порядок байт и слов может отличаться у разных устройств.
- Для float/double и 32‑битных значений каждый производитель делает по‑своему. Спецификация Modbus **не стандартизирует** эти форматы — это зона ответственности документации устройства.

**Что взять из спецификации:** правила упаковки регистров, упоминание про отсутствие стандартизации для сложных типов. Для твоего сервера это значит: чётко определи, какой endian и какие форматы ты поддерживаешь, и документируй это.

## Modbus TCP vs Modbus RTU: что именно тебе нужно, учитывая твой стек (Rust + tokio + Arch)

Ты делаешь сервер на Arch Linux с асинхронным стеком. Это почти всегда **Modbus TCP**.

Тебе критически нужны из спецификации:

1. **Структура MBAP Header** — чтобы парсить входящие TCP‑кадры и формировать ответы.
2. **Коды функций и форматы запросов/ответов** — чтобы реализовать логику чтения/записи регистров.
3. **Правила исключений** — чтобы корректно отвечать на ошибки.
4. **Диапазоны адресов и лимиты** (макс. количество регистров в одном запросе и т.п.) — чтобы не нарушать стандарт и не ломать клиентов.
5. **Unit Identifier** — как его использовать и проверять.

Для **Modbus RTU** из спецификации тебе пригодится:

- Алгоритм **CRC‑16** (если планируешь поддержку последовательного порта в будущем).
- Правила разделения кадров (паузы) — если будешь писать драйвер для RS‑485.

## Как это применить к твоему Rust‑примеру

Твой текущий пример — заготовка. Чтобы он стал рабочим Modbus TCP‑сервером, тебе нужно:

1. **Парсить MBAP Header**: прочитать 7 байт, проверить Protocol Identifier, взять Length и Unit Identifier.
2. **Валидировать PDU**: проверить код функции, диапазоны адресов, количество элементов.
3. **Реализовать логику функций**: чтение/запись в свои внутренние регистры.
4. **Формировать корректный ответ**: либо обычный PDU, либо исключение.
5. **Собирать MBAP для ответа**: тот же Transaction ID, Protocol ID = 0, Length = длина PDU, Unit ID = тот же, что в запросе.
6. **Обрабатывать параллельные соединения**: Transaction ID нужен, чтобы не перепутать ответы при множественных клиентах.

Пример логики обработки одного TCP‑пакета (псевдокод):

```rust
let mbap = read_mbap(socket)?;
if mbap.protocol_id != 0 { return Err(ProtocolError); }
let pdu = read_pdu(socket, mbap.length)?;
let response_pdu = match pdu.function_code {
    0x03 => handle_read_holding_registers(&pdu, &mut store),
    0x06 => handle_write_single_register(&pdu, &mut store),
    // ...
    _ => make_exception_response(pdu.function_code, EXCEPTION_ILLEGAL_FUNCTION),
};
let response_mbap = build_mbap(mbap.transaction_id, 0, response_pdu.len(), mbap.unit_id);
socket.write_all(&[response_mbap, response_pdu])?;
```

## Безопасность и «реальные» рекомендации

Modbus не имеет встроенной аутентификации и шифрования. Твои рекомендации из предыдущего сообщения правильные:

- Если сеть недоверенная — используй **TLS‑туннель** (stunnel, VPN) или **Modbus Security** (это отдельный стандарт поверх Modbus).
- Реализуй **контроль доступа** на уровне приложения (разрешённые IP, роли, списки регистров).
- Веди **логирование** запросов и исключений — это сильно упрощает отладку.

Пункт 2. ADU и PDU: Modbus RTU (последовательная линия, RS‑485)
Что такое PDU и ADU в RTU

    PDU (Protocol Data Unit) — смысловая часть сообщения: [Function Code (1 байт)] [Data (N байт)]. Она одинакова для RTU и TCP.
    ADU (Application Data Unit) в RTU — это PDU, «обёрнутый» для последовательной линии:
    [Device Address (1 байт)] [PDU] [CRC-16 (2 байта)].

Критичные детали, без которых сервер не будет работать

1. CRC‑16 Modbus — строгая математика, а не «примерно»

Для RTU сервер (или драйвер) обязан корректно считать и проверять CRC. Если CRC не сойдётся, кадр просто отбрасывается без ответа.

Что нужно зафиксировать в коде:

    Полином: 0xA001 (реверсивный).
    Начальное значение регистра: 0xFFFF.
    Отражение (reflection): да, байты отражаются (bit-reversed).
    Порядок байт в кадре: младший байт CRC идёт первым (little‑endian).

В Rust это обычно делают через готовую реализацию CRC (например, crc crate), но важно указать именно параметры Modbus, а не какой‑то другой CRC16. 2. Разделение кадров по паузам — специфика RTU

В RTU нет поля длины, поэтому кадры разделяют по времени:

    Между кадрами должна быть пауза не менее 3,5 символов при текущей скорости линии.
    Внутри кадра пауза не должна превышать 1,5 символа.

Следствие для реализации: если ты делаешь поддержку RS‑485, то парсер должен уметь «ждать» эту паузу, чтобы понять, где заканчивается один кадр и начинается следующий. В TCP такого нет: там кадры разделяются по полю Length в MBAP. 3. Физические параметры линии — не часть протокола, но обязательны для работы

Это не спецификация Modbus как таковая, но без этого ничего не заработает:

    Скорость (baud rate): 9600, 19200 и т.д.
    Чётность (parity): none/even/odd.
    Стоп‑биты: 1 или 2.

В коде сервера на Arch Linux это будет настройкой драйвера/UART (например, через serialport или tokio-serial).
Пример ADU для RTU (в байтах)

Запрос «прочитать 3 holding register с адреса 100» к устройству 1:

text

[0x01] [0x03] [0x00 0x64] [0x00 0x03] [CRC_LSB] [CRC_MSB]

Где:

    0x01 — Device Address (адрес устройства).
    0x03 — Function Code (Read Holding Registers).
    0x00 0x64 — начальный адрес (100).
    0x00 0x03 — количество регистров (3).
    Последние 2 байта — CRC‑16.

Ответ будет аналогичным: адрес + PDU (с количеством байт и значениями регистров) + CRC.
Как это ложится в твой стек: Rust + tokio + Arch

Если ты планируешь поддержку RTU в будущем (например, сервер, который может работать и по TCP, и по RS‑485):

    Вынеси CRC‑расчёт в отдельный модуль. Это чистая функция: fn crc16_modbus(data: &[u8]) -> u16.
    Сделай отдельный парсер для RTU‑кадра, который:
        читает байты из UART,
        ждёт паузу 3,5 символа, чтобы определить конец кадра,
        проверяет CRC,
        выделяет PDU.
    Логика обработки PDU должна быть общей для RTU и TCP: после того как ты получил чистый PDU, дальше ты делаешь одни и те же проверки функций, адресов, диапазонов и т.п.

Это даёт переиспользуемость: один и тот же «движок» Modbus (работа с регистрами, функции, исключения) будет работать поверх разных транспортов.
Важное замечание с учётом твоей задачи

Ты делаешь сервер под Arch Linux и, скорее всего, в первую очередь тебе нужен Modbus TCP. Для него CRC и паузы не нужны. Но если в будущем ты захочешь сделать шлюз RS‑485 ↔ Ethernet или сервер, который умеет и по TCP, и по последовательному порту, то именно эти детали (CRC и тайминги) будут самыми «коварными»: малейшая ошибка в отражении битов или порядке байт — и кадры не проходят.

Пункт 3. ADU и PDU: Modbus TCP (MBAP Header)

В Modbus TCP структура кадра (ADU) принципиально отличается от RTU: вместо адреса и CRC спереди идёт фиксированный 7‑байтный заголовок MBAP, а CRC вообще не используется — целостность гарантирует TCP.
Структура MBAP Header (7 байт, big‑endian)
Поле Размер Значение / назначение
Transaction Identifier 2 байта Уникальный ID запроса. Сервер обязан вернуть тот же ID в ответе — это критично при параллельных запросах и в одном соединении.
Protocol Identifier 2 байта Почти всегда 0x0000. Зарезервировано для будущих расширений. Если не 0 — кадр можно отклонять.
Length 2 байта Длина оставшихся данных: Unit Identifier + весь PDU. Важно: это не длина PDU, а «Unit ID + PDU».
Unit Identifier 1 байт Аналог Device Address из RTU. В чистом TCP‑окружении часто ставят 1 (или 255 в некоторых SCADA). Может использоваться как идентификатор устройства внутри шлюза.

Важно: все многобайтовые поля в Modbus — big‑endian (старший байт первый). В Rust это нужно учитывать при чтении/записи.
Пример: как собрать MBAP для ответа

Допустим, пришёл запрос:

    Transaction ID: 0x1234
    Protocol ID: 0x0000
    Length: 0x0006 (Unit ID 1 байт + PDU 5 байт)
    Unit ID: 0x01
    PDU: 0x03 0x00 00 0x00 03 (Read Holding Registers, адрес 0, кол‑во 3)

Сервер обрабатывает, формирует ответный PDU (например, 6 байт данных): 0x03 0x06 0xAA 0xBB 0xCC 0xDD 0xEE 0xFF.

Тогда MBAP для ответа:

    Transaction ID: тот же 0x1234
    Protocol ID: 0x0000
    Length: длина Unit ID (1) + длина PDU (8) = 9 → 0x0009
    Unit Identifier: тот же 0x01

Итоговый ADU (MBAP + PDU):
text

[0x12 0x34] [0x00 0x00] [0x00 0x09] [0x01] [0x03 0x06 0xAA 0xBB 0xCC 0xDD 0xEE 0xFF]

Критические моменты для реализации на Rust + tokio

    Всегда читай ровно 7 байт MBAP в начале. Если меньше — это неполный кадр; если соединение закрылось — это нормально, просто заверши обработку.
    Проверяй Protocol Identifier. Если не 0, можно сразу возвращать ошибку или закрывать соединение — это невалидный Modbus TCP.
    Length — это «Unit ID + PDU», а не только PDU. Частая ошибка: брать Length как длину PDU и пытаться прочитать столько байт. На деле: после заголовка нужно прочитать ещё Length байт, и среди них первый — Unit Identifier, остальное — PDU.
    Transaction ID не интерпретируется сервером, но обязательно копируется «как есть» в ответ. Это позволяет клиентам сопоставлять запросы и ответы, особенно когда в одном TCP‑соединении летит несколько запросов.
    Unit Identifier можно либо проверять (разрешённые ID), либо игнорировать (если у тебя один сервер без шлюзов). Но в любом случае его нужно корректно прочитать и в ответе вернуть тот же байт.

Как это выглядит в коде (Rust, tokio)

Пример парсинга MBAP (без обработки ошибок для краткости):
rust

use tokio::io::{AsyncReadExt, BufReader};

const MBAP_LEN: usize = 7;

async fn read_mbap(reader: &mut BufReader<impl AsyncReadExt + Unpin>) -> Result<[u8; MBAP_LEN], Box<dyn std::error::Error>> {
let mut mbap = [0u8; MBAP_LEN];
reader.read_exact(&mut mbap).await?;
Ok(mbap)
}

// Дальше можно распарсить поля:
// transaction_id = u16::from_be_bytes([mbap[0], mbap[1]])
// protocol_id = u16::from_be_bytes([mbap[2], mbap[3]])
// length = u16::from_be_bytes([mbap[4], mbap[5]])
// unit_id = mbap[6]

Формирование ответа:
rust

fn build_mbap_response(tx_id: u16, unit_id: u8, pdu_len: usize) -> [u8; MBAP_LEN] {
let mut mbap = [0u8; MBAP_LEN];
mbap[0..2].copy_from_slice(&tx_id.to_be_bytes());
// protocol id = 0 по умолчанию, уже 0
mbap[4..6].copy_from_slice(&(unit_id as usize + pdu_len).to_be_bytes()); // length
mbap[6] = unit_id;
mbap
}

Чем TCP принципиально проще и чем сложнее, чем RTU

Проще:

    Нет CRC — не нужно считать и проверять контрольную сумму.
    Нет таймингов и пауз между кадрами — кадры разделяются по полю Length.
    Нет физических настроек (baud rate, parity) — это уровень TCP/IP.

Сложнее:

    Нужно строго соблюдать формат MBAP и порядок байт (big‑endian).
    Нужно правильно трактовать Length как «Unit ID + PDU» и не ошибиться в подсчёте.
    Параллельные запросы и соединения требуют аккуратной работы с Transaction ID и Unit ID.

Нюанс про порт и сеть

    Порт по умолчанию — 502. В тестовых средах можно использовать другой, но в реальных проектах и SCADA почти всегда 502.
    Unit Identifier в TCP часто используют как «логический адрес» внутри шлюзов или мульти‑мастерных сетей. Если ты делаешь простой сервер без шлюзов, можно фиксировать Unit ID на уровне конфигурации (например, 1) и отклонять запросы с другими ID, либо принимать любые.

Следствие для твоего проекта (Arch Linux, Rust, tokio)

Поскольку ты делаешь сервер на Arch Linux с асинхронным стеком, Modbus TCP — это самый естественный выбор:

    Ты слушаешь TCP‑порт и принимаешь соединения.
    Для каждого соединения читаешь кадры по схеме: «7 байт MBAP → Length байт (Unit ID + PDU)».
    Обрабатываешь PDU, формируешь ответный PDU, собираешь MBAP с тем же Transaction ID и отправляешь.

Это даёт чистую, предсказуемую логику без низкоуровневых таймингов, которые нужны для RTU.

Четыре типа данных Modbus

Modbus оперирует четырьмя типами адресного пространства. Каждый тип имеет свои разрешения (чтение/запись) и размер элемента:
Тип Размер элемента Чтение Запись Коды функций Аналогия
Coils 1 бит да да (1 / N) 0x01, 0x05, 0x0F Дискретные выходы, реле, флаги
Discrete Inputs 1 бит да нет 0x02 Дискретные входы, датчики «да/нет»
Input Registers 16 бит да нет 0x04 Аналоговые входы, показания датчиков
Holding Registers 16 бит да да (1 / N) 0x03, 0x06, 0x10 Переменные, настройки, состояния

Ключевое: Coils и Discrete Inputs — битовые. Input Registers и Holding Registers — 16‑битные слова. Это определяет, как ты будешь хранить данные в памяти сервера.

Форматы запросов и ответов для ключевых функций
0x03 — Read Holding Registers

Запрос:

text

[0x03] [Start Address (2 байта, BE)] [Quantity (2 байта, BE)]

    Start Address: 0–65535.
    Quantity: 1–125 (для 0x03). Превышение → Exception 0x83 с кодом 03.

Ответ:

text

[0x03] [Byte Count (1 байт)] [Register Values (Quantity × 2 байта, BE каждое)]

    Byte Count = Quantity × 2.
    Каждый регистр — 2 байта, big‑endian.

Пример: запрос на чтение 3 регистров с адреса 0.

text

Запрос: 0x03 0x00 0x00 0x00 0x03
Ответ: 0x03 0x06 0x12 0x34 0x56 0x78 0x9A 0xBC
(0x06 = 6 байт данных = 3 регистра × 2)

0x04 — Read Input Registers

Формат идентичен 0x03, только другой код функции и другое адресное пространство (Input Registers вместо Holding). Quantity: 1–125.
0x01 — Read Coils

Запрос:

text

[0x01] [Start Address (2 байта, BE)] [Quantity (2 байта, BE)]

    Quantity: 1–2000 (битов).

Ответ:

text

[0x01] [Byte Count (1 байт)] [Coil Status (N байтов, упаковка битами)]

    Биты упакованы: 8 бит на байт, младший бит первого байта = Coil с наименьшим адресом.
    Если Quantity не кратно 8, последние биты в последнем байте — нули (padding).

Пример: запрос на чтение 10 coils с адреса 0.

text

Запрос: 0x01 0x00 0x00 0x00 0x0A
Ответ: 0x01 0x02 0xCD 0x01
(2 байта данных, 0xCD = биты 0–7, 0x01 = биты 8–9 + padding)

0x02 — Read Discrete Inputs

Формат идентичен 0x01, только другой код функции и адресное пространство Discrete Inputs (только чтение). Quantity: 1–2000.
0x05 — Write Single Coil

Запрос:

text

[0x05] [Address (2 байта, BE)] [Value (2 байта, BE)]

    Value: 0xFF00 = ON, 0x0000 = OFF. Любое другое значение → Exception 0x85, код 03.

Ответ: эхо запроса (сервер возвращает те же 4 байта).
0x06 — Write Single Register

Запрос:

text

[0x06] [Address (2 байта, BE)] [Value (2 байта, BE)]

Ответ: эхо запроса.
0x0F — Write Multiple Coils

Запрос:

text

[0x0F] [Start Address (2 байта, BE)] [Quantity (2 байта, BE)] [Byte Count (1 байт)] [Values (N байтов)]

    Quantity: 1–1968.
    Биты упакованы так же, как в ответе 0x01.

Ответ:

text

[0x0F] [Start Address (2 байта, BE)] [Quantity (2 байта, BE)]

(Возвращается начальный адрес и количество, а не сами значения.)
0x10 — Write Multiple Registers

Запрос:

text

[0x10] [Start Address (2 байта, BE)] [Quantity (2 байта, BE)] [Byte Count (1 байт)] [Values (Quantity × 2 байта, BE)]

    Quantity: 1–123.
    Byte Count = Quantity × 2.

Ответ:

text

[0x10] [Start Address (2 байта, BE)] [Quantity (2 байта, BE)]

0x16 — Mask Write Register (если захочешь поддержать)

Запрос:

text

[0x16] [Address (2 байта, BE)] [AND Mask (2 байта, BE)] [OR Mask (2 байта, BE)]

Логика: Result = (Current AND AND_Mask) OR OR_Mask. Позволяет менять отдельные биты регистра за один запрос.

Ответ: эхо запроса.
0x17 — Read/Write Multiple Registers

Запрос:

text

[0x17] [Read Start Addr (2)] [Read Quantity (2)] [Write Start Addr (2)] [Write Quantity (2)] [Write Byte Count (1)] [Write Values (Write Qty × 2)]

    Сначала выполняется запись, потом чтение. Атомарность — на усмотрение реализации.

Ответ: как у 0x03 (Byte Count + значения).
Лимиты количества элементов (из спецификации)
Функция Минимум Максимум
0x01 / 0x02 (чтение бит) 1 2000
0x03 / 0x04 (чтение регистров) 1 125
0x0F (запись N бит) 1 1968
0x10 (запись N регистров) 1 123
0x17 (чтение) 1 125
0x17 (запись) 1 121

Пункт 5. Адресация и «человеческая» нотация (1xxxx, 3xxxx, 4xxxx)

Это один из самых частых источников ошибок: в документации устройств пишут «адрес 40001», а в протоколе Modbus он означает «регистр 0». Если не сделать конвертацию, сервер и клиент будут «говорить про разные ячейки».
Два мира адресов

    Протокол (0‑based) — то, что реально летит по сети: адреса от 0 до 65535. Это то, с чем ты работаешь внутри кода.
    «Человеческая» нотация Modicon — то, что пишут в мануалах: 10001, 20001, 30001, 40001 и т.д.

В Modbus Application Protocol адресация всегда 0‑based, а «человеческие» номера — это просто сдвиг по типу регистра.
Как устроена нотация
Тип регистра Протокол (адрес в пакете) Человеческий номер (Modicon) Формула перевода
Coils 0, 1, 2… 10001, 10002, 10003… human = protocol + 10001
Discrete Inputs 0, 1, 2… 20001, 20002, 20003… human = protocol + 20001
Input Registers 0, 1, 2… 30001, 30002, 30003… human = protocol + 30001
Holding Registers 0, 1, 2… 40001, 40002, 40003… human = protocol + 40001

Примеры:

    Holding Register 0 → «40001»
    Holding Register 100 → «40101»
    Coil 0 → «10001»

Где это встречается в реальной жизни

    SCADA‑системы (WinCC, Ignition, Rapid SCADA) часто показывают адреса в «человеческой» нотации.
    Конфигураторы устройств (ПЛК, датчики, реле) используют 40001/40002 и т.п.
    Тестовые клиенты (modbus-poll, QModMaster) дают выбор: «Display as 4xxxx» или «Use 0‑based».

Если ты делаешь сервер, который будет подключаться к готовой SCADA, скорее всего, она будет слать запросы в 0‑based (потому что это стандарт протокола), но в интерфейсе оператора будет написано 40xxx. Важно не перепутать: в пакете всегда 0‑based.
Что делать в своём сервере на Rust

У тебя есть два пути. Выбери один и задокументируй его — иначе будет путаница.
Вариант A: сервер работает строго в 0‑based

Ты принимаешь адреса как есть (0–65535) и ничего не конвертируешь.

Плюсы:

    Проще: нет скрытых преобразований.
    Соответствует спецификации.
    Меньше шансов «угадать неправильно».

Минусы:

    Если оператор привык к 40001, ему придётся вычитать 40001 из номера.

Как реализовать:

rust

// Никаких конвертаций: адрес из пакета — сразу в индекс
let start_addr = u16::from_be_bytes([buf[0], buf[1]]);
let quantity = u16::from_be_bytes([buf[2], buf[3]]);

Вариант B: сервер принимает «человеческие» адреса и конвертирует внутри

Сервер понимает, что «40001» — это Holding Register 0, и сам делает вычитание.

Плюсы:

    Удобно для операторов, которые привыкли к 40xxx/30xxx.
    Можно сделать «совместимость с привычными мануалами».

Минусы:

    Риск двойной конвертации: если SCADA уже конвертирует, а сервер тоже — получится сдвиг на 40001 дважды.
    Нужно чётко документировать: «сервер ожидает адреса в Modicon‑нотации».

Как реализовать (пример только для Holding Registers):

rust

const HOLDING_OFFSET: u16 = 40001;

fn to_protocol_address(human: u16) -> Option<u16> {
if human < HOLDING_OFFSET {
return None; // неверный формат
}
Some(human - HOLDING_OFFSET)
}

Для всех типов можно сделать общую функцию:

rust

enum RegisterType {
Coil,
DiscreteInput,
InputRegister,
HoldingRegister,
}

const OFFSETS: [u16; 4] = [10001, 20001, 30001, 40001];

fn human_to_protocol(reg_type: RegisterType, human: u16) -> Option<u16> {
let offset = OFFSETS[reg_type as usize];
if human < offset {
return None;
}
Some(human - offset)
}

Частые ошибки и как их избежать

    «Я думал, 40001 — это первый регистр, и в коде сделал index = addr - 40001»
    Если клиент уже шлёт 0‑based (а он должен), то ты сдвигаешь дважды и получаешь неверный индекс.
    Решение: либо работай строго в 0‑based, либо явно укажи, что сервер ожидает «человеческие» адреса, и пусть клиент/SCADA не делает свою конвертацию.

    Смешивание типов
    Нельзя считать, что «все 4xxxx — это holding registers». Это просто нотация.
    Решение: тип регистра определяется кодом функции (0x03/0x04 и т.п.), а не числом адреса.

    Неучтённые лимиты
    Даже если ты принимаешь «человеческие» адреса, диапазон всё равно ограничен: протокол позволяет 0–65535, значит, «человеческий» максимум — 40001 + 65535 = 105536 (но многие устройства и клиенты используют только часть диапазона).

Практический совет для твоего проекта (Rust + tokio + Arch)

Учитывая, что ты делаешь сервер с нуля и планируешь использовать его в разработке:

    Рекомендую работать строго в 0‑based. Это соответствует спецификации, проще тестировать (modbus‑poll позволяет явно включать/выключать отображение 4xxxx), и меньше шансов на ошибку.
    В документации сервера явно напиши: «Сервер использует 0‑based адресацию согласно Modbus Application Protocol. Holding Register 0 соответствует адресу 40001 в Modicon‑нотации».
    Если позже понадобится поддержка «человеческих» адресов, сделай это опционально через флаг конфигурации, а не по умолчанию.

Пример: как это выглядит в реальном запросе

Запрос «прочитать 3 holding register, начиная с 40001»:

    Человек думает: «40001».
    В протоколе это: адрес 0.
    Запрос (PDU): 0x03 0x00 0x00 0x00 0x03
    Ответ: 0x03 0x06 <6 байт данных>

Если бы ты сделал конвертацию в сервере, то при получении адреса 0 ты бы мог в логах писать «Holding Register 0 (40001)», чтобы оператору было понятно.

Пункт 6. Исключения и коды ошибок

В Modbus сервер не просто «молчит» при ошибке — он обязан вернуть специальный ответ‑исключение (exception response), чтобы клиент понял, что запрос не выполнен и почему.
Как устроен ответ‑исключение

Ответ‑исключение — это тот же PDU, но с изменённым кодом функции и одним дополнительным байтом:

    Код функции: к оригинальному коду добавляют 0x80 (старший бит).
    Пример: 0x03 (Read Holding Registers) → 0x83 (исключение для этой функции).
    Второй байт: код исключения (1, 2, 3, …).

Формат: [Function Code | Exception Code].

Никаких полей длины, CRC и т.п. сверх этого в PDU нет. В TCP этот PDU всё так же упаковывается в MBAP (с тем же Transaction ID и Unit ID).
Основные коды исключений (из Modbus Application Protocol)
Код Hex Название Когда возвращать
01 0x01 Illegal Function Функция не поддерживается сервером (например, клиент шлёт 0x14, а ты не реализуешь Read File Record).
02 0x02 Illegal Data Address Адрес вне диапазона твоей памяти (например, запрашивают Holding Register 1000, а у тебя только 0–99).
03 0x03 Illegal Data Value Значение невалидно: слишком много элементов, некорректный бит‑флаг (например, Write Single Coil с Value ≠ 0xFF00/0x0000), и т.д.
04 0x04 Failure in Associated Device Устройство, к которому ты «пробрасываешь» запрос (шлюз/реальный прибор), недоступно или отказалось. Для чистого софтверного сервера это редко.

Есть и другие (5–12), но в 95 % случаев хватает этих четырёх.
Примеры, как это выглядит в байтах
Пример 1: Illegal Function (0x01)

Клиент: 0x03 0x00 0x00 0x00 0x01 (Read Holding Register)
Сервер (если функция отключена): 0x83 0x01
Пример 2: Illegal Data Address (0x02)

Клиент: 0x03 0x00 0x64 0x00 0x01 (адрес 100)
У тебя Holding Registers только 0–50 → сервер: 0x83 0x02
Пример 3: Illegal Data Value (0x03)

Клиент: 0x03 0x00 0x00 0x00 0xFF (запрашивает 255 регистров)
Лимит для 0x03 — 125 → сервер: 0x83 0x03
Пример 4: Write Single Coil с неверным значением

Клиент: 0x05 0x00 0x00 0x12 0x34 (Value 0x1234 ≠ 0xFF00 или 0x0000)
Сервер: 0x85 0x03
Где и как проверять, чтобы вернуть исключение

Для каждой функции делай проверки в строгом порядке (это важно для предсказуемой диагностики):

    Поддерживается ли функция?
    Если нет — Illegal Function (01).
    Валиден ли адрес? (не выходит ли за границы массива)
    Если нет — Illegal Data Address (02).
    Валидно ли количество? (лимиты по спецификации: 125 регистров, 2000 бит и т.д.)
    Если нет — Illegal Data Value (03).
    Специфичные проверки функции (например, для Write Single Coil: значение должно быть 0xFF00 либо 0x0000).
    Если не проходит — Illegal Data Value (03).

Только если все проверки пройдены — выполняй операцию и возвращай нормальный PDU.
Реализация на Rust (общий шаблон)
rust

fn handle_read_holding_registers(
start: u16,
count: u16,
store: &ModbusStore,
) -> Result<Vec<u8>, ModbusException> {
// 1. Проверка поддержки функции — обычно на уровне диспетчеризации
// 2. Проверка адреса
if start as usize + count as usize > store.holding_registers.len() {
return Err(ModbusException::IllegalDataAddress);
}
// 3. Проверка лимита количества
if count == 0 || count > 125 {
return Err(ModbusException::IllegalDataValue);
}

    // Чтение данных
    let values: Vec<u16> = store.holding_registers[start as usize..(start + count) as usize]
        .iter().copied().collect();

    // Формирование PDU: [0x03] [ByteCount] [Values...]
    let mut pdu = Vec::with_capacity(1 + 1 + values.len() * 2);
    pdu.push(0x03);
    pdu.push((values.len() * 2) as u8);
    for v in values {
        pdu.extend_from_slice(&v.to_be_bytes());
    }
    Ok(pdu)

}

# [derive(Debug, Clone, Copy, PartialEq, Eq)]
enum ModbusException {
IllegalFunction,
IllegalDataAddress,
IllegalDataValue,
FailureInDevice,
}

impl ModbusException {
fn to_exception_pdu(&self, original_fc: u8) -> Vec<u8> {
let exc_code = match self {
ModbusException::IllegalFunction => 0x01,
ModbusException::IllegalDataAddress => 0x02,
ModbusException::IllegalDataValue => 0x03,
ModbusException::FailureInDevice => 0x04,
};
vec![original_fc | 0x80, exc_code]
}
}

В обработчике запроса ты делаешь match result:

    Ok(pdu) → формируешь ответ с нормальным PDU.
    Err(exc) → формируешь PDU исключения через exc.to_exception_pdu(fc).

Важные нюансы для твоего сервера на Arch Linux + Rust + tokio

    Не маскируй ошибки. Если клиент запрашивает несуществующий регистр — верни 0x83 0x02, а не «тишину» или произвольные данные. Иначе SCADA будет думать, что всё ок, и показывать мусор.
    Логируй исключения. Запиши в лог: Transaction ID, Unit ID, Function Code, Address, Quantity, Exception Code. Это сильно ускоряет отладку при интеграции.
    Не смешивай сетевые и протокольные ошибки.
        Таймауты, разрыв соединения, ошибки чтения — это уровень TCP/tokio.
        Illegal Function, Illegal Data Address и т.д. — это уровень протокола Modbus. Их ты возвращаешь как exception response.
    Transaction ID в ответе‑исключении должен быть тем же, что и в запросе. Это позволяет клиенту сопоставить исключение с конкретным запросом.

Пункт 7. Порядок байт (Endianness) и упаковка данных

Это зона, где Modbus «ломает» ожидания новичков: протокол стандартизирует только 16‑битные регистры в big‑endian, а всё остальное (float, double, 32‑битные значения, порядок слов) — на совести производителя устройства. Если ты делаешь сервер, который будет отдавать данные в «человеческом» виде (например, температуру как float), тебе нужно чётко зафиксировать и документировать свои правила.
Что в спецификации стандартизировано

    Регистры Modbus — 16 бит.
    Порядок байт внутри регистра — big‑endian (старший байт первый). Это жёстко прописано в Modbus Application Protocol.
    PDU в целом тоже передаётся в сетевом порядке байт (big‑endian).

Пример: значение 0x1234 в регистре:

    В сети: 0x12 0x34.
    В Rust: u16::to_be_bytes().

Где начинаются проблемы: сложные типы

Modbus не стандартизирует:

    Float/double,
    32/64‑битные целые,
    Порядок слов (word order) при склейке двух регистров.

Поэтому разные вендоры делают по‑разному. Самые частые схемы для 32‑битных значений (2 регистра):
Вариант Порядок слов Порядок байт в слове Как выглядит в байтах (для 0xAABBCCDD)
Big Endian (BE) старший регистр первый big‑endian AA BB CC DD
Little Endian (LE) младший регистр первый little‑endian DD CC BB AA
Mixed A старший регистр первый little‑endian в каждом BB AA DD CC
Mixed B младший регистр первый big‑endian в каждом CC DD AA BB

Для float это ещё хуже: IEEE‑754 float из двух регистров может быть закодирован любым из этих способов, и без документации устройства угадать нельзя.

Следствие для твоего сервера: если ты собираешься отдавать float/int32 из нескольких регистров, ты должен сам выбрать схему и зафиксировать её в документации. Иначе клиенты будут получать «мусор».
Упаковка битовых значений (Coils и Discrete Inputs)

Это тоже стандартизировано:

    Биты идут по 8 штук в байте.
    Младший бит первого байта — это Coil с наименьшим адресом.
    Если количество запрашиваемых битов не кратно 8, лишние биты в последнем байте — нули (padding).

Пример: Coils 0–9 (10 бит):

    Байт 0: биты 0–7 → 0b11110000 (если 0–3 = 1) = 0xF0.
    Байт 1: биты 8–9 и 6 нулей → 0b00000011 = 0x03.
    Итого: F0 03.

В Rust удобно использовать bitvec или вручную собирать байты.
Как это ложится в твой стек: Rust + tokio + Arch
Хранение vs передача

У тебя есть два слоя:

    Внутреннее хранение — в удобном для Rust формате (например, Vec<u16> для регистров, Vec<bool> для катушек).
    Сериализация в PDU — строго по правилам Modbus (big‑endian для регистров, битовая упаковка для coils).

Раздели эти слои: пусть структура ModbusStore хранит данные «как удобно», а отдельные функции делают конвертацию в/из байтов.
Пример: запись Holding Register в PDU

pdu.push(0x06); // Write Single Register
pdu.extend_from_slice(&address.to_be_bytes());
pdu.extend_from_slice(&value.to_be_bytes());

}

Float и int32: как сделать правильно в своём сервере

Если ты хочешь поддерживать float/int32, выбери одну схему и зафиксируй её. Например:

    Float: 2 регистра, big‑endian по словам и по байтам (AA BB CC DD).
    Int32: то же самое.

Сделай отдельные функции:
rust

use std::mem;

fn u16_to_f32_be(hi: u16, lo: u16) -> f32 {
let bytes: [u8; 4] = [
(hi >> 8) as u8,
hi as u8,
(lo >> 8) as u8,
lo as u8,
];
f32::from_be_bytes(bytes)
}

fn f32_to_u16_be(value: f32) -> (u16, u16) {
let bytes = value.to_be_bytes();
let hi = ((bytes[0] as u16) << 8) | (bytes[1] as u16);
let lo = ((bytes[2] as u16) << 8) | (bytes[3] as u16);
(hi, lo)
}

И обязательно напиши в документации: «Float кодируется как 2 Holding Registers, big‑endian (старший регистр первый, в каждом регистре big‑endian)».
Частые ошибки

    Путать порядок байт и порядок слов. Например, делать to_le_bytes() для регистров — это сразу ломает совместимость.
    Не документировать схему для float. Клиент ожидает одну схему, сервер отдаёт другую — данные «плывут».
    Смешивать хранение и передачу. Хранить в little‑endian и забывать конвертировать при отправке.
    Игнорировать padding в битовых ответах. Если не обнулить лишние биты, клиент может интерпретировать их как данные.

Практические советы для твоего проекта

    Для начала поддерживай только 16‑битные Holding/Input Registers. Это покрывает 80 % задач и избавляет от головной боли с float.
    Если нужен float — сделай это отдельным документированным режимом. Не пытайся «угадать» формат под каждого клиента.
    Используй to_be_bytes() / from_be_bytes() везде, где речь про Modbus. Это явно показывает намерение и снижает риск ошибок.
    Тестируй через Wireshark. В диссекторе Modbus сразу видно, правильно ли идут байты и совпадают ли значения с ожидаемыми.

Пункт 8. Modbus TCP vs RTU в контексте Rust + tokio (Arch Linux)

Ты делаешь сервер на Arch Linux с асинхронным рантаймом tokio — это сильно влияет на то, какой транспорт выбрать и как его реализовывать. Ниже — сравнение именно с точки зрения твоего стека и типичных задач.
Где каждый из протоколов уместен
Сценарий Лучше подходит Почему
Сервер на ПК/сервере (Arch), SCADA, тестовые клиенты Modbus TCP Нативная работа с TCP, нет низкоуровневых таймингов, проще тестировать, легче масштабировать на много соединений.
Шлюз: Ethernet ↔ RS‑485 Оба Сервер принимает TCP, а внутри пробрасывает в RTU на линии.
Встраиваемое устройство на UART (ESP32, STM32) Modbus RTU Физически нет Ethernet, есть только последовательный порт.
Прототип/разработка на ноутбуке Modbus TCP Не нужен конвертер USB‑RS485, не нужны тайминги, проще отладка.

Для твоего случая (Arch + Rust + tokio + разработка) Modbus TCP — основной вариант, а RTU — опционально, если планируешь делать шлюз.
Архитектурные различия в реализации
Modbus TCP: «чистый» сетевой стек

    Транспорт: TCP (tokio::net::TcpStream).
    Границы кадров: по полю Length в MBAP.
    Нет: CRC, таймингов пауз, baud rate, parity.
    Параллелизм: tokio отлично справляется с сотнями соединений; каждое соединение — отдельный task.
    Обработка: читаешь 7 байт MBAP → читаешь Length байт → парсишь PDU → отвечаешь.

Плюсы для твоего стека:

    Полностью асинхронный ввод‑вывод без блокировок.
    Не нужно управлять таймерами на уровне «3,5 символа» — это проблема RTU.
    Легко писать тесты: можно поднимать локальный TCP‑сервер и слать пакеты через простые клиенты.

Modbus RTU: «низкоуровневый» последовательный стек

    Транспорт: UART/RS‑485 (например, tokio-serial).
    Границы кадров: пауза ≥ 3,5 символа между кадрами.
    Есть: CRC‑16, физические настройки (baud, parity, stop bits).
    Параллелизм: обычно один порт — один поток/task; параллельные запросы обрабатываются последовательно.
    Обработка: читаешь байты в буфер → ждёшь паузу → проверяешь CRC → парсишь ADU → отвечаешь (с новой паузой).

Минусы для твоего стека (если не нужен шлюз):

    Тайминги и паузы усложняют асинхронную логику.
    Нужны внешние конвертеры USB‑RS485 и драйверы.
    Больше потенциальных точек отказа (кабель, подтяжки, терминаторы, наводки).

Как это выглядит в коде (Rust + tokio)
TCP-сервер (базовый скелет)

rust

use tokio::net::{TcpListener, TcpStream};
use tokio::io::{AsyncReadExt, AsyncWriteExt};

const MBAP_LEN: usize = 7;

async fn handle_client(mut stream: TcpStream) {
let mut buf = [0u8; 256];
loop {
// Читаем MBAP
if stream.read_exact(&mut buf[..MBAP_LEN]).await.is_err() {
break; // соединение закрыто или ошибка
}
let tx_id = u16::from_be_bytes([buf[0], buf[1]]);
let proto_id = u16::from_be_bytes([buf[2], buf[3]]);
let length = u16::from_be_bytes([buf[4], buf[5]]) as usize;
let unit_id = buf[6];

        if proto_id != 0 {
            // Невалидный протокол — можно закрыть
            break;
        }

        // Читаем Unit ID + PDU
        if length > buf.len() {
            // Слишком большой кадр — защита от ошибок
            break;
        }
        if stream.read_exact(&mut buf[..length]).await.is_err() {
            break;
        }

        let pdu_start = 0; // buf[0] — Unit ID, дальше PDU
        let unit_id_in = buf[pdu_start];
        let pdu = &buf[pdu_start + 1..pdu_start + length];

        // Здесь — логика парсинга PDU и формирования ответа
        let response_pdu = match parse_and_handle_pdu(pdu) {
            Ok(p) => p,
            Err(exc) => exc.to_exception_pdu(pdu[0]), // exception response
        };

        // Собираем MBAP для ответа
        let resp_mbap = build_mbap(tx_id, unit_id, response_pdu.len());

        // Отправляем ADU
        let mut adu = Vec::with_capacity(resp_mbap.len() + response_pdu.len());
        adu.extend_from_slice(&resp_mbap);
        adu.extend_from_slice(&response_pdu);

        if stream.write_all(&adu).await.is_err() {
            break;
        }
    }

}

# [tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
let listener = TcpListener::bind("0.0.0.0:502").await?;
println!("Modbus TCP server listening on :502");

    while let Ok((stream, addr)) = listener.accept().await {
        println!("New connection from {}", addr);
        tokio::spawn(handle_client(stream));
    }

}

RTU (если будешь делать шлюз)

Если позже захочешь добавить поддержку RS‑485 через USB‑конвертер, понадобится tokio-serial:

    Настройка порта: baud, parity, data bits, stop bits.
    Чтение байтов в буфер с ожиданием паузы (таймер на 3,5 символа).

Ключевое: логика обработки PDU может быть общей для TCP и RTU. Ты можешь сделать:

text

[RTU driver] → [общий PDU handler] ← [TCP handler]

Тогда одни и те же функции parse_and_handle_pdu, проверки адресов и исключений работают и для TCP, и для RTU. Разными будут только драйверы транспорта.

        modbus-cli / modbus-poll — для отправки запросов.

    modbus (более низкоуровневая) — полезна, если хочешь понять, как вручную парсить PDU и считать CRC‑16.
    crc — для расчёта CRC‑16 (нужен только для RTU).

Как использовать: не копируй «в лоб», а смотри, как они:

    читают MBAP и определяют длину PDU;
    проверяют коды функций и границы адресов;
    формируют ответные PDU и исключения;
    обрабатывают ошибки транспорта и протокола раздельно.

Open‑source серверы и инструменты

    libmodbus (C) — эталонная реализация. В репозитории есть примеры серверов и клиентов, а также утилиты modbus_tcp_server, modbus_cli. Полезно для тестов и как референс по логике.
    QModMaster / modbus-poll — GUI‑клиенты для тестирования твоего сервера. Ими удобно проверять, правильно ли ты отдаёшь PDU, endianness, адресацию и исключения.
    Wireshark — обязательно для отладки. Встроенный диссектор Modbus показывает MBAP, PDU, типы регистров, коды исключений и порядок байт.

Практические источники для проверки «как делают в индустрии»

    Документация производителей ПЛК и модулей ввода‑вывода (Siemens, Schneider, Omron, WAGO и др.) — в ней часто приводят примеры запросов/ответов в HEX, адресацию (40001 и т.п.) и поддерживаемые функции. Это помогает понять, чего реально ждут клиенты.
    SCADA‑системы (Rapid SCADA, Ignition, WinCC) — в их документации есть разделы про Modbus, где объясняют, как они интерпретируют адреса и типы регистров. Полезно, чтобы не «угадать» неправильно.

Как применять это к твоему проекту (Rust + tokio + Arch)

    Сначала читай Application Protocol и TCP/IP Guide. Выпиши:
        коды функций и их назначение;
        лимиты количества (регистров, битов);
        формат PDU и MBAP;
        коды исключений и когда их возвращать.
    Сравни с примерами в tokio-modbus. Посмотри, как там реализованы:
        чтение MBAP и определение длины;
        проверка границ и формирование исключений;
        сериализация PDU в big‑endian.
    Тестируй на libmodbus/modbus‑cli и Wireshark. Отправь простые запросы, проверь, что:
        Holding Register 0 читается как «40001» в документации, но в пакете это адрес 0;
        при выходе за границы ты получаешь исключение 0x83 0x02;
        float/int32 (если добавишь) совпадают по байтам с тем, что ожидает клиент.
    Документируй свои решения. Если ты выбрал схему кодирования float или порядок слов для int32 — зафиксируй это явно. Иначе при интеграции будут проблемы.

Частые ошибки при использовании сторонних источников

    Опираться только на статьи/форумы. В них часто путают адресацию (10001 vs 0), endianness и формат исключений.
    Копировать примеры без понимания MBAP. Например, забыть про Transaction ID — тогда клиент не сможет сопоставить запрос и ответ.
    Смешивать TCP и RTU. В TCP нет CRC‑16 и пауз между кадрами — это частая ошибка при копировании логики из RTU‑примеров.
    Не проверять лимиты. Спецификация чётко ограничивает количество регистров (125 для 0x03) и битов (2000 для 0x01). Если превысить — нужно возвращать исключение 0x03.

Быстрый чек‑лист для твоего сервера

    Прочитал Application Protocol v1.1b3 и TCP/IP Guide v1.0b — знаешь, какие коды функций и исключений использовать.
    В коде адресация строго 0‑based (адрес 0 = Holding Register 40001).
    PDU сериализуются в big‑endian (to_be_bytes()).
    Исключения формируются как original_fc | 0x80 + код ошибки.
    Лимиты количества проверяются до доступа к данным.
    Есть тесты через modbus-cli/QModMaster и Wireshark.
