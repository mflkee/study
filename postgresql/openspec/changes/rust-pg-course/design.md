# Design

## Context

См. proposal.md (Why/What). Стек зафиксирован фактами на сентябрь 2026: Rust 1.98.1 локально, Docker 29.8 доступен, сеть есть. Репозиторий `study/postgresql` (бывший `tarantool`) переименован, в нём только `prompt.md` (новый бриф) и OpenSpec-корень. Курс — новый контент в `course/`, существующего кода нет. Спеки: `course-content` и `course-stand` (см. specs/rust-pg-course/).

## Goals / Non-Goals

**Goals:**
- Проектирование исполняемого плана сборки: каркас стенда сначала (де-риск до контента), затем модули 00→15 по одному, с проверками и паузами.
- Единый воспроизводимый стенд с profiles: PostgreSQL 18.6 — база, доп. сервисы по модулям.
- Верификация как встроенный гейт: Rust — cargo check/test/clippy, SQL — против живого PG, compose — `docker compose config`.

**Non-Goals:**
- Не курс по общему веб-девелопменту, DevOps или языку Rust во всей полноте: Rust даётся точечно под задачи с БД (см. модули 04–06).
- Не покрытие закрытой информации СИКН/SCADA: кейсы моделируются по открытым описаниям.
- Не поддержка старых версий PostgreSQL: стенд привязан к 18.6; различия с 14–17 упоминаются в тексте, но не тестируются.

## Decisions

### D1: Планирование — OpenSpec, а `course/PLAN.md` — производный документ
Бриф требует `course/PLAN.md` (шаг 2) и подтверждение. Источником плана становится этот change: `proposal.md` + `design.md` + `tasks.md` выполняют роль шага 2 (план + пауза до «ок»). На этапе каркаса (шаг 3 брифа) из них генерируется `course/PLAN.md` — статичный план для ученика. `PROGRESS.md` — живой чеклист, обновляется после каждого модуля. `tasks.md` — чеклист сборки для агента. Три документа с разной аудиторией, без дублирования содержания.

### D2: Основной стек БД-доступа — sqlx 0.9 (async), альтернативы — сравнительно
Выбор sqlx: compile-time проверяемые запросы, встроенные миграции (`sqlx migrate`), единый async-рантайм (tokio). Альтернативы: `tokio-postgres` (низкоуровневый, без макросов `query_as!`; используется в модуле 04 для сравнения), `diesel`/`sea-orm` (ORM, синхронный стиль; плохо ложится на временные ряды и аудит-триггеры). **Под-решение (важно): по умолчанию в упражнениях используются runtime-типизированные запросы `sqlx::query_as::<_, T>`**, а не макросы `query!`/`query_as!`: макросы требуют `DATABASE_URL`/offline-кэш `.sqlx` на этапе компиляции, что ломает «скопировал — собрал» без настройки окружения. Макросы разбираются в отдельном уроке с подготовкой offline-данных.

### D3: Временные ряды — нативный партиционинг как база, TimescaleDB как честное сравнение
Модуль 08 учит нативному партиционированию по `timestamptz` + BRIN + retention + downsampling (без внешних зависимостей, аудируемо). TimescaleDB (hypertable, continuous aggregates) поднимается отдельным profile стенда и сравнивается честно: где выигрыш, где оверхед и лишняя зависимость. Образ не совместим с основным на том же порту — отдельный контейнер на другом порту.

### D4: Метрология — только NUMERIC/rust_decimal, не f64
Расчёты массы нетто и метрологические величины — `numeric(p,s)` в PG и `rust_decimal` в Rust (точный decimal, не float). `f64` допускается только для вспомогательных инженерных величин (температура с достаточной точностью) и явно помечается. Это сквозной кейс 3 с property-тестами (`proptest`).

### D5: Стенд — один `infra/docker-compose.yml` с profiles
- `base`: `postgres:18` на хостовом порту 15432 (не 5432 — избегаем конфликта с возможным локальным PG; на машине автора 5433/5434 уже заняты, поэтому конкретика: 15432/15433), named volume, healthcheck.
- `tools`: клиент psql (профиль) и опционально pgAdmin (порт 5050).
- `obs`: prometheus (9090) + postgres_exporter (9187) + grafana (3000) (модуль 13).
- `timescale`: `timescaledb` (совместимая с PG18 ветка) на порту 15433 (модуль 08).
Миграции и тестовые данные лежат в репозитории (в модулях Rust — `sqlx migrate`; для SQL-модулей — версионированные `.sql`, применяемые автоматически при старте контейнера и/или скриптом `infra/apply-db.sh`). Хостовые порты в нестандартном диапазоне, чтобы не конфликтовать с окружением ученика.

### D6: Modbus — TCP как основной, RTU упоминается в теории
Эмулятор устройств на `tokio-modbus` 0.17 работает по Modbus TCP (дружелюбен к Docker и дебагу). Сценарий ESP32/Modbus RTU описывается в теории и в капстоуне как опция «со звёздочкой» (RTU через виртуальный COM-порт — вне стенда).

### D7: Формат поставки Rust-модулей
Каждый Rust-модуль — самостоятельный cargo-проект в `course/NN-*/` (свой `Cargo.toml`, workspace не общий): ученик открывает модуль независимо, без конфликтов зависимостей между модулями. Крейты общего профиля фиксируются в версиях (sqlx 0.9, tokio 1.53, axum 0.8, rust_decimal 1.43, tokio-modbus 0.17, tracing, thiserror/anyhow). Решения — в `solutions/`, исключены из `.gitattributes`/открытия по умолчанию.

### D8: Порядок сборки и гейты
1. **Каркас (шаг 3 брифа)**: `course/` дерево, корневые README/PROGRESS/resources, `infra/` с базовым стендом; сразу проверяется `docker compose up -d` + первый SQL-смоук против PG 18.6. Это де-риск: если стенд не поднимается — раньше, чем писан контент.
2. **Модули по одному, 00→15**: после каждого — прогон проверок (cargo test / clippy, SQL-скрипты, compose config), обновление `PROGRESS.md`, краткий отчёт (сделано / непроверено / изменено), пауза до команды «дальше» (см. tasks.md, гейты в бриф).
3. **Финал (шаг 5)**: сквозная проверка ссылок между файлами, актуализация корневого README и карты «кейс → модуль».

## Risks / Trade-offs

- [Устаревание версий за время сборки (sqlx 0.9/axum 0.8 уже актуальны, но выйдут новые)] → Версии фиксируются в плане и в каждом cargo-проекте; при появлении мажорных обновлений — осознанное решение, а не молчаливое обновление.
- [Магия compile-time макросов sqlx требует DATABASE_URL/.sqlx] → D2: runtime-типизированные запросы по умолчанию; макросы — отдельный урок с offline-кэшем.
- [Конфликт портов на машине ученика] → D5: нестандартные хостовые порты (5433/5434, 9090, 3000), документация конфликтов.
- [tokio-modbus 0.17 API не совпадает с туториалами из интернета] → Эмулятор пишется и проверяется на раннем этапе (спайк перед модулем 07), реальный запуск против `base`-стенда.
- [TimescaleDB vs PG18 совместимость образов] → Проверяется при каркасе, отдельный profile; если несовместимо — контейнер на базе PG18 + анализ готовых images, пометка UNVERIFIED при невозможности.
- [Объём: 16 модулей — дни работы] → Гейты брифа (один модуль, стоп, «дальше»); каркас и первые три модуля — «пусковой комплект» для ранней обратной связи.
- [Синхронизация репозитория через Syncthing: конкуренция за `.git` с других машин] → Дисциплина «одно git-репо — одна машина одновременно» (см. AGENTS.md); каждый модуль — отдельный коммит для отката (`git revert`).

## Migration Plan

Новый контент, развёртывания нет. Переход: apply создаёт каркас → модули коммитами. Откат: `git revert` конкретного модуля (модуль = один коммит, PROGRESS.md обновляется в том же коммите). Финальная проверка ссылок — шаг 5.
