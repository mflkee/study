# ADR-01: Архитектура Historian — поток от Modbus до дашборда

**Статус:** принято · **Модуль:** 14-capstone-historian · **Дата:** 2026-09-25

## Контекст

СИКН: измерительные устройства выдают данные по Modbus TCP; нужен нижний слой
архитектуры: опрос → буферизация → хранение → отдача в дашборд. Сквозной поток:
эмулятор → шлюз → PostgreSQL → REST API → Grafana.

## Решение

- **Эмулятор** — Modbus TCP-сервер (tokio-modbus) с «живыми» регистрами (масса/плотность).
- **Шлюз** (`gateway`) — опрос раз в 500 мс; точки пишутся батчем (ON CONFLICT);
  при недоступности PG — локальный буфер (файл TSV), периодический flush.
- **Хранилище** — партиционированная `measurements_hist` (RANGE по ts) + аудит
  каталога с цепочкой sha256; идемпотентность приёма через UNIQUE.
- **API** — axum: `/devices`, `/devices/{tag}/current`, `/devices/{tag}/trends`.
- **Grafana** — datasource PostgreSQL + дашборд (провижининг файлами).

## Следствия

- Компоненты переиспользуют модули курса (05, 07–12) — минимальный новый код.
- Буфер — источник правды при отказе БД (модуль 10); восстановление без дублей.
- Дашборд читает напрямую из БД (простота) — REST API для внешних клиентов.

## Альтернативы

- Один монолит вместо трёх бинарей — хуже для демонстрации слоёв и перезапусков.
- Очередь на отдельном брокере — лишняя зависимость; PG-подход достаточно (модуль 10).

# ADR-02: Партиционирование и идемпотентность хранения

**Статус:** принято

## Контекст

Архив измерений растёт навсегда; приём повторными пачками должен быть идемпотентным.

## Решение

- `measurements_hist` — `PARTITION BY RANGE (ts)` по месяцам; недостающие партиции
  создаёт `ensure_partitions` (авто-мост, безопасный DDL).
- Идемпотентность: `UNIQUE (device_id, seq, ts)` + `ON CONFLICT DO NOTHING`.
- **Граница** (важно): партиционированные таблицы требуют включения ключа
  партиции в UNIQUE — поэтому в уникальность входит ts; повторная доставка
  той же точки (тот же seq и ts) уходит в конфликт и отбрасывается.

## Следствия

- Ретеншн будущий — `DROP PARTITION` (модуль 08); полная идемпотентность по
  параметру (device_id, seq) без ts потребовала бы отдельного учётного журнала.

# ADR-03: Выбор драйвера и форм записи

**Статус:** принято

## Контекст

Шлюз пишет тысячи точек в минуту; приём пачками лучше построчного.

## Решение

- **sqlx 0.9** (runtime-запросы) — уже стек курса (D2): пул, типы, миграции.
- Батч через `UNNEST` (модуль 07); для больших объёмов — `COPY` (задел).
- Ошибка БД → буфер на диске (не молчаливая потеря).

## Следствия

- Скорость: один round-trip на пачку; на стенде курс: батч на порядки быстрее
  построчного (модуль 07).

# ADR-04: Буферизация при отказе БД

**Статус:** принято

## Контекст

Связь с PG может падать; шлюз не должен терять данные.

## Решение

- Локальный файл `buffer.tsv` — источник правды при недоступности PG;
  периодический flush батчем; после восстановления — доставка без дублей
  (UNIQUE + ON CONFLICT, ADR-02).
- Ctrl-C — грациозный флаш (модуль 05).

## Следствия

- RPO ≈ интервал между flushes (≤ 5 с в демо); флайк из модуля 10/13
  подтверждён на капстоуне: при `docker compose stop` вот буфер, при старте — докачка.
