# Лаба 01: Отказ БД — без потерь и без дублей

**Кейсы:** 12 (инциденты), 8 (буферизация при потере связи)
**Модуль:** 10-app-patterns
**Время:** 1.5 ч
**Тип:** сломай (по-настоящему) и почини

## Цель

Шлюз буферизует показания локально (кейс 8) и доставляет в PG. Мы **по-настоящему остановим PostgreSQL** (docker compose stop) посреди работы — и убедимся: данные не теряются, после восстановления доставка без дублей.

## Схема стенда

- `course_m06` + `examples/00-setup.sql` (таблицы `metering_points` с UNIQUE(device_id, seq)).
- Пример `04-buffer`: `--generate N` пишет точки в локальный файл, `--flush` доставляет в PG.

## Шаги

1. **Готовим буфер** (профилактика): сотри старый файл, сгенерируй пачку:

   ```bash
   rm -f buffer.tsv
   cargo run --example 04-buffer -- --generate 100
   cargo run --example 04-buffer -- --tail        # 100 строк в буфере
   ```

2. **Останавливаем PostgreSQL** (реальный отказ — тем и ценно):

   ```bash
   cd infra && docker compose stop postgres
   ```

3. **Доставка невозможна** — буфер цел, ничего не потеряно:

   ```bash
   cd ../course/10-app-patterns
   cargo run --example 04-buffer -- --flush
   # вывод: «доставка не удалась: ...», «данные целы в buffer.tsv»
   ```

   Проверь: файл на месте, 100 строк.

4. **Генерируем ещё данные «пока БД лежит»** (шлюз работает, пишет в файл):

   ```bash
   cargo run --example 04-buffer -- --generate 50
   cargo run --example 04-buffer -- --tail        # теперь ~150 строк
   ```

5. **Поднимаем PostgreSQL** и доставляем всё:

   ```bash
   cd infra && docker compose start postgres
   sleep 3   # дождись ready (healthcheck)
   cd ../course/10-app-patterns
   cargo run --example 04-buffer -- --flush
   # «доставлено новых строк в PG: 150 из 150 ... буфер очищен»
   ```

6. **Без дублей**: повторный flush — «буфер пуст», а в PG ровно 150 строк:

   ```bash
   docker compose exec -T postgres psql -U course -d course_m06 \
     -c "SELECT count(*) FROM metering_points;"
   ```

## Критерии успеха

- [ ] Данные, сгенерированные во время простоя PG, доставлены после восстановления (счётчик совпадает)
- [ ] Повторный flush после очистки → 0 новых (дубли исключены UNIQUE+ON CONFLICT)
- [ ] Ни одна строка не потеряна и не задвоена; объясняешь механизм (буфер-файл — источник правды; PG — пункт доставки)
- [ ] `metering_points` в конце содержит ровно столько строк, сколько было сгенерировано
- [ ] PostgreSQL снова работает (стенд цел)

## Разбор типичных проблем

| Симптом | Причина | Решение |
|---|---|---|
| flush «упал», а файл пуст | очистка буфера ДО успешной доставки | чисти буфер только после успешного UPDATE/COMMIT (пример 04 делает так) |
| после восстановления дубли | нет UNIQUE/ON CONFLICT | `(device_id, seq)` PRIMARY KEY + `ON CONFLICT DO NOTHING` |
| flush «молчит» сразу после start | PG ещё не принял соединения (healthcheck) | подожди готовности (`docker compose ps`) и повтори |
| генерация продолжается, а файл растёт без остановки | шлюз не знает о простое | это правильно: буфер неограничен крутится — добавь контроль размера/возраста (задания «со звёздочкой») |
| 0 строк «не хватает» | seq генерировался с нуля в новом прогоне после чистки файла | буфер и seq — продолжай непрерывно (counter в файле), а не обнуляй |

## Задания «со звёздочкой»

1. **Ретрай flush**: оберни доставку в цикл с задержкой — при недоступности PG не выходим, а пробуем каждые 2 с (используй `retry` из модуля 06).
2. **Ограничение буфера**: если файл > N МБ или данные старше 7 дней — алерь/ротацию (в проде: разбиение, старые во «живот», модуль 13).
3. **Контроль размера**: покажи `du -h buffer.tsv` до/после — сколько занимает пачка 10 000 точек (прикинь, сколько «влезет» на диск стенда).
4. **seq из файла**: убедись, что пачки с разными devices не пересекаются по seq (устройство = отдельный counter).
