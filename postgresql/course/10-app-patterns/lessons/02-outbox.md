# Урок 02: Outbox pattern и идемпотентность

**Модуль / кейс:** 10-app-patterns / кейсы 4 (аудит), 6 (события), 8 (буферизация)
**Время:** 2 ч

## Зачем это нужно

«Записал данные, но событие не отправилось» (или наоборот) — классическая проблема не-атомарных двух операций. **Outbox** делает «данные + исходящее событие» атомарными: оба пишутся в одной транзакции, а отдельный процесс (релей) доставляет события наружу. Вторая тема — **идемпотентность**: повторная доставка не должна плодить дубли (`UNIQUE` + `ON CONFLICT`).

## Ключевые идеи (сжато)

- Outbox-таблица (aggregate, payload, status); бизнес-операция пишет и данные, и событие — в одной транзакции.
- Релей: берёт `pending` (SKIP LOCKED), доставляет «наружу», помечает `delivered`.
- Идемпотентность приема: `UNIQUE(device_id, seq)` + `ON CONFLICT DO NOTHING` (буфер шлюза — кейс 8).
- Цена: общая запись чуть дороже; релею нужен мониторинг (накопление pending = диагноз).

## Разбор на примере

```bash
cargo run --example 02-outbox
```

Код — `examples/02-outbox.rs`. Атомарная запись данных + события:

```rust
async fn touch_device(pool: &PgPool, tag: &str) -> Result<()> {
    let mut tx = pool.begin().await?;
    sqlx::query("UPDATE devices SET model = model WHERE tag = $1").execute(&mut *tx).await?;
    sqlx::query("INSERT INTO outbox (aggregate, payload) VALUES ('device.updated', $1)")
        .bind(json!({ "tag": tag })).execute(&mut *tx).await?;
    tx.commit().await?;   // внешняя система увидит событие ТОЛЬКО после COMMIT
}
```

Релей — `relay_once` (SKIP LOCKED, 5 за раз). Фактический вывод:

```
событий в outbox (pending): 2
релей доставил: 2
осталось pending: 0 из 2
```

Идемпотентность (упражнение 02 и буфер шлюза): `INSERT … SELECT * FROM UNNEST(…) ON CONFLICT (device_id, seq) DO NOTHING` — повторная доставка возвращает 0 новых строк.

## Как это устроено под капотом

- Outbox живёт В ТОЙ ЖЕ транзакции — атомарность гарантирована PostgreSQL (commit = данные + событие вместе).
- Релей — отдельный процесс/задача: доставил → пометил; при падении релея pending остаётся → повторная доставка безопасна (идемпотентность на стороне получателя).
- Для буферного шлюза (кейс 8) источник правды — локальный файл; PG — точка доставки; `ON CONFLICT` — защита от дублей при повторном flush.

## Типичные ошибки и грабли

1. **Событие пишется ПОСЛЕ COMMIT данных** — потеряли окно; атомарно = вместе.
2. **Релей без SKIP LOCKED** — два релея доставят дважды; забрал → пометил в той же транзакции.
3. **Дубли при повторной доставке** — без UNIQUE/ON CONFLICT; идемпотентность приема обязательна.
4. **Наблюдаешь pending без алерта** — релей упал, очередь растёт; мониторинг (модуль 13).
5. **Payload не JSON** — усложняет разбор и версионирование; jsonb + схема версии.

## Мини-задание

Добавь в outbox поле `delivered_at`; сделай релей, который при «доставке» заполняет его, а в конце удаляет доставленные старше суток.

<details>
<summary>Ответ</summary>

`ALTER TABLE outbox ADD COLUMN delivered_at timestamptz;` — релей при доставке `UPDATE SET status='delivered', delivered_at=now()`; отдельной задачей `DELETE FROM outbox WHERE status='delivered' AND delivered_at < now() - interval '1 day';`
</details>

## Как это спросят на собеседовании

1. «Зачем outbox?» — атомарность «данные + событие» без двухфазных транзакций.
2. «Как не потерять событие при падении релея?» — pending остаётся, повторная доставка идемпотентна.
3. «Чем релей отличается от воркера очереди?» — тот же SKIP LOCKED-механизм, цель — доставка наружу.
