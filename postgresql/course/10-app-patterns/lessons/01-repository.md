# Урок 01: Repository-паттерн и границы транзакций

**Модуль / кейс:** 10-app-patterns / кейс 1 (каталог), 10 (эволюция схемы)
**Время:** 2 ч

## Зачем это нужно

SQL не должен «размазываться» по бизнес-коду: repository собирает запросы в одном месте и даёт чистый интерфейс. А рядом — границы транзакций: одна бизнес-операция = одна транзакция (модуль 06), иначе в базе появляются «полуоперации».

## Ключевые идеи (сжато)

- `struct Repository { pool }` + методы (найти/создать/обновить) — единственное место, где живут SQL-запросы.
- Границы: транзакция открывается на бизнес-операцию («линия + устройства»), а не на один INSERT.
- Компонуемый транзакционный метод: `pool.begin()` → операции над `&mut *tx` → `commit()`; ошибка в середине откатывает всё.
- Вне транзакций по умолчанию каждый запрос — неявная транзакция; для ReadReplica-паттернов читатели — без транзакции.

## Разбор на примере

```bash
cargo run --example 01-repository
```

Код — `examples/01-repository.rs`. Транзакционный метод:

```rust
async fn create_line_with_devices(&self, name, description, devices: &[(&str,&str)]) -> Result<()> {
    let mut tx = self.pool.begin().await?;
    let line_id: i32 = sqlx::query_scalar("INSERT INTO equipment_lines (name, description) VALUES ($1,$2) RETURNING id")
        .bind(name).bind(description).fetch_one(&mut *tx).await?;
    for (device_type, tag) in devices {
        sqlx::query("INSERT INTO devices (line_id, device_type, tag) VALUES ($1,$2,$3)")
            .bind(line_id).bind(device_type).bind(tag).execute(&mut *tx).await?;
    }
    tx.commit().await?;
    Ok(())
}
```

Фактический вывод (стенд):

```
ЛИНИЯ-R1: создана вместе с устройством
ЛИНИЯ-R2: ошибка (… violates check constraint …) — строка откатилась целиком
проверка: ЛИНИЯ-R2 существует = false (ждём false)
```

## Как это устроено под капотом

- `tx` держит соединение; все операции идут по одному соединению в одной транзакции — атомарность, изоляция от конкурентов.
- Учти: из repository дёргают И отдельные методы (свой неявный COMMIT), И транзакционные — нельзя случайно коммитить внутри «чужой» транзакции (см. модуль 06 про границы).
- В большие системы добавляют unit-of-work; в курсе достаточно «метод = операция».

## Типичные ошибки и грабли

1. **SQL по бизнес-слою** — правки размазаны; repository собирает их в одном файле.
2. **Транзакция на «каждый INSERT»** — составные операции теряют атомарность.
3. **Коммит внутри транзакционного метода, вызванного из другой транзакции** — не делай «вложенные коммиты» без явной передачи tx (модуль 06/10).
4. **Ошибку проглатываем, а куски остались** — упал запрос → rollback; иначе статус «полуготово».

## Мини-задание

Добавь в repository метод `update_model(tag, model)` (одиночный, без транзакции) и транзакционный `reassign_devices(line_name, new_line_name)` — перенос устройств между линиями целиком.

<details>
<summary>Ответ</summary>

`update_model` — простой UPDATE; `reassign_devices` — BEGIN, UPDATE devices SET line_id = (SELECT id FROM lines WHERE name=$2) WHERE line_id = (…$1…), COMMIT. Все операции на `&mut *tx`.
</details>

## Как это спросят на собеседовании

1. «Зачем repository?» — единая точка запросов, тестируемость, смена хранилища.
2. «Где граница транзакции?» — бизнес-операция целиком.
3. «Как передать транзакцию между сервисами/репозиториями?» — явно (Executor/&mut Transaction), не через глобальный state.
