# Урок 02: Уровни изоляции и MVCC

**Кейсы:** 5 (согласованные отчёты)
**Время:** 1.5 ч

## Зачем это нужно

«Почему я не вижу свежие данные?» и «почему отчёт скачет между запусками?» — обе проблемы из изоляции. Понимание read committed vs repeatable read нужно и при чтении отчётов, и при проектировании ETL, и на собеседовании. Это также фундамент для Rust: какой уровень выставить в пуле (модуль 06).

## Ключевые идеи (сжато)

- MVCC: каждая строка — несколько версий; транзакция видит «снимок».
- **Read committed** (по умолчанию): снимок на каждый оператор — «новые» чужие коммиты видны в следующих запросах той же транзакции.
- **Repeatable read**: снимок на всю транзакцию — все запросы видят один срез; чужие коммиты после BEGIN не видны.
- Незакоммиченные изменения других сессий невидимы на любом уровне (нет dirty read).

## Разбор на примере (ДВА терминала)

Запуск: `examples/02-mvcc-sessions.sql` (сессия A и сессия B). Стенд курса; допустим `measurements` с сидом.

**Терминал A:**
```sql
BEGIN;
UPDATE measurements SET value = value + 1 WHERE id = 1;   -- не коммитим!
\! sleep 4                                                 -- держим транзакцию
COMMIT;
```

**Терминал B (пока A не закоммитила):**
```sql
SELECT value FROM measurements WHERE id = 1;
```
Реальный вывод на стенде автора (сессия B):
```
 1000.000000      <- НЕ видит изменение A: A не закоммитила
```
Через пару секунд (A закоммитила) — тот же запрос в новой сессии:
```
 1001.000000      <- стало видно (read committed: следующий оператор = новый снимок)
```

**Разница уровней на одном примере.** Таблица из одной строки; B вставляет вторую строку и коммитит:

Сессия A (repeatable read, держит снимок):
```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM iso_demo;     -- 1
-- ... B коммитит вторую строку ...
SELECT count(*) FROM iso_demo;     -- всё ещё 1 (снимок на всю транзакцию)
ROLLBACK;
```
Сессия C (read committed):
```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT count(*) FROM iso_demo;     -- 2 (после коммита B — новый снимок виден)
ROLLBACK;
```

Реальные выводы на стенде автора: A видит `1` и после коммита B `1`; C видит `2`.

## Как это устроено под капотом

- Снимок = видимое множество версий на момент взятия. Read committed берёт снимок на каждый оператор; repeatable read — один на транзакцию (потому и «повторяемое чтение»).
- Старые версии строк не удаляются при записи: их убирает VACUUM (урок 03). Пока есть снимок, «живые для него» версии удалить нельзя — отсюда «долгая транзакция блокирует VACUUM».
- Аномалии: dirty read исключён на всех уровнях; non-repeatable/phantom — исключены на repeatable read; serializable добавляет защиту от аномалий последовательности (с возможными `could not serialize`).

## Типичные ошибки и грабли

1. **Портят данные в read committed, ожидая «повторяемости»** — снимок на оператор: второй SELECT видит чужие коммиты. Нужен repeatable read.
2. **Долгая транзакция repeatable read на проде** — висит часами → VACUUM не может чистить → bloat (урок 03, лаба).
3. **«Почему не вижу своих вставок?»** — свои изменения всегда видны своей транзакции; чужие незакоммиченные — никогда.
4. **Путаница `SET TRANSACTION ISOLATION LEVEL` vs `BEGIN ISOLATION LEVEL`** — обе работают, но `BEGIN ISOLATION LEVEL ...` короче и нагляднее.

## Мини-задание

Объясни словами: почему отчёт «количество замеров за сутки», запущенный дважды подряд в одной транзакции read committed, может дать разные числа, а в repeatable read — одинаковые.

<details>
<summary>Ответ</summary>

В read committed каждый SELECT берёт свой снимок: если между запросами пришли новые замеры и закоммитились — второй запрос их увидит. В repeatable read снимок один на транзакцию: оба SELECT видят одно и то же множество.
</details>
