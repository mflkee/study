# Теория модуля 03: транзакции и MVCC

Конспект-справочник. Развёрнутые примеры с реальными выводами двухсессионных прогонов — в уроках.

## ACID

- **Atomicity** — транзакция выполняется целиком или не выполняется вовсе; частичный результат откатывается.
- **Consistency** — данные из корректного состояния переходят в корректное (ограничения выполняются после COMMIT).
- **Isolation** — параллельные транзакции не видят промежуточные состояния друг друга (см. уровни изоляции).
- **Durability** — закоммиченное переживает сбой (WAL; модуль 07/13).
- PostgreSQL: `BEGIN` … `COMMIT` / `ROLLBACK`; **savepoint** — точка отката внутри транзакции (`SAVEPOINT sp`, `ROLLBACK TO sp`), вся транзакция при этом жива.

## MVCC (версионирование строк)

- Каждая строка хранит версии (минимально: начало/конец видимости). Транзакция видит «снимок» — мгновенный срез версий на момент своего снимка.
- Незакоммиченные изменения других транзакций **невидимы**. DELETE/UPDATE не стирают старые версии мгновенно — они остаются до VACUUM.
- Следствие: читатели не блокируют писателей, писатели не блокируют читателей (в отличие от классических блокировочных СУБД).

## Уровни изоляции (PostgreSQL)

| Уровень | Снимок | Типичные аномалии, которых нет | Цена |
|---|---|---|---|
| read committed (по умолчанию) | на каждый оператор | dirty read (чтение чужого незакоммиченного) | — |
| repeatable read | на всю транзакцию | + non-repeatable read, phantom read | долгие транзакции могут мешать VACUUM |
| serializable | на всю транзакцию, с отслеживанием конфликтов | + serialization anomaly | может падать с «could not serialize» |

Практика СИКН: чтения отчётов — read committed; согласованные выгрузки («весь день одним срезом») — repeatable read; деньги/аудит с сильными инвариантами — serializable (и retry в коде).

## Блокировки

- Строковые: `FOR UPDATE` (запись), `FOR SHARE` (чтение с защитой). Ожидание — блокировка до COMMIT/ROLLBACK держателя.
- Табличные: `LOCK TABLE ... IN EXCLUSIVE MODE` и др. (DDL-зависимости).
- **Deadlock**: A ждёт B, B ждёт A; PostgreSQL через deadlock_timeout (по умолчанию 1 с) обнаруживает и **откатывает одну** транзакцию с `ERROR: deadlock detected`.
- **VACUUM и bloat**: старые версии строк убирает VACUUM; **снимок repeatable read (или открытый курсор) не даёт удалить «живые для него» версии** — VACUUM показывает `N are dead but not yet removable`. Долгая транзакция = растущий bloat.
- **Advisory locks** — прикладные блокировки: `pg_try_advisory_lock(key)` / `pg_advisory_unlock(key)`; можно для семантики «один процесс на задачу».

## Очередь задач: FOR UPDATE SKIP LOCKED

```sql
WITH claimed AS (
    SELECT id FROM tasks
    WHERE status = 'pending'
    ORDER BY id
    FOR UPDATE SKIP LOCKED   -- пропустить строки, залоченные другими
    LIMIT 2
)
UPDATE tasks SET status = 'processing'
WHERE id IN (SELECT id FROM claimed) RETURNING id;
```

- Параллельные воркеры берут РАЗНЫЕ задачи и **не блокируются**.
- Обычный `FOR UPDATE` (без SKIP LOCKED) — блокируется, пока держатель не закоммитит.
- Ядро очереди задач: захват → обработка → статус; ретраи/dead-letter — модуль 10 (и Rust-воркеры — тоже там).

## Диагностика

- `pg_locks` — кто что блокирует; `pg_stat_activity` — активные транзакции (`state`, `xact_start`).
- `pg_stat_user_tables.n_dead_tup` — потенциальный bloat (сброс может врать — проверяй `VACUUM VERBOSE`).
- `VACUUM VERBOSE table` — сколько версий удалено / «dead but not yet removable».
