# Лаба 01: Партиция без индекса / Ретеншн удалил нужное — сломай и почини

**Кейс:** 5 (отчёты), 12 (инциденты)
**Модуль:** 08-timeseries-partitioning
**Время:** 1.5 ч
**Тип:** диагностируй по симптомам

## Цель

Два инцидента эксплуатации временных рядов:

1. **Партиция без индекса** — партиционирование ускоряет *pruning* (читаем только партицию), но НЕ даёт индекс: точечный запрос снова сканирует всю партицию. Найти и починить.
2. **Ретеншн удалил нужное** — ретеншн-скрипт дропнул партицию, а запоздалые данные с буфера шлюза (кейс 8, модуль 10) ещё «в пути»: `INSERT` в старый диапазон теперь падает, данные теряются. Воспроизвести и починить.

## Схема стенда

База `course_m06` (15432), таблицы модуля 08 (`00-setup-partitions.sql` уже применён — 1 М строк). Работа в psql.

## Часть A. Партиция без индекса

1. Запрос «показания устройства 3 за час»:

   ```sql
   EXPLAIN (ANALYZE, BUFFERS)
   SELECT count(*) FROM measurements_part
    WHERE device_id = 3 AND ts >= '2026-09-21 12:00:00+00' AND ts < '2026-09-21 13:00:00+00';
   ```

   До индекса — `Seq Scan` по партиции (вся партиция!). **Pruning сработал (одна партиция), индекс не сработал.**

2. Добавь B-tree `(device_id, ts)` (как в примере 01) и повтори EXPLAIN: `Bitmap Index Scan` / `Index Only Scan`, время и `Buffers` падают.

3. Верни исходное (DROP INDEX), запиши вывод «партиция ≠ индекс».

## Часть B. Ретеншн удалил нужное

1. Подготовь «историю» с месячными партициями (пример 02 — это уже сделано, но собери свою на `hist`):

   ```sql
   DROP TABLE IF EXISTS hist CASCADE;
   CREATE TABLE hist (id bigint, ts timestamptz, value numeric(12,4)) PARTITION BY RANGE (ts);
   CREATE TABLE hist_2026_08 PARTITION OF hist FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
   CREATE TABLE hist_2026_09 PARTITION OF hist FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
   INSERT INTO hist SELECT i, '2026-08-01'::timestamptz + ((i % 59) || ' days')::interval, i
     FROM generate_series(1, 10000) i;
   ```

2. «Ретеншн 30 дней» (плохой, по имени): дропни партицию августа:

   ```sql
   DROP TABLE hist_2026_08;
   ```

3. А теперь пришли «запоздалые» данные за 15 августа (буфер шлюза доставил после ретеншна):

   ```sql
   INSERT INTO hist VALUES (999999, '2026-08-15 10:00:00+00', 1.0);
   ```

   Ждём **ошибку**: `no partition of relation "hist" found for row` — данные шлюза теряются, и это НЕ тихий отказ: приложение падает.

4. **Починка** — «ретро-партиция» (создаём заново для старых границ, данные примутся) или «не дропать, пока окно доставки не закрыто»:

   ```sql
   CREATE TABLE hist_2026_08 PARTITION OF hist FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
   INSERT INTO hist VALUES (999999, '2026-08-15 10:00:00+00', 1.0);   -- теперь вставляется
   ```

5. **Безопасный ретеншн** — с проверкой «партиция гарантированно пуста/окончена»:

   ```sql
   -- дропаем только партиции, целиком старше порога (max(ts) + запас на доставку)
   DO $$
   DECLARE p text;
   BEGIN
     FOR p IN
       SELECT c.relname FROM pg_inherits i
         JOIN pg_class c ON c.oid = i.inhrelid
        WHERE i.inhparent = 'hist'::regclass
     LOOP
       EXECUTE format('DROP TABLE %I', p);   -- здесь только иллюстрация шаблона;
                                              -- в проде: проверка диапазона партиции
     END LOOP;
   END $$;
   ```

   Правило: ретеншн по **границам партиции** (макс. диапазон партиции < now() − окно задержки доставки), а не по «примерному возрасту».

## Критерии успеха

- [ ] Часть A: увидел `Seq Scan` по одной партиции (pruning есть, индекса нет), после индекса — `Index Scan` с меньшими `Buffers`/временем
- [ ] Часть B: воспроизвёл «no partition of relation found for row» (шлюз не может доставить запоздалые данные)
- [ ] Починил ретро-партицией или изменил условие ретеншна так, чтобы окно доставки не пересекалось с дропом
- [ ] Написал безопасный шаблон ретеншна (по границам партиции) в свои заметки

## Разбор типичных проблем

| Симптом | Причина | Решение |
|---|---|---|
| «партиции много, а всё равно медленно» | pruning работает, индекса в партиции нет | добавь индекс per-partition (`ON measurements_part (device_id, ts)`) |
| индексы «в партициях» не видны в размерах | индексы создаются отдельно на каждой партиции | смотри `pg_index` по `pg_inherits`, не по мастер-таблице |
| «no partition found for row» | ретеншн дропнул диапазон, в который ещё может прийти доставка | ретро-партиция или ретеншн с запасом (окно доставки) |
| `DROP TABLE` партиции «не сработал» | партиция привязана к мастер-таблице; обычный DROP валиден только для партиции | `DROP TABLE имя_партиции` — корректный способ удалить партицию с данными |
| данные «потерялись молча» | ретеншн «по имени» + не проверены границы | проверять диапазон перед DROP (`to_regrange`/`pg_partition_range`) + алертинг (модуль 13) |

## Задания «со звёздочкой»

1. **DETACH вместо DROP**: `ALTER TABLE hist DETACH PARTITION hist_2026_08;` — данные сохраняются как обычная таблица (бэкап/архив перед ретеншном).
2. **Автопартицинг**: напиши функцию, которая при INSERT создаёт недостающие партиции (или `pg_partman` — краткий разбор).
3. **BRIN вместо B-tree** на партиции: сравни размеры и планы для диапазонных запросов (помни: на честных данных планировщик решает сам — пример 01).
