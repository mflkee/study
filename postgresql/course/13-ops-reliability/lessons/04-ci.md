# Урок 04: Docker и базовый CI

**Модуль / кейс:** 13-ops-reliability / кейс 12 (инциденты — повторяемость)
**Время:** 2 ч

## Зачем это нужно

Стенд курса — сам по себе CI-артефакт: `docker compose` поднимает всё одной командой. CI превращает «у меня работает» в «проверено на эталоне»: каждый push гоняет тесты модуля 12 против контейнера PostgreSQL.

## Ключевые идеи (сжато)

- Docker-обёртки: `docker compose` для стенда (profiles base/tools/obs/timescale), контейнеры изолированы, порты нестандартные.
- CI-пайплайн (пример ниже): checkout → setup Rust → тесты (`cargo test --tests` — модуль 12 сам поднимает контейнеры!) → docker compose config.
- Запускать `cargo test` уже не требует общего стенда: testcontainers поднимает свой PG.
- Секреты — env-переменные CI-раннера, не в репозитории.

## Разбор на примере

Файл-шаблон (в репозитории курса — `.github/workflows/ci.yml`):

```yaml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions-rust-lang/setup-rust-toolchain@v1
      - name: testcontainers (нужен Docker)
        run: docker info
      - name: cargo test (модуль 12 — сам поднимает PG)
        working-directory: course/12-testing
        run: cargo test --tests
      - name: compose config
        run: docker compose -f infra/docker-compose.yml config --quiet
```

Факт со стенда курса: `docker compose config` (все profiles) — код 0; `cargo test --test pg_integration` — 2 зелёных (контейнер изолирован).

## Как это устроено под капотом

- CI-раннер (GitHub Actions ubuntu-latest) имеет Docker — testcontainers поднимает PG прям при тесте; никакого общего стенда.
- Rust-тесты собираются в свежем окружении: `cargo test` скачает зависимости (или кэш), применят миграции модуля 12 на контейнер — полностью воспроизводимо.
- `docker compose config` валидирует compose без поднятия (дешёвый gate).
- Шаги с таймаутом: тесты с testcontainers на CI могут быть медленными (первый pull образа) — вынести pull в отдельный шаг.

## Типичные ошибки и грабли

1. **CI без Docker** — testcontainers не стартует; на ubuntu-latest Docker доступен, на ранних раннерах — проверить.
2. **Общий стенд в тестах** — CI в параллели ломается; правильный путь — контейнер на тест (модуль 12).
3. **Забыл `docker compose config`** — опечатка в compose обнаружена только при up.
4. **Секреты в коде** — токены/пароли только через CI env (не коммитить).
5. **Версии в Cargo.toml** — зафиксируй (в курсе все версии в PLAN.md); иначе CI «сломается через месяц».

## Мини-задание

Скопируй шаблон ci.yml в свой проект (или в курс), запусти `docker compose config` в CI вручную локальной командой — убедись, что код 0.

<details>
<summary>Ответ</summary>

`docker compose -f infra/docker-compose.yml config --quiet && echo OK` — завершается с 0; это дешёвый gate на каждые пуши.
</details>

## Как это спросят на собеседовании

1. «Что даёт CI для БД-проектов?» — повторяемость: тесты на чистом контейнере, а не «на моей машине».
2. «Как тестировать с БД в CI?» — testcontainers поднимает контейнер; не полагаться на общий стенд.
3. «Куда класть секреты?» — secrets CI/env, не в git.
