# Урок 01: Бэкап, WAL и восстановление (pg_dump, pg_basebackup, PITR)

**Модуль / кейс:** 13-ops-reliability / кейс 12 (инциденты)
**Время:** 2.5 ч

## Зачем это нужно

Бэкап — не «файл в папке», а **воспроизводимое восстановление**. Курс ставит практику: дамп → восстановить в пробную базу и сверить строки; физический снимок → поднять из него сервер; WAL-архив → последний рубеж.

## Ключевые идеи (сжато)

- **Логический** (`pg_dump -Fc`) — данные/схема в одном файле; restore в любую версию; точечная выгрузка.
- **Физический** (`pg_basebackup -Fp`) — файловый снимок + WAL; основа реплики и PITR.
- **WAL-архив** (`archive_mode=on`, `archive_command`) — каждый запечатанный сегмент копируется; без него PITR невозможен.
- **PITR**: восстановить физический снимок + докатать WAL до `recovery_target_time` (UNVERIFIED-нюанс docker — см. лабу).
- RPO/RTO: RPO — сколько данных можно потерять (до точки бэкапа/архива); RTO — сколько времени подниматься.

## Разбор на примере

```bash
bash course/13-ops-reliability/examples/01-pgdump-restore.sh   # dump + restore + сверка
bash course/13-ops-reliability/examples/02-pgbasebackup.sh      # физический снимок
bash course/13-ops-reliability/examples/03-pitr-restore.sh      # восстановление из снимка
```

Фактический результат на стенде:

```
01: alarms источник=100 restore=100   # сверка после restore в пробную базу
02: 296M  basebackup_… (без recovery.signal)
03: alarms_rows=100                   # сервер поднят из снимка, данные на месте
```

Стенд курса поднят с `archive_mode=on` и `archive_command='cp %p /archive/%f'` (compose): WAL-сегменты копятся в томе `pg-course_wal_archive`.

## Как это устроено под капотом

- `pg_dump -Fc` — поток в custom-формат (сжатие, параллельный restore); идемпотентен к версиям.
- `pg_basebackup` — копия файлов данных в согласованном состоянии (backup_label + стартовый WAL), **не мешает работе** сервера.
- WAL снимается по сегментам (по умолчанию 16 МБ) при их заполнении/переключении; архивная каталогизация — источник для восстановления «на момент».
- Клиентский restore: `pg_restore` в чистую БД; физический: замена PGDATA + recovery (backup_label) с опциональным `recovery_target_time`.

## Типичные ошибки и грабли

1. **Бэкап без проверки восстановления** — файл есть, а не восстанавливается; всегда сверяй count.
2. **`archive_command` молча ломается** — pg_wal растёт, диск забит (лаба A); следи за логами cp.
3. **Физический бэкап «не туда»** — `pg_basebackup -D` внутрь PGDATA (катастрофа); бери рядом с PGDATA.
4. **Права/тома в docker** — `pg_dump` пишет в поток на хост, а не внутрь контейнера (пример 01 делает так).
5. **PITR в docker руками** — капризен (восстановление читает конфиг PGDATA, права, timeline); на классическом стенде — стабильно (пометка UNVERIFIED в лабе).

## Мини-задание

Запусти `examples/01-pgdump-restore.sh`, зафиксируй своё время дампа и restore (RTO); напиши вслух свой RPO при ежесуточном симповида восстановления.

<details>
<summary>Ответ</summary>

RPO ≈ время последнего pg_dump/инкремента; RTO ≈ длительность pg_restore/поднятия из basebackup. Цифры зависят от объёма — «время восстановления = бюджет инцидента».
</details>

## Как это спросят на собеседовании

1. «Что выберешь: логический или физический бэкап?» — оба: логический для данных/точек, физический для полного восстановления и реплики.
2. «Что такое WAL-архив и зачем?» — копия сегментов WAL вне сервера — материал для PITR.
3. «RPO/RTO — это что?» — потери данных и время восстановления; определяют частоту бэкапов.
