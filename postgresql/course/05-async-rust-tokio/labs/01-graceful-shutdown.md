# Лаба 01: Грациозный останов воркера

**Кейс:** 7 (очередь задач — задел), 12 (инциденты — «не потеряй при рестарте»)
**Модуль:** 05-async-rust-tokio
**Время:** 1 ч
**Тип:** реши сам (сигналы, дренаж)

## Цель

Собрать воркера, который:

1. непрерывно берёт задачи из канала и «обрабатывает» их (модель записи в БД, 50 мс/задача);
2. по **SIGINT** (`Ctrl-C`) и **SIGTERM** останавливается **грациозно**: прекращает приём нового, дообрабатывает уже взятые (дренаж), выводит отчёт и завершается с кодом 0;
3. повторный сигнал в течение 2 секунд — принудительный выход (не вечный дренаж).

Это заготовка воркеров модуля 10 (там очередь будет жить в PostgreSQL, а не в канале).

## Схема стенда

- Стенд не нужен: работает локально (`cargo run`).
- За основу возьми `examples/05-pipeline.rs` (референс) — но допиши своё.

## Шаги

1. **Каркас**: создай `examples/08-worker.rs`? Нет — проще: скопируй `examples/05-pipeline.rs` в `examples/08-worker.rs` и переделай:
   - полезная нагрузка — целые `u64` (номера задач);
   - «обработка» — `sleep(50 мс)` + счётчик;
   - обработка и SIGINT, и SIGTERM: `tokio::signal::unix::signal(SignalKind::terminate())` + `interrupt()`.
2. **Один сигнал**: объедини оба источника сигналов через `select!` (future обоих держи `tokio::pin!`, по граблям урока 03).
3. **Повторный сигнал**: после первого сигнала запусти таймер 2 секунды; если второй сигнал пришёл раньше таймера — `std::process::exit(130)` (принудительно). Если таймер победил — дренаж завершился, вывод и выход 0.
4. Проверь:
   ```bash
   cargo run --example 08-worker                # жми Ctrl-C
   timeout -s INT 3 cargo run --example 08-worker   # автопроверка SIGINT
   timeout -s TERM 3 cargo run --example 08-worker   # автопроверка SIGTERM
   ```

## Ожидаемое поведение (эталон, снят автором на `03-otmena-graceful`)

```
  обработано 37
SIGINT пойман: останавливаем производителя и дренируем очередь…
  производитель остановлен (стоп-сигнал)
итог: обработано 38 значений; очередь пуста, выходим с кодом 0
```

Отличие твоего воркера: должен работать и с SIGTERM, и принудительно завершаться повторным сигналом.

## Критерии успеха

- [ ] Воркер обрабатывает задачи непрерывно (видно по выводу)
- [ ] По SIGINT и SIGTERM: остановлен приём → дренаж → `итог` → код выхода 0
- [ ] Второй сигнал в течение дренажа — принудительный выход (код 130)
- [ ] В коде сигнальные future держатся через `tokio::pin!` (не пересоздаются в цикле)
- [ ] `cargo clippy` и `cargo fmt --check` чисты

## Разбор типичных проблем

| Симптом | Причина | Решение |
|---|---|---|
| SIGINT не ловится вообще | `ctrl_c()` пересоздаётся в цикле (сигнал теряется в окне) | `pin!` + `&mut` — одно future на программу |
| после первого сигнала воркер «висит» | производитель не остановлен, канал не закрывается, дренаж ждёт вечно | стоп-сигнал производителю (`watch`) |
| дренаж бесконечный | обработка задачи вечная или канал не закрыт | таймаут дренажа (повторный сигнал → exit) |
| SIGTERM не ловится | слушаешь только `interrupt()` | `signal(SignalKind::terminate())` тоже в select! |
| `select!` «забывает» про сигнал | ветка recv готова всегда | `biased;` + сигнальную ветку первой |

## Задания «со звёздочкой»

1. **Таймаут дренажа**: вместо повторного сигнала — `timeout(2s)` на цикл дренажа (`tokio::time::timeout`), при истечении — принудительный выход.
2. **`tokio-util::sync::CancellationToken`**: перепиши остановку на cancellation-token (добавь зависимость `tokio-util`), сравни с watch-подходом.
3. **Замер «потеряно/обработано»**: добавь в отчёт, сколько задач было в канале в момент сигнала (`rx.len()` до дренажа) и сколько обработано после — покажи, что потерь нет.
