# Теория модуля 05: асинхронность (async/await, tokio)

Конспект-справочник. Развёрнутые примеры с фактическими выводами — в уроках (`lessons/`).

## async/await и Future

- `async fn` — функция, возвращающая `Future`; тело выполняется только при `.await` (или `poll` рантаймом).
- `.await` — отдаём управление рантайму, пока операция не готова (не блокируем поток).
- **Кооперативная многозадачность**: одна задача уступает поток через `.await`; если задача не делает `.await` — она «держит» поток (долгий CPU-цикл внутри async — плохо).
- Конкурентность ≠ параллелизм: `tokio::join!` выполняет две задачи на ОДНОМ потоке вперемежку.
- Блокирующие вызовы (`std::thread::sleep`, синхронный IO) внутри async — останавливают поток рантайма; для них — `tokio::task::spawn_blocking`.

## Задачи и каналы

- `tokio::task::spawn` — отдельная задача на рантайме; `JoinHandle::await` ждёт её завершения (вернёт `Result`, поймает панику).
- **mpsc** (multi-producer, single-consumer): `tokio::sync::mpsc::channel(N)` — bounded буфер; `send().await` ждёт место (backpressure), `recv()` → `Option<T>` (None, когда все senders упали — удобный признак завершения).
- `unbounded_channel()` — без ограничений; опасно при быстром производителе (память).
- **`select!`** — ждать ПЕРВОЕ готовое событие из нескольких веток. Если постоянно готова одна ветка, редкая может «не выигрывать» — тогда `biased;` (проверка веток по порядку) и/или держать редко меняющийся future живым.

## Отмена и грациозный останов

- `tokio::signal::ctrl_c()` — future, готовая по SIGINT; её надо держать ОДНОЙ на программу (`tokio::pin!` + `&mut` в select!) — пересоздание в цикле теряет сигнал в окне между drop и регистрацией.
- Стоп-сигнал производителю — `tokio::sync::watch<bool>`: `sender.send(true)` → у получателя `changed()` готова.
- **Дренаж**: после остановки принимать оставшееся из канала (`while let Some(...) = rx.recv().await`) — ничего не теряется.
- Паттерн: сигнал → stop производителю → выход из select → дренаж → `producer.await` → итог → код 0.

## Backpressure

- Bounded-канал `channel(N)` — производитель ждёт, когда потребитель освободит место: очередь не растёт, память ограничена, ничего не теряется.
- Альтернативы при переполнении: `try_send` (не ждать) с политикой drop-new/drop-oldest (свежесть важнее полноты — для телеметрии это осознанное решение).
- Плохой вариант — `unbounded_channel` под нагрузкой: рост памяти до OOM.

## Как это ложится на БД-слой (мост к модулю 06)

- Пул sqlx — асинхронный: каждый запрос — future; конкурентные запросы не блокируют потоки.
- Каналы — каркас очередей задач (модули 07/10: воркеры, SKIP LOCKED, ретраи).
- Грациозный останов — как корректно завершать воркеров, чтобы не потерять незакоммиченные данные при рестарте.
- `biased;` и удержание future — практика надёжных select-циклов в долгоживущих процессах.
