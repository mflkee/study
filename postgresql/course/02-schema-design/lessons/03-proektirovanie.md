# Урок 03: Проектирование схемы под телеметрию

**Кейсы:** 1 (каталог), 3 (точность), 5 (отчёты)
**Время:** 1.5 ч

## Зачем это нужно

Схема под поток измерений отличается от схемы под операционный учёт: телеметрия append-only, пишется непрерывно, читается «по времени» и «по устройству». Типовое решение «как в трейдинге» здесь ломается: если не заложить форму запросов в индексы и не решить ретеншн — таблица растёт, запросы деградируют, база «встаёт» ночью во время бэкапа.

## Ключевые идеи (сжато)

- Поток измерений — **append-only**: пишем, редко правим; ретеншн — удаление старых блоков.
- Ключевые запросы определяют индексы **до** массовой заливки: «по устройству + по времени» → `(device_id, ts)`; «по времени» → BRIN на ts.
- Точность и время — `numeric` и `timestamptz` (модуль 01): это не косметика, а требование аудита.
- Справочники отдельно от фактов: в потоке — FK, не повторяющиеся строки (модуль 02, урок 01).
- Ретеншн/партиционирование — инженерное решение до того, как таблица стала гигантской (глубоко — модуль 08).

## Разбор на примере

Схема `measurements` из модуля 01 уже реализует эти принципы; разберём почему она такая:

```sql
CREATE TABLE measurements (
    id        bigserial PRIMARY KEY,          -- поток: bigserial, не serial (объёмы большие)
    device_id int  NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    ts        timestamptz NOT NULL,           -- момент, не «стенное» время
    value     numeric(20,6) NOT NULL,         -- точность под метрологию
    quality   int NOT NULL DEFAULT 0 CHECK (quality BETWEEN 0 AND 3)
);

CREATE INDEX idx_measurements_device_ts ON measurements (device_id, ts);
```

**Почему так:**

- `(device_id, ts)` — композитный B-tree под типовой запрос «значения устройства за период»; при `WHERE device_id = ... AND ts BETWEEN ...` индекс отсекает и устройство, и время (модуль 02, урок 02).
- `bigserial` — поток не ограничен 2 млрд строк.
- `timestamptz` + `numeric` — аудит и метрология (модуль 01, урок 03).
- FK `ON DELETE CASCADE` — удаление устройства чистит его измерения (аккуратно: удаление линии каскадом сносит много данных).

**Что здесь НЕ решено и почему (темы следующих модулей):**

| Вопрос | Ответ в курсе |
|---|---|
| Таблица растёт бесконечно | ретеншн + партиционирование — модуль 08 |
| Запрос «все значения за сутки всех устройств» | BRIN по ts — модуль 02 (урок 02), модуль 08 |
| Скорость массовой записи (500 мс опрос × N устройств) | batch/COPY — модуль 07 |
| Качество данных на входе | quality-флаги, partial-индекс — этот урок (мини-задание) |

**Правило «сначала запросы»:** перед созданием таблицы выпиши 3–5 запросов, которые будут работать постоянно (не аналитика раз в месяц). Для каждого — колонки в WHERE и желаемый индекс. Схема каталога выросла именно так: «последние значения по устройствам» → `(device_id, ts)`.

## Как это устроено под капотом

- Планировщик принимает решение по индексам и статистике: чем точнее статистика (ANALYZE), тем лучше оценки rows и выбор способа сканирования.
- Потоковые вставки пишут в WAL и кучи; каждый дополнительный индекс = дополнительная запись при INSERT (вот почему «индексов должно быть ровно столько, сколько нужно реальным запросам»).
- Ночной ретеншн (DELETE старых строк) генерирует bloat и тормозит VACUUM — поэтому для больших потоков ответ — партиционирование (модуль 08), а не DELETE.

## Типичные ошибки и грабли

1. **Схема «сделал и забыл»** — через год таблица без нужного индекса, а ранний запрос «встал»; индексы эволюционируют вместе с запросами.
2. **serial под телеметрию** — переполнение через годы; сразу bigserial/IDENTITY.
3. **Справочники в потоке** — повторы тегов/моделей в измерениях (урок 01): дороже и в диске, и в правках.
4. **Нет плана ретеншна** — «когда-нибудь почистим»; чистится, когда диск кончился.
5. **Индексы СРАЗУ до заливки** — первичная загрузка данных идёт быстро без индексов: сначала COPY, потом CREATE INDEX (модуль 07 покажет замеры).

Опиши одним абзацем схему таблицы «события оператора» (кто, когда, что сделал с устройством) для аудита СИКН: перечисли колонки, ключи, какой индекс дашь и почему.

<details>
<summary>Ответ (вариант)</summary>

Колонки: `id bigserial PK`, `device_id int NOT NULL REFERENCES devices(id)`, `ts timestamptz NOT NULL`, `operator text NOT NULL`, `action text NOT NULL`, `comment text`. Индекс `(device_id, ts)` — типовой запрос «история действий по устройству». `timestamptz`, а не timestamp — аудит должен держать момент.
