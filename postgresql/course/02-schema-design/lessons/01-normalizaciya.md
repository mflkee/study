# Урок 01: Нормализация, ключи и связи

**Кейсы:** 1 (каталог оборудования)
**Время:** 2 ч

## Зачем это нужно

Справочник оборудования и поток измерений — это классическая пара «справочники + факты». Если справочные данные (модель, линия, тип) размножить по каждой строке факта, каждая правка превращается в массовый UPDATE, а опечатка в одной строке незаметно разъезжается по отчётам. Нормализация — это способ сделать данные согласованными по построению, а не по дисциплине.

## Ключевые идеи (сжато)

- **1NF** — атомарные значения, без повторяющихся групп. **2NF** — неключевые поля зависят от всего PK. **3NF** — неключевое не зависит от неключевого.
- Для производственных схем достаточно разумной 3NF; денормализация — осознанное решение под производительность.
- **PK** — уникальная идентификация, **FK** — целостность ссылок, **UNIQUE** — бизнес-ключ (тег `M-01-001`).
- Симптом «плохой» схемы: одна и та же правка применяется в N строках; «плавающие» значения справочника.

## Разбор на примере

Запуск: `./infra/apply-db.sh course/02-schema-design/examples/01-normalizaciya.sql`.

**«Сырая» денормализованная таблица** — справочные поля в каждой строке события:

```sql
CREATE TEMP TABLE raw_events (
    line_name   text,  device_tag  text,  device_type text,
    model       text,  ts          timestamptz,  value numeric(20,6)
);
```

В данных — «опечатка модели»: у `D-02-001` в одной строке `MVD-2`, в другой `MVD-1`:

```sql
SELECT DISTINCT device_tag, model FROM raw_events ORDER BY device_tag;
```
```
 device_tag |  model
------------+---------
 D-02-001   | MVD-2
 D-02-001   | MVD-1      <-- та же сущность, разные значения
 M-01-001   | CMF-300
```

**Проблема:** правка модели = первый UPDATE по всем строкам; опечатка «зашилась» в одну строку и будет всплывать в отчётах. Причём попытка нормализовать через `SELECT DISTINCT ... model` падает на `UNIQUE(tag)` — дубли справочника пойманы ограничением ещё на загрузке (это фича, не баг).

**Нормализация:** справочники из DISTINCT (с дедупликацией через `min(model)` по бизнес-ключу), события ссылаются на `device_id`:

```sql
CREATE TEMP TABLE n_lines  AS SELECT DISTINCT line_name AS name FROM raw_events;
CREATE TEMP TABLE n_devices AS
    SELECT device_tag AS tag, device_type, min(model) AS model, l.id AS line_id
    FROM raw_events d JOIN n_lines l ON l.name = d.line_name
    GROUP BY device_tag, device_type, l.id;
CREATE TEMP TABLE n_events AS
    SELECT e.ts, e.value, dev.id AS device_id
    FROM raw_events e JOIN n_devices dev ON dev.tag = e.device_tag;
```

Теперь правка модели — **одна строка**, и её видно сразу:

```sql
UPDATE n_devices SET model = 'MVD-2' WHERE tag = 'D-02-001';
```
```
   tag    |  model
----------+---------
 D-02-001 | MVD-2
 M-01-001 | CMF-300
```

## Как это устроено под капотом

- `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE` создаёт индекс — PostgreSQL проверяет уникальность через поиск в нём.
- `REFERENCES` порождает FK-ограничение: каждая вставка проверяет существование родителя; выбор `ON DELETE` определяет поведение при удалении (в схеме каталога — `CASCADE`).
- `serial`/`bigserial` — это `integer` + последовательность (`nextval`), а не «автоинкремент» из других СУБД; в PG 18 чаще используют `GENERATED ... AS IDENTITY`.
- Нормализация не бесплатна: факты реплицируются через JOIN; для горячих путей (например, «тег прямо в измерении») иногда сознательно оставляют денормализованную колонку — но с аудитом и процедурой правки.

## Типичные ошибки и грабли

1. **SELECT DISTINCT «по всем полям» справочника** — дубли из-за опечаток не схлопываются; UNIQUE ловит, но падает загрузка. Дедупликация агрегатом (`min`) — честный способ.
2. **FK без выбора поведения ON DELETE** — удаление линии с устройствами запрещено по умолчанию (RESTRICT); если нужен каскад — `ON DELETE CASCADE`, но тогда удаление линии сносит и измерения — думай о последствиях.
3. **Уникальность «на БД», а не «в коде»** — проверки в приложении не защищают от конкурентных вставок; UNIQUE — единственная гарантия.
4. **Денормализация «пока»** — потом забыли, и справочник живёт в трёх таблицах. Денормализация обязана быть задокументированной и проверяемой.
5. **serial vs IDENTITY** — в новом коде используй `GENERATED ALWAYS AS IDENTITY`; `serial` — устаревший стиль.
