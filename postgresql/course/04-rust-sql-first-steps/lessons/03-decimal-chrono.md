# Урок 03: rust_decimal, chrono, serde — точность и сериализация

**Модуль / кейс:** 04-rust-sql-first-steps / кейс 3 (точность расчётов), кейс 1 (каталог)
**Время:** 2.5 ч

## Зачем это нужно

Масса, плотность, содержание воды — метрологические величины, терять точность нельзя. На `f64` «1000.1» не равно «1000.1» после операций: ошибка копится и в отчётах всплывают аномалии. В этом уроке: точная десятичная арифметика (`rust_decimal`), корректное время (`chrono`) и сериализация телеметрии в JSON (`serde`) — фундамент всех расчётов курса (модуль 12 добавит property-тесты).

## Ключевые идеи (сжато)

- **`f64` хранит число в двоичной мантиссе**: `0.1` ≈ `0.10000000000000000555…` — отсюда накопление ошибки. Для учётных расчётов — нельзя.
- **`rust_decimal::Decimal`** — десятичное число: 96-битная мантисса + масштаб (scale). Диапазон ~1e-28…1e28, «железная» точность десятичных дробей, любые знаки.
- **`chrono`**: `DateTime<Utc>` для `timestamptz`; сериализуется в ISO 8601 (`2026-09-23T00:00:00Z`).
- **`serde`**: структуры → JSON одной строкой; `Decimal` по умолчанию сериализуется **строкой** (не числом!) — значение не теряет точность.
- **Батчевая запись** — один запрос на тысячи строк через `UNNEST` (подробно в модуле 07).

## Разбор на примере

Запусти оба примера и сверь вывод:

```bash
cargo run --example 04-serde-telemetry   # телеметрия из PG → JSON
cargo run --example 05-batch-write       # 10 000 строк одним запросом
```

**1. Сериализация телеметрии** (`examples/04-serde-telemetry.rs`):

```rust
#[derive(Debug, sqlx::FromRow, Serialize)]
struct TelemetryPoint {
    tag: String,
    ts: DateTime<Utc>,
    value: Decimal,
    quality: i32,
}
```

Фактический вывод (фрагмент):

```json
[
  {
    "tag": "M-01-001",
    "ts": "2026-09-23T00:00:00Z",
    "value": "995.000000",
    "quality": 0
  },
  {
    "tag": "D-01-001",
    "ts": "2026-09-23T00:00:00Z",
    "value": "850.200000",
    "quality": 0
  }
]
```

Обрати внимание: `"value": "995.000000"` — **строка с исходной точностью**, а не `995.0`. По умолчанию `rust_decimal` сериализует в строку — именно поэтому JSON не «съедает» хвосты. Время — ISO 8601 с зоной `Z`, так REST-клиент (модуль 11) не перепутает часовой пояс.

**2. Точечная арифметика.** Сравни в консоли (или напиши юнит-тест):

```rust
let f = 1000.1_f64 - 1000.0_f64;            // 0.09999999999993179
let d = Decimal::from_str("1000.1")? - Decimal::from_str("1000.0")?; // 0.1
```

`Decimal` не потерял ни одного знака. Именно поэтому в упражнении 02 и лабе 01 все расчёты — на `Decimal`.

**3. Батчевая запись через `UNNEST`** (`examples/05-batch-write.rs`): массивы Postgres приходят из Rust как `Vec<T>`, в `INSERT` их разворачивает `UNNEST`:

```rust
let ts: Vec<DateTime<Utc>> = ...;    // 10 000 меток
let vals: Vec<Decimal> = ...;        // 10 000 значений

sqlx::query(
    "INSERT INTO batch_demo (ts, value)
     SELECT * FROM UNNEST($1::timestamptz[], $2::numeric[])")
    .bind(&ts).bind(&vals).execute(&pool).await?;
```

Фактический вывод:

```
вставлено 10000 строк одним запросом за 32.068989ms
проверка: в таблице 10000 строк
```

Один round-trip вместо десяти тысяч — начало темы производительности (модуль 07).

## Как это устроено под капотом

- **Decimal**: мантисса 96 бит + scale (0..28). Сложение/вычитание/умножение точны; **деление** может дать бесконечную дробь (`1/3`) — rust_decimal бросит/вернёт ошибку или округлит по стратегии. Поэтому в формулах делят на «круглые» числа (100) или округляют явно.
- **Округление**: `round_dp(n)` — до n знаков, «половина от нуля». Явная стратегия — `round_dp_with_strategy(n, RoundingStrategy::MidpointAwayFromZero)` (старое имя стратегии — `RoundHalfUp`, deprecated с версии 1.43).
- **chrono/Utc**: `timestamptz` хранит момент времени в UTC; SQLx отдаёт его как `DateTime<Utc>`; serde пишет ISO 8601. Для отчётов «по линии за смену» зона важна (модуль 08).
- **UNNEST**: параметр-массив приходит как отдельное значение по протоколу; `UNNEST` разворачивает его в строки. Один `INSERT` выполняет сервер за один проход.

## Типичные ошибки и грабли

1. **`f64` для метрологии** — накопление ошибки на миллионах точек; сравнения «равно» перестают работать. Держи и в БД (`numeric`), и в Rust (`Decimal`) одно и то же представление.
2. **Деление без округления** — `1/3` увалка; знай стратегию по умолчанию и задавай явную в учётных формулах.
3. **`Decimal` в JSON «как число»** — потеря хвостов (`1000.10` → `1000.1`). Если API-контракт требует число — включай feature `serde-arbitrary-precision` осознанно.
4. **`NaiveDateTime` вместо `DateTime<Utc>`** — потеря зоны: отчёт по «суткам» съедет на таймзону клиента.
5. **Построчная вставка в цикле** — 10 000 round-trip'ов (это минуты). Батч через `UNNEST` — миллисекунды.

## Мини-задание

`Decimal::from_str("0.1")? + Decimal::from_str("0.2")?` — чему равно? Проверь в тесте. Затем: `Decimal::from_str("1")? / Decimal::from_str("3")?` — что вернётся? Объясни по документации.

<details>
<summary>Ответ</summary>

`0.1 + 0.2 = 0.3` ровно (в отличие от `f64`, где `0.30000000000000004`). Деление `1/3` в `Decimal` — либо ошибка (деление на цикл дробь), либо результат по стратегии округления по умолчанию: в `rust_decimal` 1.x по умолчанию — ошибка/паника? Нет: `Decimal` умеет делить только с конечным представлением, иначе возвращает ошибку при `checked_div` либо округляет в `div` по умолчанию. Проверь в консоли и запомни вывод — в лабе 01 ты будешь делить на 100 (безопасно).
</details>

## Как это спросят на собеседовании

1. «Почему нельзя хранить деньги в float?» — двоичное представление, накопление ошибки, нерівні порівняння.
2. «Как устроен rust_decimal?» — 96-битная мантисса + scale; границы ~1e-28..1e28.
3. «Почему Decimal сериализуется в JSON строкой?» — сохранить точность; для чисел — feature `serde-arbitrary-precision`.
4. «Как вставить 10 000 строк быстро?» — один `INSERT ... SELECT * FROM UNNEST($1::...[], $2::...[])` либо `COPY` (модуль 07).
