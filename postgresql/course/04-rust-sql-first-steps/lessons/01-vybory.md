# Урок 01: Выбор крейта доступа к PostgreSQL

**Модуль / кейс:** 04-rust-sql-first-steps / кейсы 1 (каталог), 3 (точность)
**Время:** 2 ч

## Зачем это нужно

От выбора библиотеки зависит весь дальнейший код курса: как ты пишешь запросы, проверяются ли типы, есть ли пул соединений и миграции. Частая ошибка новичка — взять первую попавшуюся библиотеку (или ORM «чтобы не писать SQL»), а потом воевать с ней на временных рядах и триггерах. В этом уроке сравним три пути и выберем основной — по решению дизайна курса (OpenSpec, D2).

## Ключевые идеи (сжато)

- **tokio-postgres** — асинхронный драйвер «в лоб»: минимум абстракций, полный контроль над протоколом. Читаешь колонки по индексу `row.get(0)`, типы проверяются во время выполнения.
- **sqlx** — тоже асинхронный драйвер, но с пулом соединений, маппингом строк в структуры (`FromRow`) и типизированными запросами: runtime (`query_as`, как в этом модуле) и compile-time (`query_as!` — урок 06). Это **не ORM**: SQL пишешь сам.
- **diesel / sea-orm** — ORM: маппят таблицы на структуры и собирают запросы сами. Удобны для типовых CRUD, но плохо ложатся на временные ряды, `COPY`, оконные функции и аудит-триггеры (модули 07–09).
- Курс использует **sqlx + runtime-запросы** (D2): макросы `query_as!` требуют `DATABASE_URL` на этапе компиляции, что ломает «скопировал — собрал». Макросы разберём отдельно в модуле 06 с offline-кэшем.

## Разбор на примере

Оба минимальных примера делают одно и то же: выводят устройства справочника. Сравни код и запусти оба (схема применена, см. README модуля):

```bash
cargo run --example 01-tokio-postgres-hello   # голый драйвер
cargo run --example 02-sqlx-hello             # sqlx + пул
```

**1. tokio-postgres** (`examples/01-tokio-postgres-hello.rs`):

```rust
let (client, connection) = connect(&url, NoTls).await?;
tokio::spawn(async move { connection.await });   // фоновая задача протокола

let rows = client.query("SELECT tag, model FROM devices ORDER BY id", &[]).await?;
for row in rows {
    let tag: &str = row.get(0);                  // тип указываешь сам
    let model: Option<&str> = row.get(1);
}
```

**2. sqlx** (`examples/02-sqlx-hello.rs`):

```rust
let pool = PgPoolOptions::new().max_connections(5).connect(&url).await?;

let rows: Vec<(String, Option<String>)> =
    sqlx::query_as("SELECT tag, model FROM devices ORDER BY id")
        .fetch_all(&pool).await?;
```

Фактический вывод обоих примеров одинаков:

```
M-01-001: CMF-300
D-01-001: MVD-1
W-01-001: MVM-2
M-02-001: CMF-200
D-02-001: MVD-2
```

### Таблица сравнения

| | tokio-postgres | sqlx | diesel / sea-orm |
|---|---|---|---|
| Стиль | драйвер | драйвер + утилиты | ORM |
| Пул соединений | свой руками | из коробки (`PgPool`) | есть (sea-orm — поверх sqlx) |
| Типы запросов | runtime | runtime + compile-time макросы | собственный DSL |
| Маппинг строк | `row.get(i)` вручную | `FromRow` (деривация) | макросы на структуры |
| Миграции | нет | `sqlx migrate` (модуль 06) | есть встроенные |
| Async | tokio | tokio/async-std | diesel — sync, sea-orm — async |
| Временные ряды / COPY / оконные функции | легко (SQL свой) | легко (SQL свой) | мучительно |
| Курс | сравнение (пример 01) | **основной** | упоминание |

## Как это устроено под капотом

- И tokio-postgres, и sqlx говорят с PostgreSQL по **протоколу v3** поверх TCP (см. модуль 13 про PG-протокол и WAL). Разница — в слое поверх: sqlx добавляет пул, деривации и проверку типов, не меняя суть драйвера.
- **Почему sqlx не сломался без `sqlx migrate` и макросов в этом модуле:** мы включили только нужные фичи в `Cargo.toml` (`runtime-tokio`, `tls-rustls-ring`, `postgres`, `chrono`, `rust_decimal`, `json`, `derive`) — меньше зависимостей, быстрее сборка, нет требований к окружению на этапе компиляции (D2).
- **`tokio::spawn(async move { connection.await })`** в примере 01 — это не деталь: клиент tokio-postgres общается с сервером через эту фоновую задачу. Забыл её — запросы «висят» навсегда.

## Типичные ошибки и грабли

1. **Забыл фоновую задачу `connection.await`** у tokio-postgres — классика: компилируется, но всё висит. У sqlx этой проблемы нет (пул управляет соединениями сам).
2. **ORM ради «не писать SQL»** — на временных рядах ты всё равно напишешь SQL (оконные функции, `COPY`, `UNNEST`), но уже через костыли ORM. Выбирай инструмент под задачу.
3. **Типы «на слово»** в tokio-postgres: `row.get::<_, i64>(0)` — если в колонке лежит `int4`, получишь ошибку во время выполнения, а не на компиляции.
4. **Макросы `query!` сразу** — требуют `DATABASE_URL`/`.sqlx` на этапе компиляции; в этом модуле их нет (D2), подключатся в 06.

Открой `Cargo.toml` модуля: из каких фич sqlx собран и почему именно таких? Убери ненужную фичу (например, `json`) и запусти `cargo check` — собери вывод, потом верни.

<details>
<summary>Ответ</summary>

`default-features = false` + набор: `runtime-tokio` (наш рантайм), `tls-rustls-ring` (шифрование соединений), `postgres` (драйвер), `chrono`/`rust_decimal`/`json` (маппинг типов, урок 02), `derive` (деривация `FromRow`). Макросы и миграции не включены — они разбираются в модуле 06. ## Как это спросят на собеседовании

1. «Почему sqlx, а не Diesel?» — SQL под контролем для временных рядов/аудита, async, пул и миграции, compile-time проверка как опция.
2. «Чем runtime-запросы sqlx отличаются от макросов `query_as!`?» — первые проверяются в момент исполнения и не требуют БД на компиляции; вторые проверяют SQL во время сборки и нуждаются в `DATABASE_URL`/offline-кэше.
3. «Что будет, если забыть `connection.await` в tokio-postgres?» — клиент не общается с сервером, запросы вешаются.
