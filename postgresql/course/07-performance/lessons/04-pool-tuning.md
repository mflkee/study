# Урок 04: Тюнинг пула соединений под нагрузку

**Модуль / кейс:** 07-performance / кейс 11 (нагрузочный стенд), 2 (телеметрия)
**Время:** 2.5 ч

## Зачем это нужно

Пул — «бутылочное горлышко»: слишком маленький — запросы ждут в очереди; слишком большой — PostgreSQL тонет в конкуренции за буферы/блокировки и память. Правильный размер пула под профиль нагрузки — половина успеха. Проверяется собственным генератором (пример 05) против `pgbench`.

## Ключевые идеи (сжато)

- Компромисс пула: меньше — очередь в приложении, больше — давка на сервере. Эмпирика: «ядра × 2…4» для типовых OLTP; для тяжёлых — отдельный пул.
- Ключевые параметры: `max_connections`, `acquire_timeout`, `min_connections`, `idle_timeout` (урок 01 модуля 06).
- **Замеры, а не догадки**: меняешь пул → гоняешь нагрузку → смотришь TPS/латентность (свой генератор и pgbench, лаба 01).
- Симптомы: рост `waiting`/ошибки `PoolTimedOut` — пул мал; деградация серверного CPU и `LOCKs` — пул велик.

## Разбор на примере

```bash
cargo run --example 05-loader -- --seconds 5 --pool 4
cargo run --example 05-loader -- --seconds 5 --pool 16
```

Код — `examples/05-loader.rs`: смесь «80% INSERT в telemetry_raw + 20% UPDATE events», пачки по 20 операций в тик. Вывод (стенд автора, 4 с):

```
итог: вставок 660, обновлений 160, всего 820 операций за 4.1 с = 201 TPS   (пул 4)
```

Сравнение с `pgbench` (его профиль другой — честное сравнение, лаба 01):

```bash
docker compose exec -T postgres pgbench -c 4 -j 2 -T 5 -U course course_m06
# tps = 492 (без времени подключения)
```

Влияние пула видно по латентности и `PoolTimedOut`:

```rust
PgPoolOptions::new()
    .max_connections(сила)
    .acquire_timeout(Duration::from_secs(5))
    .min_connections(1)      // прогрев
    .idle_timeout(Duration::from_secs(60))
```

## Как это устроено под капотом

- PgPool раздаёт соединения; при переборе запрос встаёт в очередь ожидания. `acquire_timeout` — предохранитель.
- На сервере каждое соединение — процесс со своим кэшем/памятью; много соединений = память + конкуренция за `shared_buffers`, `WAL`, блокировки индексов.
- TPS — не линейная функция размера пула: кривая растёт, потом стоит/падает. Ищем «плечо» кривой.
- `pg_stat_activity` покажет, сколько соединений реально работают (`state='active'`), а сколько висят в fetch/wait — важнейшая метрика тюнинга (модуль 13 — мониторинг).

## Типичные ошибки и грабли

1. **Пул больше, чем `max_connections` сервера** — `too many clients`, паника, отказ приложения.
2. **Один и тот же пул для «лёгких» и «тяжёлых» запросов** — тяжёлый запрос держит соединение, лёгкие встают в очередь. Нужен пул для тяжёлых (или его отсутствие: асинхронный стек позволяет просто редко их запускать).
3. **Меняю пул, но смотрю только средний TPS** — смотри перцентили латентности (p95/p99): среднее прячет «хвосты» (в генераторе — память/буфер пачек).
4. **Замеряю «сам себя»** — если нагрузка генерируется в том же пуле и блокирует драйвер — цифры лгут; генератор и приложение — разные сущности (пример 05 — отдельный процесс, пачки между тиками).
5. **Упрямый пул 64 на 4 ядра** — сервер не вывозит; малые пулы часто быстрее.

## Мини-задание

Прогони свой генератор с пулом 2/4/16/32 (пример 05, `--pool`) — построй таблицу TPS × pool. Найди, где кривая «выходит на полку»; объясни, почему дальше не растёт.

<details>
<summary>Ответ</summary>

На стенде курса рост TPS заметно замедляется после ~8–16 соединений (тупление на одном CPU/за блокировки индекса). Полка — и есть практический оптимум; дальше — только пересмотр на стороне SQL/индексов.
</details>

## Как это спросят на собеседовании

1. «Как выбрать размер пула?» — экспериментально: TPS × pool, искать «плечо»; эмпирика «ядра × 2..4».
2. «Чем опасен переизбыток соединений?» — память сервера, конкуренция за буферы и блокировки.
3. «Как понять, что пул мал?» — `PoolTimedOut`/рост `waiting`; смотри `pg_stat_activity` и латентность.
