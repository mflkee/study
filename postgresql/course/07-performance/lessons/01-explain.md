# Урок 01: EXPLAIN (ANALYZE, BUFFERS) — чтение планов

**Модуль / кейс:** 07-performance / кейс 11 (нагрузочный стенд)
**Время:** 2.5 ч

## Зачем это нужно

«Почему медленно?» — первый вопрос эксплуатации. PostgreSQL строит **план выполнения** и умеет показать его; `EXPLAIN` — способ увидеть, где теряется время: полный скан, неиспользуемый индекс, сортировка. План читается как конвейер: снизу вверх, «кто съедает время».

## Ключевые идеи (сжато)

- `EXPLAIN <sql>` — план (оценки); `EXPLAIN (ANALYZE, BUFFERS) <sql>` — фактические время, строки, чтения.
- Чтение: идём от **самых вложенных узлов**; ищем `Seq Scan` на больших таблицах, `Nested Loop` с «дорогим» внутренним, сюрпризы по `rows` (оценка ≠ факт).
- Ключевые узлы: `Seq Scan` (полный скан), `Index Scan`/`Index Only Scan` (по индексу), `Bitmap Heap Scan`, `Nested Loop`/`Hash Join`/`Merge Join`, `Sort`, `Limit`.
- `BUFFERS` — физические/кэш-чтения: `shared hit` (кэш) против `shared read` (диск); диск = боль.

## Разбор на примере

База `course_m06`, таблица `events` (20 000 строк, модуль 07 `examples/00-setup.sql`).

**Синтаксис** (`psql -d course_m06`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE device_id = 1 AND ts < '2026-09-25 01:00:00+00';
```

Без индекса — `Seq Scan` (все 20 000 строк):

```
Seq Scan on events  (cost=0.00..460.00 rows=... width=...) (actual time=... rows=5000 loops=1)
  Filter: (device_id = 1)
  Buffers: shared hit=154
```

Чиним индексом (лаба модуля 06, здесь — по-другому: смотрим влияние на ЗАПИСЬ, урок 04):

```sql
CREATE INDEX idx_events_device_ts ON events (device_id, ts);
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
```

Теперь `Index Scan using idx_events_device_ts`, `rows` точнее, время на порядок меньше.

## Как это устроено под капотом

- План строится на **статистике** (`pg_stats`, собранной `ANALYZE`): селективность, гистограммы. Отсюда магические `cost` (условные единицы).
- `ANALYZE` — реальные цифры; если статистика старая — ESTIMATES могут врать (обнови `ANALYZE`).
- `Bitmap Heap Scan` — индекс вернул много ссылок; их сортируют по физическому порядку, чтобы читать страницы по одному разу (дешевле чем Index Scan для широких выборок).
- `Seq Scan` не всегда плох: на маленьких таблицах он честно выигрывает (индекс = лишние чтения).

## Типичные ошибки и грабли

1. **`EXPLAIN` без `(ANALYZE)`** — оценки, не факты; для диагностики нужен фактический прогон (`(ANALYZE, BUFFERS)`).
2. **И читаю план «сверху»** — правильное чтение: от вложенных узлов к корню.
3. **Индекс «не работает»** — колонка в функции (`date_trunc('day', ts)`) — выражение не в индексе B-tree; или порядок колонок не под фильтр.
4. **Забыл `ANALYZE` после массовой вставки** — статистика устарела, план кривой.
5. **Смотрю только время, не `loops`** — `loops: N` в узле объясняет, почему время «вдруг» большое (вложенный цикл).

## Мини-задание

Возьми запрос «последние 10 событий по каждому device_id» (`SELECT DISTINCT ON (device_id) ... ORDER BY device_id, ts DESC`), посмотри план до и после создания индекса `(device_id, ts)`. Объясни по `loops` и `Buffers`.

<details>
<summary>Ответ</summary>

До индекса — `Sort` + `Seq Scan` (все строки, сортировка по device_id, ts). После — `Index Only Scan`/`Index Scan` по `(device_id, ts)` без сортировки: индекс уже упорядочен, `DISTINCT ON` берёт первые вхождения. `Buffers` падают на порядок.
</details>

## Как это спросят на собеседовании

1. «Как найти, что запрос сканирует всю таблицу?» — `EXPLAIN (ANALYZE, BUFFERS)` ищем `Seq Scan` с большим `rows`.
2. «Чем `Bitmap Heap Scan` отличается от `Index Scan`?» — индексное чтение страниц для широких выборок.
3. «Почему план может врать?» — устаревшая статистика; лечится `ANALYZE` и проверкой по факту.
