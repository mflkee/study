# Урок 02: pg_stat_statements — поиск медленных запросов

**Модуль / кейс:** 07-performance / кейс 11 (нагрузочный стенд)
**Время:** 2 ч

## Зачем это нужно

В проде нельзя ставить `EXPLAIN ANALYZE` на каждый запрос — а вот агрегированная статистика по всем запросам сервера уже включена: расширение `pg_stat_statements`. Это первый инструмент поиска «что тормозит» по суммарному времени, без ручных замеров.

## Ключевые идеи (сжато)

- `pg_stat_statements` — таблица статистики по **нормализованным** запросам: `calls`, `total_exec_time`, `mean_exec_time`, `rows`.
- Включается: `shared_preload_libraries=pg_stat_statements` + `CREATE EXTENSION`. В стенде курса уже включено (docker-compose, `infra`).
- Сортируем по `total_exec_time DESC` — «кто съел больше всего времени суммарно», а не «кто средний».
- `pg_stat_reset()` — обнулить (чистый замер после деплоя).

## Разбор на примере

```bash
cargo run --example 04-pgstat
```

Код — `examples/04-pgstat.rs` (выборка TOP-12 по нашим таблицам). После прогона примеров 02/03/05 статистика реальна. Фактический вывод со стенда автора (фрагмент):

```
запрос                                                        total_ms   mean_ms    calls
INSERT INTO telemetry_raw (device_id, seq, ts, value)          2003.2       0.04    50008
COPY telemetry_raw (device_id, seq, ts, value) FROM ST          148.2     148.20        1
INSERT INTO events (device_id, ts, value) SELECT i % $1           29.8      29.76        1
```

Что видно: 50 000 построчных INSERT'ов дали 2003 мс суммарно (мелочь в среднем, но суммарно — смысл жизни), а один COPY — 148 мс суммарно на всё.

Полезные запросы для эксплуатации:

```sql
-- топ по суммарному времени
SELECT calls, round(total_exec_time::numeric,1) AS total_ms,
       round(mean_exec_time::numeric,2) AS mean_ms, left(query,60) AS query
  FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- топ по средней латентности (с фильтром «не одноразовые»)
SELECT calls, round(mean_exec_time::numeric,2) AS mean_ms, left(query,60)
  FROM pg_stat_statements WHERE calls > 100 ORDER BY mean_exec_time DESC LIMIT 10;
```

## Как это устроено под капотом

- При старте сервера библиотека перехватывает выполнение запросов; ключом является **нормализованный текст** (константы → `$1`): 50 000 разных запросов с разными `seq` склеиваются в одну строку статистики.
- Сброс: `SELECT pg_stat_reset();` — обнулить всё (полезно перед нагрузочным тестом, чтобы не смешивать с историей).
- Гранулярность — на сервер; по базе различают по `query` (текст) или по `dbid`/`userid` (колонки).

## Типичные ошибки и грабли

1. **Смотрю `mean_exec_time` и пропускаю «сироту»** — один запрос за вечер с `calls=1` и латентностью 30 с испортит всё суммарное время; это и есть кандидат на разбор, а не «среднее».
2. **Не сбросил `pg_stat_statements` перед замером** — статистика за сутки смешивает профиль; для чистого замера — `pg_stat_reset()`.
3. **Забыл включить расширение ещё в одном стенде** — `pg_stat_statements` пер-база; в `course_m06` расширение создано отдельно (`CREATE EXTENSION`).
4. **Читаю «знакомые» запросы и не вижу своих** — фильтр по имени таблицы (`query ILIKE '%telemetry%'`) или по `dbid`.

## Мини-задание

Сбрось статистику (`pg_stat_reset`), прогони `cargo run --example 03-insert-methods -- --n 5000`, потом покажи топ-5 по `total_exec_time` — объясни, откуда взялся самый «дорогой» запрос.

## Как это спросят на собеседовании

1. «Как найти медленный запрос в проде без профилировщика?» — `pg_stat_statements` по `total_exec_time`.
2. «Что такое нормализация запросов?» — константы → параметры; агрегация в одну строку.
3. «Как замерить влияние деплоя?» — `pg_stat_reset()` → прогон → сравнение, модуль 13 — мониторинг.
