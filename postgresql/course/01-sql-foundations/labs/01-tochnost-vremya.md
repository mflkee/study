## Цель

1. **Потеря точности**: накопительный расчёт на float8 «разъезжается» на сотых — аудит не сходится.

## Шаги

### Часть A. Потеря точности в накопительном расчёте

**Симптом:** «Итог за месяц не сходится на 0.01–0.05».

Воспроизведи — сложим `0.1` десять тысяч раз в float8 и в numeric:

```sql
BEGIN;
-- float8: 0.1 не представим точно, ошибка накапливается
SELECT sum(0.1::float8) AS float_sum FROM generate_series(1, 10000);

-- numeric: точная десятичная арифметика
SELECT sum(0.1::numeric) AS numeric_sum FROM generate_series(1, 10000);
ROLLBACK;
```

Ожидаемый вывод на стенде курса:

```
      float_sum
--------------------
 1000.0000000001588

 numeric_sum
-------------
      1000.0
```

В float-мире 0.1×10000 ≠ 1000 ровно: накопленный «хвост» 1.588e-10. На реальных объёмах (миллионы замеров) ошибка вырастает до сотых — и аудит не сходится.

**Объяснение:** внутри float8 — двоичная мантисса; 0.1 ≈ 0.1000000000000000055511151231257827. Десять тысяч суммирований дают накопленный «хвост». Для масс/объёмов на проде эта погрешность видна в отчётах и аудите.

**Починка:** в схеме — колонки `numeric(20,6)` (как `measurements.value`). Ниже — вариант миграции уже существующей float-таблицы.

### Часть B. Время без пояса

**Симптом:** «Данные за ночь вдруг попали на вечернее окно».

Воспроизведи: приложение записывает телеметрию «00:00 MSK», но без указания пояса, в колонку `timestamp`; читатели подключаются в UTC-сессии:

```sql
BEGIN;
SET TIME ZONE 'UTC';
CREATE TEMP TABLE bad_telemetry (ts timestamp, value numeric);
INSERT INTO bad_telemetry VALUES ('2026-09-23 00:00:00', 100.0);

-- "цифры", которые записал интегратор
SELECT ts AS stored_digits, value FROM bad_telemetry;

-- истинный момент, если трактовать строку как МОСКОВСКОЕ время
SELECT ts AT TIME ZONE 'Europe/Moscow' AS true_moment, value FROM bad_telemetry;

-- как это прочитает сессия в UTC (цифры трактуются как UTC) — данные "поехали"
SELECT ts::timestamptz AS misread_as_session_utc, value FROM bad_telemetry;
ROLLBACK;
```

Ожидаемый вывод на стенде курса:

```
    stored_digits    | value
---------------------+-------
 2026-09-23 00:00:00 | 100.0

      true_moment       | value
------------------------+-------
 2026-09-22 21:00:00+00 | 100.0

 misread_as_session_utc | value
------------------------+-------
 2026-09-23 00:00:00+00 | 100.0
```

Симптом налицо: «00:00» на самом деле — это `21:00` предыдущего дня (если цифры были MSK-полночью). Reader в UTC-сессии видит «00:00+00» и считает, что всё в порядке — а данные «съехали» на 3 часа. Ошибка невидима, пока кто-то не сравнит с бумажным журналом.

**Объяснение:** `timestamp` без пояса хранит «календарные цифры»; как их понимать — решает пояс сессии на чтении. `timestamptz` хранит момент и всегда показывает одну и ту же физическую секунду.

**Починка:** правильный тип в новой схеме — `timestamptz`. Для существующей таблицы с `timestamp` миграция:

```sql
-- Правим значения: строки '2026-09-23 00:00:00' интерпретируем как MSK и сохраняем момент
ALTER TABLE bad_telemetry ALTER COLUMN ts TYPE timestamptz
USING ts AT TIME ZONE 'Europe/Moscow';
```

Так мы задаём поясу интерпретации один раз при миграции, и дальше данные — моменты, а не «цифры на стене».

## Разбор типичных проблем

| Симптом | Причина | Решение |
|---|---|---|
| `float_sum` = ровно 1000.0 | на малых объёмах ошибка не видна | накопи на большем числе суммирований или через `- 1000` сравнение |
| `AT TIME ZONE` даёт NULL/неожиданное | путаница направления: `timestamp AT TIME ZONE 'пояс'` переводит из пояса в UTC-момент | проверь семантику: для столбца `timestamp` это «интерпретируй как пояс, верни момент» |
| Миграция упала на существующих строках | в старых данных уже «битые» значения | прогони SELECT с вариантом USING сначала, потом ALTER в транзакции |
