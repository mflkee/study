# Урок 03: Типы данных — числовая точность и время

**Кейсы:** 3 (точность расчётов)
**Время:** 1.5 ч

## Зачем это нужно

СИКН — это про метрологию: масса нетто, плотность, влажность. Одна ошибка типа — и «правильные» данные разъезжаются на копейки, а аудит их не увидит. Два главных решения схемы: **во что хранить числа** и **как хранить время**.

## Ключевые идеи (сжато)

- `float8` — приближённо: `0.1 + 0.2 = 0.30000000000000004`. Для масс и расчётов — `NUMERIC(p,s)`.
- `timestamptz` хранит **момент** (внутри UTC), `timestamp` — **стенное время** без пояса. Телеметрия и аудит — только `timestamptz`.
- `jsonb` нормализует ключи (порядок не важен при сравнении); `enum` — строгий тип с фиксированным набором.
- Одинаковые на вид записи времени «12:00+00» и «15:00+03» — это ОДИН момент.

## Разбор на примере

Запуск: `./infra/apply-db.sh course/01-sql-foundations/examples/04-tipy-numeric-timestamptz.sql`.

**1. float8 vs numeric:**

```sql
SELECT 0.1::float8 + 0.2::float8 AS float_sum,
       0.1::numeric + 0.2::numeric AS numeric_sum;
```
```
      float_sum       | numeric_sum
----------------------+-------------
 0.30000000000000004  |        0.3
```

Внутри `float8` — двоичное представление: 0.1 не хранится точно, поэтому результат 0.30000000000000004. `numeric` — десятичная арифметика, точная. Для «масса брутто 1000.000 кг» разница незаметна на глаз, но в накопительных расчётах (итоги за месяц) ошибка накапливается — см. лабу модуля.

**2. timestamptz: один момент, разные записи:**

```sql
SET TIME ZONE 'UTC';
SELECT '2026-09-24 12:00:00+00'::timestamptz AS utc_noon,
       '2026-09-24 15:00:00+03'::timestamptz AS msk_noon;
```
```
        utc_noon        |        msk_noon
------------------------+------------------------
 2026-09-24 12:00:00+00 | 2026-09-24 15:00:00+03
```
```sql
SELECT ('2026-09-24 12:00:00+00'::timestamptz = '2026-09-24 15:00:00+03'::timestamptz) AS same_instant;
```
```
same_instant
-------------
t
```

**3. timestamptz: отображение зависит от пояса сессии:**

```sql
SET TIME ZONE 'Europe/Moscow';
SELECT '2026-09-24 12:00:00+00'::timestamptz AS shown_in_msk;
```
```
      shown_in_msk
------------------------
 2026-09-24 15:00:00+03
```

Момент тот же — показан в поясе сессии. В таблице `measurements` значения хранятся как `timestamptz`; к ним всегда применим `AT TIME ZONE` для перевода в нужный пояс.

**4. timestamp vs timestamptz: арифметика интервалов:**

```sql
SELECT '2026-09-24 12:00:00'::timestamp + interval '1 hour'      AS ts_plus,
       '2026-09-24 12:00:00+00'::timestamptz + interval '1 hour' AS tstz_plus;
```
```
      ts_plus       |       tstz_plus
--------------------+------------------------
 2026-09-24 13:00:00 | 2026-09-24 13:00:00+00
```

Формально результат тот же, но `timestamp` не знает о поясах — при переходе на летнее время «13:00 стенного» может стать не тем «13:00 момента».

**5. jsonb: порядок ключей не важен:**

```sql
SELECT '{"tag":"M-01","v":1}'::jsonb = '{"v":1,"tag":"M-01"}'::jsonb AS jsonb_equal;
```
```
jsonb_equal
------------
t
```

**6. array и enum** — основы: `ARRAY['a','b','c']`, `array_length(...)`, а enum создаётся один раз с фиксированным набором значений (`DO $$ ... CREATE TYPE device_kind AS ENUM (...)`; использование — `'mass_meter'::device_kind`). Обрати внимание: в схеме каталога мы сознательно использовали `CHECK`-ограничение вместо enum — через `CREATE TYPE` нет `IF NOT EXISTS`, а CHECK переживает повторное применение скрипта.

## Как это устроено под капотом

- PostgreSQL хранит `timestamptz` как **мгновение** (целое число микросекунд от 2000-01-01 UTC); пояс — свойство **отображения**, не хранения. Поэтому «+00» и «+03» — один и тот же бинарный момент.
- `timestamp` без пояса — просто «дата-время по календарю»; равенство и арифметика не учитывают DST (переход на летнее/зимнее время).
- `numeric` хранит десятичные цифры как целое + масштаб — точность до выбранного `s`, ценой скорости и размера.
- `jsonb` при записи нормализует ключи (сортирует, чистит дубли и пробелы) — сравнение и индексация становятся детерминированными.

## Типичные ошибки и грабли

1. **float8 для массы/объёмов/денег** — накопленная ошибка в отчётах; сравнение «равно» не работает. Для метрологии — `numeric`.
2. **`timestamp` для телеметрии** — потерян пояс; данные из разных часовых поясов смешиваются. В СИКН-потоке всегда `timestamptz` + фиксация пояса на входе.
3. **Приложение шлёт «12:00:00» без пояса** — PostgreSQL интерпретирует в поясе сессии; если сессия у сервера в UTC, а оператор в MSK — всё «поехало» на 3 часа.
4. **Сравнение jsonb-документов** — порядок ключей игнорируется (может удивить, если ждёшь байтовое сравнение).
5. **Enum-колонка расширяется только миграцией** (ALTER TYPE ADD VALUE), нельзя вставить новое значение «на лету» — в отличие от CHECK + таблицы-справочника.

## Мини-задание

Определи тип колонки для хранения массы нетто с точностью до 0.001 кг и для момента измерения с поясом. Обоснуй в одном предложении каждый.

<details>
<summary>Ответ</summary>

- Масса нетто: `numeric(18,3)` — десятичное точное, до тысячных кг.
- Момент измерения: `timestamptz` — это момент, а не «стенное» время; пояс фиксируется значением, отображение — поясам сессий.

(Точность `numeric(18,3)` достаточно для значений до 10^15 кг с тремя знаками; реальный регламент может требовать `(20,6)`.)
