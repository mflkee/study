# Урок 05: Подзапросы, CTE и оконные функции

**Кейсы:** 5 (сменные и суточные отчёты)
**Время:** 2 ч

## Зачем это нужно

Отчёт «последнее значение каждого устройства», «дельта между замерами», «топ устройств по среднему» — это оконные функции и подзапросы. Это уровень, на котором SQL из «примитивных выборок» превращается в аналитический инструмент: без них сменный отчёт пишется десятком кривых запросов с самодельной джойн-магией.

## Ключевые идеи (сжато)

- Оконная функция считает значение для КАЖДОЙ строки по окну `PARTITION BY ... ORDER BY ...` — строки не схлопываются (в отличие от GROUP BY).
- `row_number() OVER (...)` — номер строки в окне — классика для «последнего значения».
- `lag(x)` — значение из предыдущей строки окна: дельта между замерами.
- Оконная функция живёт в `SELECT`/`ORDER BY`; фильтровать по ней в `WHERE` нельзя — нужен подзапрос или CTE.
- CTE (`WITH ... AS (...)`) — именованные подзапросы: читаемость и переиспользование.

## Разбор на примере

Запуск: `./infra/apply-db.sh course/01-sql-foundations/examples/06-okonnye-funkcii.sql`.

**1. ROW_NUMBER: последнее значение каждого устройства:**

```sql
SELECT device_id, ts, value
FROM (
    SELECT device_id, ts, value,
           row_number() OVER (PARTITION BY device_id ORDER BY ts DESC) AS rn
    FROM measurements
) t
WHERE rn = 1
ORDER BY device_id;
```
```
 device_id |           ts           |    value
-----------+------------------------+-------------
         1 | 2026-09-23 12:00:00+00 |  998.500000
         2 | 2026-09-23 12:00:00+00 |  850.150000
         3 | 2026-09-23 00:00:00+00 |    0.480000
         4 | 2026-09-23 12:00:00+00 |  497.250000
         5 | 2026-09-23 12:00:00+00 |  859.950000
```

Механика: окно = все строки устройства (`PARTITION BY device_id`), внутри — по убыванию `ts`; `row_number()=1` — самая свежая. Фильтр по `rn` вынесен в подзапрос: в WHERE оконная функция недоступна.

**2. LAG: дельта относительно предыдущего замера:**

```sql
SELECT device_id, ts, value,
       round(value - lag(value) OVER (PARTITION BY device_id ORDER BY ts), 3) AS delta
FROM measurements
ORDER BY device_id, ts;
```
```
 device_id |           ts           |    value    | delta
-----------+------------------------+-------------+-------
         1 | 2026-09-22 00:00:00+00 | 1000.000000 |
         1 | 2026-09-22 06:00:00+00 | 1010.500000 | 10.500
         1 | 2026-09-22 12:00:00+00 | 1005.250000 | -5.250
         ...
         5 | 2026-09-23 12:00:00+00 |  859.950000 | -0.150
```

Первый замер каждого устройства — `lag` = NULL (дельта пустая). Это нормально и часто именно так и оставляют.

**3. GROUP BY по дню (агрегаты, не окна):**

```sql
SELECT device_id, ts::date AS day, count(*) AS n, round(sum(value), 3) AS total
FROM measurements
GROUP BY device_id, ts::date
ORDER BY device_id, day;
```
```
 device_id |    day     | n |  total
-----------+------------+---+----------
         1 | 2026-09-22 | 4 | 4005.875
         1 | 2026-09-23 | 3 | 2996.250
         2 | 2026-09-22 | 2 | 1700.400
         ...
```

**4. rank над агрегатом:** устройства по среднему значению:

```sql
SELECT device_id, round(avg(value), 3) AS avg_v,
       rank() OVER (ORDER BY avg(value) DESC) AS rnk
FROM measurements
GROUP BY device_id
ORDER BY rnk;
```
```
 device_id |  avg_v   | rnk
-----------+----------+-----
         1 | 1000.304 |   1
         5 |  859.963 |   2
         2 |  850.188 |   3
         4 |  500.357 |   4
         3 |    0.490 |   5
```

Здесь окно — вся выборка (нет PARTITION BY): `rank` по убыванию среднего. Пример показывает, что оконные функции можно применять поверх агрегатов (исполняются после GROUP BY).

## Как это устроено под капотом

- Оконные функции выполняются в отдельном шаге после `GROUP BY`/`HAVING` и до `ORDER BY` — поэтому к ним нельзя обращаться в WHERE.
- `PARTITION BY` делит строки на группы, `ORDER BY` в окне задаёт порядок «оконного» вычисления (для `lag`/`row_number` он критичен).
- `row_number()`/`rank()`: rank оставляет пропуски при равенстве (1,2,2,4), `dense_rank` — нет (1,2,2,3). Для «топ-N» чаще нужен именно rank.
- CTE (`WITH`) — не всегда материализуется (в PG 18 может быть inline): используй для читаемости и переиспользования, а не как гарантию ускорения.

## Типичные ошибки и грабли

1. **Фильтр по оконной функции в WHERE** — `WHERE rn = 1` упадёт; нужно `WHERE` во внешнем запросе (подзапрос/CTE).
2. **Забытый PARTITION BY** — окно = вся таблица: `row_number()` пронумерует строки глобально, отчёт по устройствам сломается.
3. **Тот же ORDER BY в окне и в партиции** — дельта считается не по времени, а по порядку вставки: в окне ОБЯЗАТЕЛЬНО `ORDER BY ts`.
4. **lag без порядка** — может вернуть «прошлую» строку в произвольном порядке.
5. **Путаница rank/dense_rank/row_number** — для «последнего значения» row_number по убыванию ts, для «топ-N по значению» — rank по значению.

## Мини-задание

Построй отчёт «последний замер каждого устройства за 2026-09-23» (только этот день) с дельтой к предыдущему замеру того же дня. Используй CTE.

<details>
<summary>Ответ</summary>

```sql
WITH ranked AS (
    SELECT device_id, ts, value,
           row_number() OVER (PARTITION BY device_id ORDER BY ts DESC) AS rn,
           lag(value)   OVER (PARTITION BY device_id ORDER BY ts)     AS prev
    FROM measurements
    WHERE ts >= '2026-09-23 00:00:00+00' AND ts < '2026-09-24 00:00:00+00'
)
SELECT device_id, ts, value,
       round(value - prev, 3) AS delta
FROM ranked
WHERE rn = 1
ORDER BY device_id;
```

Для device_id=1: последнее значение дня 998.500000, дельта ≈ −4.250 (от 1002.750000).
</details>
