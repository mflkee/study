# Урок 01: Пул соединений — конфигурация, размер, таймауты, retry

**Модуль / кейс:** 06-sqlx-in-depth / кейс 2 (телеметрия), 7 (очередь)
**Время:** 2 ч

## Зачем это нужно

Каждый запрос к PostgreSQL — это соединение (TCP + аутентификация, дорого). Пул держит N живых соединений и выдаёт их запросам: без пула под нагрузкой процесс задыхается в «открыть-закрыть», а с безразмерным пулом — PostgreSQL тонет в конкуренции. Нужно понимать конфигурацию и признаки «не влез в пул».

## Ключевые идеи (сжато)

- `PgPool` — набор живых соединений; `max_connections` — потолок; лишние запросы **ждут** свободное соединение до `acquire_timeout`.
- Конфигурация: `min_connections` (прогрев), `max_connections` (потолок), `acquire_timeout` (сколько ждать), `idle_timeout` (закрывать «простаивающие»).
- `pool.size()`, `pool.num_idle()` — статистика; `pool.clone()` дёшев (Arc) — раздаётся по задачам.
- **Retry** — экспоненциальная задержка (`base`, `2×base`, `4×base`…); ретраить ТОЛЬКО транзиентные ошибки (пики, serialization failure), не баги данных.

## Разбор на примере

```bash
cargo run --example 01-pool
```

Код — `examples/01-pool.rs`: пул на 5 соединений, 20 конкурентных задач (каждая: сон 10 мс + `count(*)`), потом «маленький» пул на 1 соединение для демонстрации таймаута.

Фактический вывод:

```
пул до запросов: size=0 idle=0
  задача  0: устройств в базе = 6
  ...
20 задач отработали через пул из 5 соединений, сумма count(*) = 120
пул после: size=5 idle=5
acquire_timeout сработал: pool timed out while waiting for an open connection
```

Что важно:
- `size=0` до запросов — пул открывает соединения **лениво** (при первом запросе), `min_connections` — желательный прогрев.
- 20 задач на 5 соединениях — никто не упал: лишние ждали в очереди пула (нашёл `waiting` через `num_waiting` — в sqlx 0.9 метода нет, оценка по таймаутам).
- `acquire_timeout` — реальная ошибка `pool timed out` при исчерпании пула.

**Retry-хелпер** (в `src/lib.rs`): экспоненциальная задержка, `attempts` попыток:

```rust
let value = retry(5, Duration::from_millis(20), || async {
    // транзиентная операция
}).await?;
```

## Как это устроено под капотом

- Пул = очередь свободных соединений + счётчик; `acquire()` берёт свободное или открывает новое (до `max`); если все заняты — задача становится в очередь ожидания.
- `acquire_timeout` — сторожевая: если место не освободилось за время — `PoolTimedOut`.
- Соединение, упавшее с сетевой ошибкой, пул выбрасывает и открывает новое (self-healing).
- Размер пула — компромисс: много соединений = много памяти сервера и конкуренция на каталогах/блокировках PG; мало — очередь в одном процессе. Эмпирика для PG: «число ядер × 2…4» + отдельный пул на тяжёлые задачи (тюнинг — модуль 07).

## Типичные ошибки и грабли

1. **`max_connections` больше, чем `max_connections` в PG** — конфиг сервера (по умолчанию 100); при переборе — `too many clients`, паника в рантайме. Пул приложения должен быть меньше лимита сервера.
2. **Один долгий запрос держит соединение** — пул «кончился», остальные ждут/таймаутят. Не держи соединение во время внешней HTTP-паузы: бери соединение, делай запрос, отдавай.
3. **Ретрай вслепую** — например, на нарушении уникальности: повторов станет больше, баг не исправится. Классифицируй ошибки (урок 04).
4. **Забытый `?` на `acquire()`** — и пул ловит `PoolTimedOut` без обработки.
5. **`num_waiting` нет в sqlx 0.9** — не ищи метод; диагностируй по `acquire_timeout`/метрикам `pg_stat_activity` (модуль 13).

## Мини-задание

Пул на 2 соединения, 10 задач: каждая берёт acquire, спит 100 мс, возвращает. Замерь общее время (должно быть ≈ 5 × 100 мс — по 2 задачи одновременно). Уменьши `acquire_timeout` до 50 мс — поймай ошибку и объясни, что произошло.

<details>
<summary>Ответ</summary>

10 задач по 100 мс на пуле из 2 = 5 «волн» ≈ 500+ мс. `acquire_timeout = 50 мс` при занятых 2 соединениях — `pool timed out`: задача ждала место дольше таймаута. Это сигнал: либо поднять пул, либо ускорить запросы.
</details>

## Как это спросят на собеседовании

1. «Как выбрать размер пула?» — баланс памяти сервера и очередей; «ядер × 2..4», отдельный пул для тяжёлых задач; не превышать лимит сервера.
2. «Что будет при исчерпании пула?» — запросы ждут до `acquire_timeout`, потом ошибка `PoolTimedOut`.
3. «Какие ошибки ретраить?» — только транзиентные (timeout, serialization, потеря соединения); Unique/Check — нет.
