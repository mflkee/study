# Урок 02: Фикстуры и тест SQL-функции

**Модуль / кейс:** 12-testing / кейс 4 (аудит), 1 (каталог)
**Время:** 2 ч

## Зачем это нужно

SQL-функции и триггеры — это код, который обязан тестироваться так же, как Rust: с подготовленными данными (фикстурами), предсказуемыми вызовами и проверкой результата. «Написать функцию и не проверить» — главный источник сюрпризов в проде.

## Ключевые идеи (сжато)

- **Фикстуры** — детерминированные данные для теста (product+order в нашем случае); вставляются в начале теста в свою таблицу.
- Хелперы фикстур — отдельные функции (`insert_fixtures`), чтобы тесты читались как сценарий.
- Тест SQL-функции: вызвать функцию через `sqlx::query_scalar("SELECT order_total($1)")`, сверить с ожиданием.
- Ожидаемая ошибка функции — часть теста (`assert!(call…is_err())`).
- `sqlx::test` (макрос) — альтернатива: БД создаётся и откатывается автоматически на тест; в нашем курсе изоляцию даёт testcontainers (урок 01), либо `sqlx::test` на dev-стенде.

## Разбор на примере

```bash
cargo test --test pg_integration order_total
```

Код — `tests/pg_integration.rs` + `exercises/ex02_fixtures.rs` (упражнение 02). Тест:

```rust
let (product_id, order_id) = insert_fixtures(&pool, "SKU-1", "Массомер", "12.5000", 3).await?;
let total = call_order_total(&pool, order_id).await?;
assert_eq!(total, Decimal::from_str("37.5000").unwrap(), "12.5 × 3 = 37.5");
// нет заказа → функция кидает исключение:
assert!(call_order_total(&pool, 999_999).await.is_err());
```

Фактический итог на стенде: `test result: ok. 2 passed` (миграции + функция с фикстурами).

## Как это устроено под капотом

- Фикстуры вставляются в контейнер-БД теста (никакого влияния на стенд курса).
- `SELECT order_total($1)` — вызов хранимой функции из Rust; результат `numeric` → `Decimal` (модуль 04).
- Функция кидает `RAISE EXCEPTION` при отсутствии заказа — ошибка приходит как `sqlx::Error` и проверяется в тесте; это тестируемое поведение, а не «сюрприз».

## Типичные ошибки и грабли

1. **Фикстуры «утекают» между тестами** — контейнер изолирован; если используешь общий стенд — транзакция/truncate после каждого теста.
2. **Проверка только успеха** — не забудь negative-кейсы (нет заказа, неправильные типы).
3. **Сравнение типов** — `numeric` → `Decimal`, не строка (модуль 04): bind числом, не текстом (иначе «expression is of type text» — поймано при сборке модуля).
4. **Тест зависит от порядка** — каждый тест сам строит свои фикстуры (нет глобального сида).
5. **Функция меняется в миграции «назад»** — правь только новыми миграциями (модуль 06), а тест — контракт поведения.

## Мини-задание

Добавь тест: функция `order_total` для заказа с qty=0 должна падать (CHECK qty>0) — проверь, что INSERT ордера с qty=0 даёт ошибку.

<details>
<summary>Ответ</summary>

```rust
let res = sqlx::query("INSERT INTO orders (product_id, qty) VALUES ($1, 0)")
    .bind(product_id).execute(&pool).await;
assert!(res.is_err(), "CHECK qty > 0 нарушается");
```
</details>

## Как это спросят на собеседовании

1. «Как тестировать хранимые функции?» — фикстуры + вызов функции + сверка результата + negative-кейсы.
2. «Фикстуры — это что?» — детерминированные данные теста, создаваемые в самом тесте.
3. «Чем тест SQL-функции отличается от теста репозитория?» — уровень: функция — чистый контракт БД; репозиторий — интеграция с приложением.
