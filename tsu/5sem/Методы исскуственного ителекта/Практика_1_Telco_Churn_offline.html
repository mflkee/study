Шаг 4. Feature Engineering (создание признаков)¶

Модели понимают только числа, поэтому кодируем категориальные признаки:

  • Label Encoding — для бинарных Yes/No и пола (Male/Female).
  • One-Hot Encoding — для многозначных (InternetService, PaymentMethod, Contract и т.д.).

Реализуем через ColumnTransformer: бинарные — OneHotEncoder(drop='if_binary'), остальные — OneHotEncoder(handle_unknown='ignore'), числа — StandardScaler.

Шаг 5. Разделение, масштабирование и обучение LogisticRegression¶

Собираем Pipeline: препроцессинг (ColumnTransformer) + модель. Это защищает от утечки данных (scaler обучается только на train).

In [14]:
from sklearn.preprocessing import OneHotEncoder

# Бинарные признаки кодируем в 0/1 (Label Encoding)
X_enc = X.copy()
for col in binary_cols:
    vals = sorted(X_enc[col].unique())
    X_enc[col] = X_enc[col].map({vals[0]: 0, vals[1]: 1})

X_train, X_test, y_train, y_test = train_test_split(
    X_enc, y, test_size=0.2, random_state=RANDOM_STATE, stratify=y
)
print("Train:", X_train.shape, "| Test:", X_test.shape)
print("Доля Churn в train:", round(y_train.mean(), 4), "| в test:", round(y_test.mean(), 4))

# Препроцессор: числа -> StandardScaler, бинарные уже 0/1 -> passthrough, многозначные -> One-Hot
preprocessor = ColumnTransformer(
    transformers=[
        ("num", StandardScaler(), numeric_cols),
        ("bin", "passthrough", binary_cols),
        ("cat", OneHotEncoder(handle_unknown="ignore"), multi_cols),
    ]
)

log_reg = Pipeline(steps=[
    ("prep", preprocessor),
    ("model", LogisticRegression(max_iter=1000, random_state=RANDOM_STATE)),
])

log_reg.fit(X_train, y_train)
print("Модель обучена.")

предсказано «остался» предсказано «ушёл»
реально остался TN — верно FP — ложная тревога

Наш Recall (~0.55) означает: модель находит лишь около половины реально уходящих клиентов. Именно FN самые дорогие в бизнесе — потерянного клиента уже не удержать. Accuracy (~0.80) при этом выглядит «хорошо», хотя это следствие дисбаланса классов.

def metrics(name, y_true, y_pred, y_proba):
    return {
        "Модель": name,
        "Accuracy": accuracy_score(y_true, y_pred),
        "Precision": precision_score(y_true, y_pred),
        "Recall": recall_score(y_true, y_pred),
        "F1": f1_score(y_true, y_pred),
        "ROC-AUC": roc_auc_score(y_true, y_proba),
    }

Вывод по звёздочке — стало ли лучше?

На этом датасете — нет, не лучше: LogisticRegression обошла ансамбли по всем ключевым метрикам (F1 ≈ 0.60 и ROC-AUC ≈ 0.842 против F1 ≈ 0.56 у RandomForest и ≈ 0.57 у CatBoost).

Почему так:

  • после One-Hot признаки во многом линейно разделимы, а LogisticRegression со StandardScaler — очень крепкий baseline для Telco Churn;
  • ансамбли с дефолтными гиперпараметрами на небольшой выборке (5634 train) склонны переобучаться (RandomForest — из-за глубоких деревьев, CatBoost — без тюнинга);
  • дисбаланс классов одинаково давит Recall у всех моделей.

Что стоит попробовать, чтобы ансамбли «выиграли»:

  • тюнинг гиперпараметров (GridSearchCV/Optuna: max_depth, n_estimators, learning_rate);
  • балансировка классов (class_weight="balanced" для RF и LogReg, scale_pos_weight/auto_class_weights для CatBoost);
  • подбор порога классификации под бизнес-метрику (Recall/F1);
  • feature engineering: число подключённых услуг, флаг наличия поддержки и т.п.

Главный урок: ансамбль — не гарантия улучшения. Выбор модели нужно проверять на конкретных данных и метриках, а не выбирать «по умолчанию». При этом важность признаков у ансамблей подтверждает выводы EDA (см. ниже).

Ответ на вопрос «какой фактор главный?»

Главные драйверы оттока — признаки, связанные с условиями контракта и стажем клиента:

  1. Contract (Month-to-month) — самый сильный фактор. Помесячный контракт → резко выше риск ухода.
  2. tenure — стаж: чем дольше клиент, тем ниже вероятность ухода (обратная зависимость).
  3. TotalCharges / MonthlyCharges — дорогие тарифы и малые суммарные платежи повышают отток.
  4. OnlineSecurity / TechSupport (отсутствие услуг) и InternetService (Fiber optic) — тоже заметные факторы.

Бизнес-вывод: удержание через перевод клиентов с Month-to-month на срочные контракты и подключение поддерживающих услуг (TechSupport, OnlineSecurity) — наиболее очевидные рычаги снижения оттока.
