Проблема и назначение системы

Как было (AS IS)

  • реестр СИ/ЭСИ — в разрозненных Excel-файлах по папкам и подразделениям;
  • сроки поверки контролируются вручную по календарю — риск просрочки;
  • данные из ФГИС «Аршин» переносятся руками: опечатки и дубли;
  • статус прибора нигде не агрегирован; нет разграничения доступа к файлам.

Назначение и результат

  • единая база измерительного оборудования с иерархией «папка → группа → прибор»;
  • автоматический контроль сроков и синхронизация с ФГИС «Аршин»;
  • прозрачная история поверок и ремонтов; доступ заказчика — только к своим папкам;
  • результат: работающая система v0.13.0: 91 путь API, 124 операции, 18 экранов, 196 backend-тестов.

Два уровня разграничения

  • роль — какой класс операций разрешён (чтение / оператор / администратор);
  • скоуп папок — белый список разрешённых и чёрный список скрытых папок;
  • нет доступа к объекту → 404, а не 403: система не раскрывает сам факт существования чужих данных.

Поток данных: вход в систему (HMAC, stateless)

POST /auth/login
→
PBKDF2-HMAC-SHA256
600 000 итераций, соль 16 Б
→
HMAC-токен
base64url(payload).base64url(sig)
→
200 {access_token, user}
↓
get_current_user: подпись → загрузка пользователя → is_active
→
require_operator / require_admin
→
скоуп папок → 403 или 404
  1. Клиент: POST /api/v1/auth/login {email, password}.
  2. Pydantic-валидация → AuthService.login(); пароль проверяется PBKDF2-HMAC-SHA256, 600 000 итераций.
  3. Сервер формирует токен: base64url(payload) . base64url(HMAC-SHA256(payload, secret)), payload = {sub, role, iat, exp}.
  4. Ответ 200 {access_token, user}; клиент подставляет Authorization: Bearer <token>.
  5. Сервер не хранит сессии: отзыв = блокировка пользователя (проверка на каждом запросе) или ротация ключа.

Поток данных: импорт из Аршина и поверка

Сверка с ФГИС «Аршин»

  1. POST /arshin/search — поиск по свидетельству, регистрационному номеру, типу прибора.
  2. ArshinClient: таймаут 30 с, до 5 попыток, экспоненциальная задержка 2 → 45 с.
  3. GET /arshin/vri/{vri_id} — детализация; ответ кэшируется в si_verifications вместе с raw_payload_json.
  4. POST /equipment/folders/{id}/refresh-tasks — шапка задачи + строка на каждый прибор: UPDATED / UPDATED_UNCERTAIN / UNCHANGED / NOT_FOUND / ERROR.
  5. Неоднозначный заводской номер → serial_ambiguous + список кандидатов; применяется выбранная оператором запись.

Поверка и ремонт

  • POST /equipment/{id}/verification — режим (выездная/на месте, с демонтажом или без), маршрут, сроки;
  • этапы, переписка и вложения; закрытие — POST .../verification/close;
  • групповые операции: POST /equipment/verifications/bulk + PATCH .../batch/{batch_key}.

Доступ: RBAC + скоуп папок

Уровень Где проверяется Результат при отказе
Аутентификация get_current_user (подпись токена, is_active) 401
Роль require_operator / require_admin 403
Скоуп папок is_folder_access_allowed в сервисах 404 (soft-denial)
Ролевые экраны RequireRoles в React Router редирект в интерфейсе
  • DEVELOPER и ADMINISTRATOR видят всё — скоуп не ограничен;
  • MKAIR и CUSTOMER — только allowed_folder_ids минус hidden_equipment_folder_ids;
  • проверка применяется к спискам, одиночным объектам и вложенным сущностям (поверки, ремонты, комментарии, задачи);
  • почему 404, а не 403: 403 подтверждает существование объекта, а сам факт наличия чужого прибора — коммерческая информация.

Фон, миграции, эксплуатация

Фоновые задачи (Redis + RQ)

  • очередь notifications, воркер отдельным контейнером: python -m app.tasks.worker;
  • письма-упоминания, события процессов, уведомления подписчикам, временные пароли;
  • таймаут задачи 120 с, TTL результата 300 с, TTL ошибки 24 ч;
  • fallback: при недоступности Redis письмо уходит синхронно — уведомление не теряется;
  • напоминания по срокам идемпотентны: UNIQUE (task_id, reminder_date);
  • пакетное обновление папки — BackgroundTasks с прогрессом в БД.

Миграции и эксплуатация

  • Alembic: 66 ревизий, alembic upgrade head при старте контейнера backend;
  • GET /api/v1/health — живость; GET /api/v1/health/ready — БД (SELECT 1) и Redis, иначе 503;
  • контейнеры restart: unless-stopped, перед деплоем — pg_dump базы.

Что осталось и выводы

Сделано

  • единая БД: 30 таблиц, 3НФ с документированными денормализациями;
  • REST API: 91 путь, 124 операции, OpenAPI и Swagger; веб-клиент: 18 экранов;
  • интеграция с ФГИС «Аршин» с ретраями и пакетным обновлением;
  • 196 pytest + 33 vitest, нагрузочные тесты Locust, CI/CD с деплоем.

Осталось

  1. второй протокол взаимодействия (кроме HTTP/REST) — уточнить зачёт SMTP, иначе WebSocket/SSE;
  2. фикс PBKDF2: вынести хеширование в пул потоков и перепрогнать нагрузочный тест;
  3. тесты на устойчивость: 4xx/5xx, некорректные токены, недоступность Аршина;
  4. демонстрация по сценарию приёмки из ТЗ (раздел 11.6).

Вывод: спроектированная клиент-серверная архитектура закрывает требования практики 1, подтверждена тестами и нагрузочными прогонами и работает в реальной эксплуатации.
