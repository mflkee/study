## 11.2 Назначение и цели создания системы

**Назначение.** Автоматизация учёта, поверки и ремонта средств измерений и эталонов
в метрологических службах и лабораториях: единый реестр оборудования, контроль сроков,
прозрачная история процессов, разграничение доступа между исполнителями и заказчиками.

**Цели создания:**

1. Централизовать учёт СИ/ЭСИ вместо разрозненных Excel-файлов по папкам и подразделениям.
2. Исключить просроченные поверки за счёт хранения дат поверки и срока действия свидетельства.
3. Автоматизировать получение сведений из ФГИС «Аршин»: поиск, импорт, пакетное обновление папки.
4. Обеспечить единую историю поверок и ремонтов с этапами, сроками и ответственными.
5. Разграничить доступ: заказчик видит только закреплённые за ним папки.
6. Снизить ручной труд при подготовке отчётов (дашборд, выгрузка XLSX).

**Критерии достижения целей:**

| Цель | Измеримый критерий |
|---|---|
| Единый реестр | все приборы компании в одной БД, иерархия «папка → группа → прибор» |
| Контроль сроков | у каждой карточки есть дата поверки и срок действия; просрочка видна в реестре |
| Интеграция с Аршином | поиск по свидетельству/рег. номеру и пакетное обновление папки работают без ручного ввода |
| История процессов | по каждому прибору доступны все поверки и ремонты с перепиской и вложениями |
| Разграничение доступа | пользователь без доступа к папке получает 404, а не данные |
| Отчётность | выгрузка реестра, очередей и журнала событий в XLSX |

## 11.3 Характеристика объектов автоматизации

**Объект автоматизации** — процессы учёта и обслуживания измерительного оборудования
метрологической службы:

- ведение реестра оборудования по объектам (папкам) и группам;
- постановка СИ на поверку, контроль этапов и сроков, получение свидетельств;
- заявка на ремонт, контроль маршрута и этапов, закрытие с результатом;
- сверка карточек с ФГИС «Аршин»;
- коммуникация исполнителей и заказчиков (комментарии, вложения, упоминания);
- подготовка отчётов и аудит действий.

**Участники процесса:**

| Роль | Код | Функции |
|---|---|---|
| Разработчик | `DEVELOPER` | техническая поддержка и диагностика, полный доступ |
| Администратор | `ADMINISTRATOR` | пользователи, роли, права по папкам, справочники, настройки |
| Сотрудник метрологической службы | `MKAIR` | ведение реестра, поверки и ремонты, переписка, отчёты по своей зоне |
| Заказчик | `CUSTOMER` | просмотр закреплённых папок, согласование, комментарии к своим приборам |

**Масштаб:** от нескольких единиц до нескольких десятков пользователей; единая база
на собственном сервере; несколько тысяч карточек оборудования.

**Особенности предметной области, влияющие на систему:**

- данные о поверках первичны во внешнем государственном реестре — система обязана
  работать и при его недоступности (кэш последних сведений);
- заводской номер не уникален: в Аршине один короткий номер может принадлежать десяткам
  приборов, поэтому автоматическое сопоставление требует участия оператора;
- сроки ремонта и поверки нормативно заданы и не должны «переписываться» задним числом;
- заказчик не должен видеть приборы других организаций (soft-denial через 404).

## 11.4 Требования к системе

### 11.4.1 Требования к системе в целом

**Архитектура.** Трёхуровневая клиент-серверная система:

1. **Клиент** — SPA на React 19 + TypeScript, собирается Vite, раздаётся nginx.
2. **Сервер приложений** — FastAPI (Python 3.12), REST API под префиксом `/api/v1`,
   бизнес-логика в сервисном слое, доступ к данным через SQLAlchemy 2.0.
3. **Хранилище** — PostgreSQL 16; Redis 7 + RQ для фоновых задач; файловое хранилище
   вложений на диске сервера.

**Режим работы:** круглосуточный, веб-доступ через браузер; обновление — контейнерами
Docker Compose с автоматическим применением миграций при старте.

**Требования к интеграции:** HTTP-интеграция с ФГИС «Аршин» (поиск и детализация по
свидетельству и регистрационному номеру), SMTP для email-уведомлений.

### 11.4.2 Требования к функциям (подсистемам)

| Подсистема | Состав функций |
|---|---|
| Аутентификация и профиль | вход по email/паролю, выдача токена, профиль, смена пароля, проверка SMTP |
| Пользователи и роли | CRUD пользователей, назначение роли, блокировка, временный пароль, скоуп папок |
| Реестр оборудования | папки, группы, карточки, типы СИ/ЭСИ/ИО/ВО/прочее, поиск, фильтры, сортировка, пагинация |
| Поверки | создание, режим проведения, этапы, сроки, переписка, групповые операции, закрытие |
| Ремонты | создание, маршрут, этапы, сроки, переписка, закрытие с результатом |
| Интеграция с Аршином | поиск, детализация, импорт, пакетное обновление папки, выбор записи при неоднозначном номере |
| Коммуникации | комментарии, вложения, приватные заметки, @упоминания, email-уведомления |
| Задачи | kanban-доска, участники и роли, чек-листы, сроки, напоминания, привязка к приборам |
| Отчётность и аудит | журнал событий, дашборд, экспорт XLSX, архивы вложений (ZIP) |
| Служебные функции | `/health`, `/health/ready`, OpenAPI-спецификация |

Детализация — в приложении А (F1–F17).

### 11.4.3 Требования к надёжности

- Сохранность данных: PostgreSQL с транзакциями, внешние ключи с политиками
  `CASCADE`/`SET NULL`, резервное копирование перед каждым развёртыванием.
- Версионирование схемы: 66 миграций Alembic, применение при старте контейнера.
- Отказоустойчивость фоновых задач: при недоступности Redis уведомление отправляется
  синхронно (fallback), задача не теряется молча.
- Health/ready-проверки: `/health` — живость процесса, `/health/ready` — доступность БД
  и Redis (при `NOTIFICATION_QUEUE_ENABLED=false` Redis не требуется).
- Восстановление после сбоя: контейнеры с `restart: unless-stopped`, идемпотентные
  миграции и повторные запуски пакетных операций.

### 11.4.4 Требования к безопасности

- Обязательная аутентификация для всех прикладных эндпоинтов, кроме `/health*` и `/auth/login`.
- Пароли — только в виде хеша PBKDF2-HMAC-SHA256 (600 000 итераций, соль 16 байт).
- Токен доступа — stateless HMAC-SHA256, подписанный секретным ключом; сервер не хранит сессии.
- Ролевая модель: `DEVELOPER`, `ADMINISTRATOR`, `MKAIR`, `CUSTOMER`.
- Дополнительное ограничение по папкам: белый список разрешённых и чёрный список скрытых папок.
- **Soft-denial:** при отсутствии доступа к объекту возвращается `404`, чтобы не раскрывать
  факт его существования.
- Проверка активности пользователя на каждом запросе (блокировка действует немедленно).
- Передача данных по HTTPS (TLS terminates на периметре), CORS ограничен списком origin.
- Загрузка файлов: ограничение размера (25 МБ), сжатие изображений, хранение вне web-root,
  выдача только через авторизованный эндпоинт.

### 11.4.5 Требования к эргономике и технической эстетике

- Веб-интерфейс на русском языке, адаптивная вёрстка, тёмная и светлая темы.
- Единые паттерны: таблицы с пагинацией, диалоги подтверждения, индикаторы загрузки.
- Ошибки формулируются для пользователя, а не кодом HTTP.

### 11.4.6 Требования к эксплуатации, техническому обслуживанию и ремонту

- Развёртывание: Docker Compose (postgres, redis, backend, backend-worker, frontend).
- Обновление: сборка образов в CI, публикация в GHCR, перезапуск на сервере.
- Резервное копирование БД — `pg_dump` перед деплоем, хранение в каталоге резервных копий.
- Мониторинг — внешняя проверка `/api/v1/health/ready`.

### 11.4.7 Требования к персоналу

- Администратор: навыки управления пользователями и правами, понимание структуры папок.
- Пользователь: базовые навыки работы в браузере. Специальной подготовки не требуется.
- Разработчик: Python/FastAPI/SQLAlchemy, React/TypeScript, Docker.

### 11.4.8 Требования к защите информации от несанкционированного доступа

- Разграничение доступа на уровне API, а не только интерфейса.
- Приватные комментарии и сообщения видны только автору и администраторам.
- Журнал событий фиксирует действия пользователей по оборудованию, поверкам, ремонтам, задачам.
- Секреты (пароль БД, SMTP, секрет подписи токенов) — в переменных окружения, не в репозитории.

| Пагинация списков | обязательна для реестра, очередей, событий, задач |
| Тяжёлые операции | выносятся в фон (RQ) или `BackgroundTasks` |

**Б.4 Масштабируемость**

- горизонтальное масштабирование backend (несколько uvicorn-воркеров/контейнеров);
- очередь Redis позволяет добавить воркеров без изменения API;
- stateless-аутентификация не требует sticky sessions.

**Б.5 Совместимость**

- браузеры: Chrome/Chromium, Firefox, Safari (две последние версии);
- СУБД: PostgreSQL 16 (допустимо 14+);
- ОС сервера: Linux; развёртывание в Docker.

**Б.6 Ограничения**

- фиксированный стек: Python/FastAPI/PostgreSQL/React;
- размещение преимущественно на собственном сервере;
- правовые: обработка персональных данных пользователей (152-ФЗ), публичные данные ФГИС «Аршин»;
- мобильное приложение не предусмотрено (адаптивный веб-клиент).

**Б.7 Требования к коду и сопровождению**

- линтеры: `ruff` (backend), `eslint` (frontend), `mypy` (типизация);
- тесты запускаются в CI до сборки образов;
- миграции только через Alembic, ручные правки схемы на проде запрещены;
- версия приложения — единый источник в `frontend/package.json` и корневом `package.json`.
