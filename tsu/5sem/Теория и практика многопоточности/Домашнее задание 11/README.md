## 2. Этапы выполнения

### Этап 1. Набор данных

Генератор с зерном выдаёт одинаковый набор при одинаковом зерне, поэтому замеры и ответ счётчика
воспроизводимы. Заголовки и города берутся из фиксированных массивов, зарплата — 40 000…250 000 ₽,
15 % вакансий удалённые. Фактически: **1 000 000 записей за 400.5 мс**.

Почему набор большой: на десятках и тысячах записей рекурсивное разбиение только добавляет накладные
расходы, и сравнивать параллельный подсчёт с последовательным бессмысленно. Проверка соответствия
критерию включает нормализацию заголовка (нижний регистр, удаление пунктуации) — это та же операция,
что делал конвейер ДЗ 10; без неё миллион записей считается быстрее, чем создаются задачи.

### Этап 3. Рекурсивная задача и разбиение на партии

`BatchCountTask` — `RecursiveTask<CountResult>` с диапазоном `[from, to)`, критерием и размером партии.

- Если диапазон не больше партии — это **лист**: он считает свои записи последовательно, а
  `CounterStats` фиксирует партию.
- Иначе диапазон делится на две части **по границе партий**: `mid = from + (партий слева) * batchSize`.
  Левая половина уходит в `fork()`, правая считается в текущем потоке (`compute()`), затем результаты
  складываются `join()`-ом. Так дерево задач остаётся сбалансированным, а листьев ровно
  `ceil(size / batchSize)`.

Почему не «делить пополам по индексу»: при `size = 1000`, `batchSize = 300` деление пополам даёт
листья 250/250/500, и обещание «каждая пачка — новая задача» перестаёт быть проверяемым. При
выравнивании по партиям для тех же чисел листья — 300/300/300/100, а их число равно `ceil(1000/300) = 4`.
Тест проверяет это равенство для разных размеров и партий.

## 5. Почему выравнивание по партиям и почему пул свой

- **Проверяемость разбиения.** При делении «пополам по индексу» листья получаются произвольного
  размера, и нельзя утверждать ни «каждая пачка — новая задача фиксированного размера», ни точное
  число партий. Выравнивание по границе партии делает число листьев предсказуемым
  (`ceil(size / batchSize)`) и проверяемым тестом.
- **Нет общего состояния.** Задача хранит только `final`-поля и общий атомарный счётчик статистики,
  поэтому «украденная» подзадача корректно считается тем потоком, который её выполнил.
- **Ассоциативное сложение.** `CountResult.plus` ассоциативен и коммутативен, поэтому порядок
  завершения подзадач на ответ не влияет — это обязательное условие корректности Fork/Join.
- **Свой пул.** `ForkJoinPool.commonPool()` общий для всего приложения: на его числа влияет чужая
  нагрузка, а размер не является параметром эксперимента. Здесь пул создаётся с явным параллелизмом и
  именованными потоками `hw11-forkjoin-N` и закрывается по завершении.
- **Демон-потоки** пула не мешают процессу завершиться даже при аварии, но пул всё равно закрывается
  явно (`close()` → `shutdown` → ожидание → при необходимости `shutdownNow`).
