# Design

## Context

Корневой каталог курса содержит только тексты заданий в `Домашнее задание N (дедлайн ...)/`, пустой `openspec/` и `lesson1/HelloWorld.java`. Кода приложения нет, системы сборки нет, README нет. См. `proposal.md` — Why.

Ограничения, заданные средой и проверенные на машине:

- JDK 26 установлен, Gradle отсутствует, Maven 3.9 присутствует → сборка только на Maven.
- Требование текста ДЗ 1 — «создать каркас проекта на Spring Boot», поэтому отказ от фреймворка недопустим.
- Итоговое ДЗ потребует переиспользовать этот же код, значит структура должна быть расширяемой, а не одноразовой.
- Spring Boot 4.1.1 — актуальная стабильная версия (проверено по Maven Central).

Соглашения по структуре и запуску зафиксированы в `openspec/config.yaml` → `context`, здесь они не дублируются.

## Goals / Non-Goals

**Goals:**

- Дать рабочий Spring Boot-каркас, который переиспользуется ДЗ 2–8 и Итоговым ДЗ без переписывания.
- Показать оба способа создания потока настолько явно, чтобы это читалось в отчёте как отдельные пункты чек-листа.
- Ввести единый механизм изолированного запуска демо, пригодный для ДЗ с зависанием (ДЗ 7) и бенчмарков (ДЗ 3).
- Разложить вывод так, чтобы его можно было дословно приложить к отчёту.

**Non-Goals:**

- Наполнять домен парсера вакансий, H2, `@Scheduled`, REST-эндпоинты — это Итоговое ДЗ.
- Строить полноценный фреймворк запуска демо с параметризацией — хватает одного свойства.
- Оптимизировать производительность или вводить JMH — на уровне ДЗ 1 достаточно замеров по чек-листу.

## Decisions

### D1. Единый Maven-проект в каталоге `app/`, а не pom в корне курса

**Выбор:** `app/pom.xml` с модулями `ru.tsu.tpm.vacancyparser.hw01..hw08`.

**Почему:** корень курса — это учебный каталог со смесью текстов заданий, `openspec/` и будущих отчётов. Помещение `pom.xml` в корень заставило бы Maven сканировать всё дерево, а каталоги с пробелами и кириллицей в именах («Домашнее задание 1 (дедлайн 09.09.2026)») — плохая территория для сборки. Отдельный `app/` отделяет код от текстов заданий и отчётов.

**Альтернативы:** (а) `pom.xml` в корне — отклонено по причинам выше; (б) 8 независимых проектов — отклонено, потребовало бы строить каркас заново для Итогового ДЗ и разошлось бы с требованием «итогового приложения»; (в) Gradle — отклонено, не установлен.

**Уточнение при реализации:** в корне курса всё же создан агрегирующий `pom.xml` (`packaging: pom`, `<modules><module>app</module></modules>`). Он не является pom приложения и не тянет в сборку тексты заданий — Maven собирает только явно объявленный модуль. Нужен потому, что спецификация и все команды проекта используют вид `mvn -pl app ...` из корня курса, а без агрегатора `-pl app` не резолвится (нечего выбирать из reactor'а). Альтернатива — переписать все команды на `mvn -f app/pom.xml ...`; отклонена, так как затрагивает спецификацию, `config.yaml` и артефакты всех восьми ДЗ.

### D2. Компиляция под `--release 21` при JDK 26 в runtime

**Выбор:** `<maven.compiler.release>21</maven.compiler.release>`, Spring Boot 4.1.1.

**Почему:** установленный JDK 26 — bleeding edge, а Spring Framework 4.1 внутри Boot официально ориентирован на JDK 17–25. Компиляция под 21 даёт доступ ко всем нужным языковым возможностям (records, sealed, switch-выражения, text blocks) и одновременно страхует от несовместимости Tomcat/Spring на 26-м JDK.

**Альтернативы:** (а) `<release>26</release>` — отклонено из-за риска несовместимости, который проявился бы только в рантайме; (б) установка JDK 21 — отклонено, лишнее изменение окружения.

**Риск:** при несовместимости — понижать до `--release 17`, а не менять Boot.

**Проверено при реализации (задача 1.2):** сборка `mvn -pl app package` на JDK 26 проходит успешно с Boot 4.1.1 и `--release 21`; байт-код в jar имеет major version 65 (Java 21). Понижение до 17 не потребовалось.

### D3. Запуск демо через `ApplicationRunner` + `@ConditionalOnProperty("app.hw")`

**Выбор:** каждый пакет `hwNN` содержит `@Component implements ApplicationRunner` с `@ConditionalOnProperty(name = "app.hw", havingValue = "hwNN")`.

**Почему:** задания требуют не «сервиса», а воспроизводимого запуска с осмысленным выводом в консоль — `main()`-классы обрывали бы контекст Spring и лишали бы доступа к бинам. `ApplicationRunner` выполняется после поднятия контекста (до старта HTTP-сервера в Boot 4), даёт доступ к DI и позволяет вызвать `System.exit` для ДЗ с зависанием. Условие по свойству гарантирует, что демо не запускается при обычном `mvn spring-boot:run` и что два демо никогда не выполняются одновременно.

**Альтернативы:** (а) `CommandLineRunner` — практически равноценно, выбран `ApplicationRunner` из-за порядка вызова относительно `@Scheduled`; (б) отдельные `main()` — отклонено, теряется Spring-контекст; (в) Spring Shell/профили — лишняя зависимость.

### D4. Пакет `common` сразу, начиная с ДЗ 1

**Выбор:** `ru.tsu.tpm.vacancyparser.common` создаётся в ДЗ 1 с консольным логированием и тайминг-хелперами, дальше наполняется по мере надобности.

**Почему:** ДЗ 3 (бенчмарки), ДЗ 6 (счётчики), ДЗ 7 (дамп потоков) и ДЗ 8 (сводка по HTTP) требуют одинаковых вещей — аккуратно размеченного вывода и замера времени. Заложив их сразу, избегаем дублирования и рефакторинга в середине курса.

**Альтернативы:** дублировать вывод в каждом ДЗ — отклонено, гарантированный технический долг.

### D5. Имена потоков — доменные, нумерация — через общий счётчик

**Выбор:** демонстрационные потоки создаются с доменными именами (`CounterWorker`, `LoggerThread`, …), порядковый номер берётся из общего `AtomicInteger`-счётчика на старте демо.

**Почему:** текст задания прямо требует понятных имён. Счётчик на `AtomicInteger` попутно демонстрирует атомарность — это подготовка к ДЗ 6, а не отдельная задача.

**Альтернативы:** полагаться на `Thread-N` — прямо нарушает требование; нумеровать вручную в каждом классе — отклонено, номера могут совпасть.

### D6. Отчёт — Markdown рядом с текстом задания

**Выбор:** `Домашнее задание 1 (дедлайн 09.09.2026)/README.md`.

**Почему:** текст задания и отчёт лежат рядом, отчёт легко найти и скопировать в Google/Яндекс документ. Конвенция зафиксирована в `config.yaml` и повторно используется ДЗ 2–8.

## Risks / Trade-offs

- **[Spring Boot 4.1.1 может оказаться несовместим с JDK 26 в рантайме]** → сборка идёт под `--release 21`; при падении первым делом понижать `release` до `17`, а не менять версию Boot. Проверяется задачей 1.2.
- **[`join()` в ДЗ 1 привлекает API из ДЗ 2 — «прыжок вперёд»]** → `join()` используется минимально, только чтобы дождаться завершения; отчёт по жизненному циклу остаётся за ДЗ 2.
- **[Вывод списка активных потоков внутри Spring Boot будет шумным из-за потоков Tomcat/GC]** → это ожидаемо и даже полезно; в отчёте отдельно выделяются потоки самого приложения от потоков контейнера, чтобы вывод читался.
- **[Двузначность JDK (26 vs release 21) при запуске через `spring-boot:run` и в IDE]** → целевой уровень задаётся в `pom.xml`; при расхождении версий в выводе IDE явно указывать `--release 21` в настройках компилятора.
