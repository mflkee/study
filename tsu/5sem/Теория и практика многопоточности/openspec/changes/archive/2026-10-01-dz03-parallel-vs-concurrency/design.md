# Design

## Context

См. `proposal.md` — Why. Здесь только то состояние проекта и ограничения, которые повлияли на технические решения.

Что уже есть после ДЗ 1–2 и важно для этого ДЗ:

- `app/` — единственный Maven-модуль, Spring Boot 4.1.x, `--release 21`, JUnit 5.
- Пакет `ru.tsu.tpm.vacancyparser.common` с консольным выводом и хелпером замера времени на `System.nanoTime()` — из ДЗ 1. Основа для измерителя, но это был хелпер «замерить один кусок кода», здесь нужна статистика по повторам.
- Из ДЗ 2 в проекте уже есть наблюдение потоков — она позволит **наблюдаемо** зафиксировать число потоков, реально задействованных `parallelStream()`, вместо того чтобы полагаться на формулу.

Технические факты, определившие решения:

- **`parallelStream()` не создаёт собственный пул.** Он использует `ForkJoinPool.commonPool()`. Его параллелизм равен `Runtime.getRuntime().availableProcessors() - 1` (при 1 процессоре — 1), потому что один поток должен остаться планировщиком. То есть на машине с N ядрами параллельный поток получает N-1 потоков. Отсюда прямое следствие: **результат зависит от машины**, и «parallel проиграл» на ноутбуке с 4 ядрами не противоречит «parallel выиграл» на сервере с 32 ядрами. Без фиксации числа процессоров любой вывод невоспроизводим.
- **Одиночный замер на JVM невалиден.** Первый вызов исполняется интерпретатором (или C1), дальше HotSpot компилирует метод в C2. Время падает на порядок после нескольких прогонов. Сравнивать «один замер sequential против одного замера parallel» бессмысленно: разница может быть целиком разницей стадии JIT, а не параллелизма.
- **Цена параллелизма не нулевая даже когда потоков много.** Форк задач, синхронизация счётчиков, проход по нескольким листам (leaves) и обратная сборка — всё это платится всегда. Для дешёвой операции над миллионом элементов (арифметика в цикле) выигрыш от разделения может не окупить эти расходы, особенно когда потоков всего 3.
- **Порог переключения на параллелизм зависит от стоимости задачи на элемент.** Для `Integer`-арифметики элемент очень дешёвый: накладные на элемент мизерны, и вся экономия — на перекрытии. Для операций с аллокациями и боковыми эффектами (сортировка по компаратору, сборка строк, вызовы в БД) картина иная.
- **Первый кадр `parallelStream()` может быть ложным.** Параллельный вариант на очень маленьком входе выполняется целиком в вызывающем потоке (`invoke()` без форка), и его «параллельность» — нулевая. На миллионе элементов этого эффекта уже нет, но при прогреве на малых выборках он искажает понимание.

## Goals / Non-Goals

**Goals:**

- Получить числа, на которые можно сослаться в отчёте, и которые не разъедутся при повторном запуске.
- Сделать вывод самодостаточным: чтобы по выводу было видно, **на чём** измерено, даже если читатель работает на другой машине.
- Донести до вывода сам вывод-анализ: если параллельный проиграл, причина должна называться в консоли, а не оставаться в голове автора.
- Не сломать вывод на машине с 1–2 ядрами: демо обязано отработать и там, где параллельность физически невозможна.
- Выделить переиспользуемое: измеритель с прогревом и повторами понадобится ДЗ 4–8 и Итоговому ДЗ.

**Non-Goals:**

- Строить честный микробенчмарк уровня JMH (отдельные JVM на итерацию, управление параллелизмом через `-Djava.util.concurrent.ForkJoinPool.common.parallelism`, черновые прогоны, статистика по доверительным интервалам). Задача — «измерить и проанализировать», а не «построить инструмент измерения».
- Вручную задавать размер пула через системное свойство. Это сделало бы измерение «удобным», но текст задания требует измерить именно `parallelStream()` — с его собственными настройками по умолчанию.
- Менять предмет измерения на «какой из двух вариантов быстрее на моей машине» без оговорки о машине — именно такая безоговорочность делает вывод нечестным.
- Оптимизировать сами операции (переписать фильтрацию на цикл, чтобы выиграть на скорости). Это лишило бы сравнение смысла: обе ветви должны быть одинаково «Stream API».
- Оперировать `Collection.parallelStream()` для всех трёх операций в агрегирующей ветке с ранним выходом — здесь нужны именно три указанные операции.

## Decisions

### D1. Один список генерируется один раз и переиспользуется обоими вариантами

**Выбор:** список из 1 000 000 случайных чисел создаётся один раз перед всеми измерениями; обе ветви (последовательная и параллельная) обрабатывают **этот же** список.

**Почему:** иначе сравниваются два разных набора данных, а время включает в себя стоимость генерации, и разница может объясняться разным составом данных (например, чётных чисел в двух выборках разное количество → разный объём работы при фильтрации). Переиспользование одного списка делает разницу времени объяснимой: вход одинаков, отличается только способ исполнения.

**Альтернативы:** (а) генерировать список отдельно для каждого замера — отклонено, добавляет к времени генерацию и делает выборки разными; (б) генерировать внутри измеряемого участка — отклонено, время генерации (~десятки мс) сравнялось бы со временем самой операции; (в) переиспользовать список между повторами — принято, это убирает генерацию из измеряемого интервала полностью.

### D2. Прогрев + несколько повторов + усреднение, одиночный замер невалиден

**Выбор:** для каждой измеряемой ветви выполняется прогрев (один прогон, не учитываемый в результате), затем `N` повторов (по умолчанию 5), из которых считается среднее арифметическое. Минимум и максимум повторов остаются доступными для сверки.

**Почему:** это прямое следствие того, что JIT компилирует метод по счётчику вызовов. Первый прогон измеряет интерпретацию, третий — часто уже C1, пятый-десятый — C2. Разница между этими стадиями легко перекрывает эффект от параллелизма, то есть одиночный замер может дать вывод, **противоположный** истинному. Прогрев сдвигает все повторы в область зрелой JIT, а усреднение гасит остаточный шум планировщика. Пять повторов — компромисс: меньше — заметен шум, больше — демо заметно удлиняется.

**Альтернативы:** (а) один замер — отклонено, методологически недействителен, именно его даёт «неверный вывод» из `proposal.md`; (б) брать минимальное время из повторов — отклонено как основной критерий: минимум хорош для отсечения внешних помех, но скрывает реальную стоимость; используется только как дополнительная сверка; (в) JMH — отклонено как отдельная зависимость ради одного задания, см. Non-Goals; (г) прогрев фиксированного числа раз (например, 20) — отклонено как избыточное: на операциях такого размера достаточно прогрева, покрывающего стадию C2, а лишние прогоны просто тратят время демо.

### D3. Замер по `System.nanoTime()` с вычислением интервала, а не «счётчик +1»

**Выбор:** замер — это разница двух значений `nanoTime()`: `start` перед ветвью, `end` после неё; результат переводится в миллисекунды.

**Почему:** `nanoTime()` монотонен и имеет наносекундное разрешение; системные часы могут быть переведены назад на длительности замера и дать отрицательное или завышенное значение. Кроме того, «замерить отдельный метод» — плохой интерфейс: он не позволяет включить в измеряемый интервал всё, что относится к операции, и не даёт получить **результат** операции (его же надо куда-то сложить). Разница вокруг тела lambda проще и не даёт JIT оптимизировать замер «в ноль».

**Альтернативы:** (а) `currentTimeMillis()` — отклонено, разрешение 1 мс и подвержен переводу часов; (б) отдельный «счётчик итераций» вместо времени — отклонено, задача требует именно времени; (в) `Duration`/`Instant.now()` — то же самое, но с лишними аллокациями.

### D4. Фактическое число потоков параллельного варианта наблюдается, а не вычисляется

**Выбор:** помило `Runtime.getRuntime().availableProcessors()`, в вывод попадает **наблюдаемое** число потоков, реально работавших при параллельном исполнении: имена потоков общего пула (`ForkJoinPool.commonPool-worker-N`) снимаются во время выполнения параллельной операции и агрегируются.

**Почему:** формула `availableProcessors() - 1` — это **намерение** реализации, а не факт. На реальной машине размер пула может быть иначе (учтены ограничения среды, фактическая загрузка ЦП, `commonPool-worker` может быть один даже при 8 ядрах, если часть занята). Если в отчёте написать «parallelStream использовал 7 потоков на 8-ядерной машине», а в выводе видно 3 — это ошибка. Наблюдение стоит дёшево: демо из ДЗ 2 уже умеет обходить потоки, нужен лишь фильтр по имени и снимок в момент работы. Это заодно делает вывод честным на машине с 1 ядром: там в выводе будет видно, что параллелизм фактически не состоялся, и это не нужно отдельно оговаривать в тексте.

**Альтернативы:** (а) только формула `availableProcessors() - 1` — отклонено, она декларативна и может расходиться с фактом; (б) управлять параллелизмом системным свойством и мерить «правильный» пул — отклонено, это уже не тот `parallelStream()`, который требует текст задания, и это ДЗ 8; (в) вообще не упоминать число потоков — отклонено, тогда вывод нельзя объяснить.

### D5. Размер общего пула выводится явно, вместе с предупреждением о воспроизводимости

**Выбор:** в блок условий замера выводятся: версия JVM, число доступных процессоров, размер `ForkJoinPool.commonPool()` (его параллелизм) и оговорка, что общий пул разделяется со всем процессом и его фактический параллелизм зависит от числа процессоров, доступных JVM.

**Почему:** текст задания требует не просто «кто быстрее», а анализ причин. Ключевая причина — в свойствах общего пула, и её нельзя назвать, не показав его размер. Оговорка о разделяемости нужна потому, что Spring Boot-приложение поднимает свои потоки (Tomcat, scheduler), и на реально нагруженной машине параллельный вариант конкурирует с ними — это часть честного вывода, а не неудобная деталь.

**Альтернативы:** (а) выводить только `availableProcessors()` — отклонено, не объясняет механизм; (б) молча проглотить факт общего пула — отклонено, это ровно то, что Итоговое ДЗ заставит заменить своим пулом; (в) измерять на отдельном пуле для чистоты — отклонено, см. Non-Goals и D8.

### D6. Три операции как единая измеряемая «ветвь», результат сохраняется

**Выбор:** каждая операция реализована так, что существует её последовательная и параллельная версия, возвращающие **одинаковый тип результата**. Результат каждого замера не выбрасывается, а сохраняется и используется для сверки (в вывод попадает, например, количество отобранных чётных элементов и сумма).

**Почему:** сохранение результата даёт сразу две вещи. Первое — **проверку корректности**: если параллельный и последовательный варианты разошлись по результату, замер бессмысленен, и это видно в выводе. Второе — защита от мёртвой оптимизации JIT: если результат вычисления не используется, HotSpot вправе выбросить сам цикл как «мёртвый код», и измеряемая операция станет пустой. Плюс это напрямую закрывает требование спеки «результат не зависит от варианта исполнения».

**Альтернативы:** (а) измерять цепочку `filter→map→sum` одним таймером — отклонено: текст задания требует измерить все три операции, и в цепочке нельзя понять, какая именно стоила дорого; (б) возвращать только время, результат не печатать — отклонено, теряется и проверка корректности, и защита от мёртвой оптимизации; (в) возвращать `Optional`/nullable для суммы — отклонено, сумма всегда есть.

### D7. Диапазон элементов выбран так, чтобы фильтрация давала предсказуемый результат

**Выбор:** случайные числа генерируются в диапазоне, где ровно половина — чётные (например, `0..2N-1`, где N = 1 000 000), либо фиксируется состав и печатается фактическое количество чётных.

**Почему:** из учебных соображений удобно предсказывать «половина отобранных элементов» — это позволяет в отчёте привести ожидаемый результат и сверить его с фактическим. Если числа произвольные, ожидаемое количество чётных неизвестно заранее, и сверка «правильный ли результат» становится слабее. Диапазон также влияет на время: `Integer` в пределах кэша/boxing-кэша ведёт себя иначе, чем большие значения.

**Альтернативы:** (а) `ThreadLocalRandom.nextInt()` без ограничения — отклонено, невозможно заранее сказать ожидаемый размер выборки; (б) фиксированное сид-генерируемое число — отклонено, «случайные числа» в тексте задания, а детерминированный seed и случайность — разные требования; (в) `Double`-значения — отклонено, задание о числах, а `Integer` даёт меньше накладных расходов на boxing.

### D8. Никакой подмены пула: измеряется ровно `parallelStream()` из текста задания

**Выбор:** параллельный вариант — это `list.parallelStream()` без обёртывания в собственный `ForkJoinPool`, без `CompletableFuture.supplyAsync` и без управления параллелизмом.

**Почему:** текст задания прямо требует сравнить `stream()` и `parallelStream()`. Подстановка своего пула дала бы более «красивые» цифры параллельной ветви, но измеряла бы уже другое — а именно собственный пул будет предметом ДЗ 8 и Итогового ДЗ. Здесь честно измеряется то поведение, которое имеет `parallelStream()` из коробки, включая его проигрыш на слабых ЦП.

**Альтернативы:** (а) `stream().parallel().submit(() -> ...)` — то же самое, отклонено как ложное усложнение; (б) задать `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N` — отклонено: меняет объект измерения и прячет свойство, которое как раз требуется объяснить; (в) измерить оба варианта и на своём пуле — отклонено, это ДЗ 8.

### D9. Анализ выводится в консоль, а не остаётся в отчёте

**Выбор:** после вывода таблицы времён печатается блок анализа: по каждой операции — кто быстрее, во сколько раз, и объяснение, привязанное к числу процессоров и размеру общего пула. Для проигрыша формулировка называет накладные расходы (форк задач, синхронизация счётчиков, обратная сборка) как причину, не окупаемую разделением работы; для выигрыша — что работа была разделена между потоками общего пула.

**Почему:** текст задания требует «проанализируйте, почему один метод работает быстрее другого **в конкретной ситуации**», и чек-лист — «проведён анализ причин различий». Если объяснение живёт только в README, его легко не заметить проверяющему, и демо выглядит как «просто напечатал миллисекунды». Печать причины рядом с цифрами делает демо самодостаточным, а отчёт — ссылкой на вывод.

**Альтернативы:** (а) только числа в консоли, анализ в отчёте — отклонено по причине выше; (б) условный текст «если parallel проиграл, то…» без привязки к фактам замера — отклонено, получится общая теория вместо разбора конкретной ситуации; (в) печатать вывод через `System.out.println` внутри lambda — отклонено, портит измеряемый интервал; анализ печатается после замера.

### D10. Замеры ограничены по времени, чтобы демо оставалось пригодным для запуска вручную

**Выбор:** фиксированное число повторов (5) и прогрев (1) на операцию; дополнительно замер «холодного» первого прогона выводится отдельной строкой как иллюстрация эффекта JIT, но не используется в сравнении.

**Почему:** конвенция из `openspec/config.yaml` → `apply` требует, чтобы демо сначала запускалось вручную, а вывод прикладывался в отчёт как есть. Значит, демо должно отрабатывать за разумное время. Итоговое число прогонов: 3 операции × 2 варианта × (1 прогрев + 5 повторов) = 36 прогонов плюс один холодный — на миллионе элементов это секунды, а не минуты. Холодный прогон выводится потому, что он **сам по себе является частью объяснения**: он наглядно показывает, почему одиночный замер недействителен.

**Альтернативы:** (а) 20+ повторов «для статистики» — отклонено, удлиняет ручной запуск демо; (б) фиксированное время замера вместо числа повторов — отклонено, для быстрых операций это либо слишком долго, либо слишком шумно; (в) не печатать холодный прогон — отклонено, теряется самый наглядный аргумент о JIT.

### D11. Размер списка и параметры замера выносятся в параметры демо с разумными значениями по умолчанию

**Выбор:** размер списка (по умолчанию 1 000 000), число повторов и длительность прогрева задаются параметрами демо с дефолтами, соответствующими тексту задания; фактические применённые значения печатаются в выводе.

**Почему:** текст требует ровно 1 000 000, но возможность уменьшить размер ради быстрой проверки сильно упрощает отладку демо (прогон 36 раз по миллиону при каждой правке — мучительно). При этом «1 000 000» остаётся значением по умолчанию, поэтому сдаваемый замер делается ровно на требуемом объёме, а напечатанные параметры не дают забыть, какой объём реально измерялся.

**Альтернативы:** (а) хардкод `1_000_000` без параметров — отклонено, отладка дорогая; (б) без дефолтов — отклонено, пришлось бы указывать все параметры при каждом запуске; (в) параметры извне через системные свойства — отклонено, лишняя обвязка для домашнего задания; достаточно Spring-конфигурации демо.

## Risks / Trade-offs

- **[Параллельный вариант выиграет на машине с 8–16 ядрами, и вывод «parallel лучше» окажется неверным для чужой машины]** → число процессоров, версия JVM, размер общего пула и наблюдаемое число потоков печатаются обязательно, а в отчёте формулировка вывода привязана к этим цифрам («на этой машине при N процессорах…»), а не выдаётся за универсальное правило. Это снимает главный риск задания — вывод, который нельзя воспроизвести.
- **[На машине с 1–2 ядрами параллельный вариант гарантированно проиграет, и это может выглядеть как «плохая реализация»]** → демо обязано корректно отработать в этом случае (сценарий спеки «на любом числе процессоров»), а в отчёте явно пишется, что проигрыш на слабом ЦП — ожидаемое и правильное поведение `parallelStream()`, а не ошибка кода; там же указывается наблюдаемое число потоков, подтверждающее, что параллелизм физически не состоялся.
- **[Остаточный шум планировщика превышает саму разницу времён]** → повторы с усреднением (D2), печать минимума и максимума для оценки разброса; в отчёте приводится разброс, и если разброс сопоставим с разницей между вариантами, это фиксируется как «значимой разницы не показано», а не натягивается вывод в пользу параллельности. Честный вывод «разница в пределах шума» допустим и корректен.
- **[JIT-оптимизация может исказить замер: либо выбросит «мёртвый» код, либо скомпилирует только одну ветвь]** → результат каждой операции сохраняется и печатается (D6), что исключает мёртвый код; ветви одинаково «тяжёлые» (одни и те же `filter`/`map`/`reduce`), поэтому обе попадают в одну и ту же стадию компиляции. Холодный прогон печатается отдельной строкой (D10) и в сравнение не идёт.
- **[Общий пул делится с потоками Spring Boot-контекста, из-за чего замеры «плавают» между запусками]** → это не чинится, а **фиксируется**: условия замера печатаются, а в отчёте оговаривается, что общий пул разделяем и в нагруженном процессе параллельный вариант конкурирует с потоками приложения. Управление собственным пулом сознательно отложено на ДЗ 8 (см. D8) — там же будет и повод сравнить.
- **[Полный перебор 36 прогонов удлиняет ручной запуск демо, который по конвенции нужно выполнить перед сдачей]** → числа прогонов фиксированы и умеренны (D10), а уменьшение размера списка параметром позволяет быстро прогнать демо на этапе отладки; на сдачу запускается с дефолтным объёмом 1 000 000.
- **[Печать большого объёма служебной информации (имена потоков, параметры JVM) делает вывод многословным и мешает читать таблицу времён]** → вывод разделён на блоки: условия замера → таблица результатов → анализ; имена потоков сводятся до числа, а не печатаются списком, чтобы таблица времён оставалась главным содержимым.
## Уточнения по факту реализации

Ниже — решения и находки, возникшие при применении изменения. Ни одно из них не сужает требования
спецификации.

### U1. Обе ветви прогреваются одинаково (найденный дефект методики)

Проход для наблюдения числа потоков (задача 3.3) изначально крутил только **параллельную** операцию.
JIT компилирует каждую ветвь отдельно по её счётчику вызовов, поэтому к началу измерений
`parallelStream()`-ветвь оказывалась прогретой, а `stream()`-ветвь получала только один прогревочный
прогон `Measurer`. Последовательный вариант выглядел медленнее не из-за отсутствия параллелизма, а
из-за недогретого кода — это прямо противоречило исходному риск-плану («обе ветви попадают в одну и
ту же стадию компиляции»).

**Решение:** проходы для наблюдения выполняют и параллельную, и последовательную операцию
(перегрузка `ParallelismProbe.observe(parallelPass, companionPass, passes)`). Перегрузка с одним
проходом оставлена только для проверок самого датчика. Эффект: разброс последовательной фильтрации
сузился с `12.8..22.1` до `10.8..11.6` мс, вердикт по преобразованию (ранее «мигал» между «в
пределах шума» и «быстрее в 4.08 раза») стал одинаковым во всех трёх запусках.

### U2. Ограничение процессоров для проверки на слабой машине — `taskset`, а не флаг JVM

Задача 7.3 предполагала ограничить доступные процессоры «запуском JVM» — то есть
`-XX:ActiveProcessorCount`. Проверка показала, что этот способ **не ограничивает реальную
параллельность**: флаг меняет только представление JVM о числе процессоров и размеры её пулов
(`availableProcessors` и `parallelism` честно становятся 1 и 1), но операционная система по-прежнему
выдаёт процессу все физические ядра. На прогоне с `-XX:ActiveProcessorCount=1` параллельный вариант
**выиграл** 2.10× на фильтрации — то есть проверка «на слабой машине» на самом деле измеряла
двенадцатиядерную машину.

**Решение:** проверка выполняется привязкой к ядру — `taskset -c 0`, где ограничение настоящее.
На одном ядре фильтрация выходит «в ноль» (1.02×, то есть одинаково), а агрегация **проигрывает**
0.74× (последовательный быстрее в 1.35×) — и демонстрация печатает ветку анализа проигрыша с числом
процессоров. Требуемое поведение (демо завершается с кодом 0, печатает результаты обоих вариантов и
объясняет проигрыш) подтверждено; изменён только способ создания условий.

Формулировка отчёта обязана это отметить: **вывод о числе процессоров нельзя делать по флагу JVM**,
иначе результат под настоящей параллельностью принимается за результат на слабой машине.

### U3. Замечание о разбросе не называет выдуманную причину

В замечании к неустойчивому замеру («разброс сравним с разницей средних») сначала была жёстко
названа причина — «паузы сборки мусора на аллокациях внутри операции». На одноядерном прогоне это
замечание попало под **фильтрацию**, которая ничего не аллоцирует, и причина оказалась просто
неверной.

**Решение:** замечание стало фактическим — приводится разброс и разница средних, перечисляются
возможные причины (внешние помехи, паузы сборки мусора, стадия компиляции JIT) и указывается, что
для вывода нужны повторы с меньшим разбросом. Диагноз не выдумывается: демонстрация не знает,
аллоцирует ли операция.

### U4. «Холодный» прогон не является нижней оценкой

Изначальная формулировка в выводе подавала холодный прогон как иллюстрацию того, что одиночный
замер «медленнее». На прогонах это подтвердилось не всегда: холодный прогон фильтрации выходил и
**быстрее** среднего (10.822 против 12.287 мс), когда среднее завышала пауза сборки мусора.

**Решение:** в отчёте холодный прогон приводится как доказательство того, что одиночный замер
непредставителен **в обе стороны**, а не как нижняя граница. Текст вывода оставлен нейтральным
(«показывает эффект JIT»), без утверждения направления.
