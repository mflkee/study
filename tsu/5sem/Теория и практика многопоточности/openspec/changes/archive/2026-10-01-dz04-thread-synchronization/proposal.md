# Proposal

## Why

ДЗ 4 (дедлайн 21.09.2026) — первый блок курса, где многопоточность перестаёт быть «просто запустить потоки»: требуется **взаимодействие потоков через общие данные** и защита от гонок данных. ДЗ 1–3 научили создавать, останавливать и замерять потоки, но не научили делать их работу корректной при одновременном доступе к общему состоянию. Без этого ни Итоговое ДЗ (параллельный сбор вакансий в общие структуры и счётчики), ни ДЗ 5 (`ReentrantLock`/`Condition`), ни ДЗ 8 (пул потоков) не имеют фундамента: любой из них упирается в корректность разделяемого состояния. Сейчас в `app/` есть только каркас и базовые примитивы из ДЗ 1–3 — синхронизации в проекте нет.

## What Changes

- Создаётся пакет `ru.tsu.tpm.vacancyparser.hw04.synchronization` с классом `DataCollector` — потокобезопасным сборщиком данных, хранящим общий список элементов, счётчик обработанных элементов и множество обработанных ключей.
- Реализуются методы `collectItem(Item)`, `incrementProcessed()`, `isAlreadyProcessed(String key)` с защитой от гонки данных; ключевой инвариант — под N потоками итоговый счётчик ровно N, дубликатов нет, `isAlreadyProcessed` не допускает двойной обработки одного ключа.
- Критические секции защищаются монитором объекта через `synchronized`-методы (по требованию п. 2 текста ДЗ — блокировка именно на методах).
- Реализуется связка `wait()` / `notify()` / `notifyAll()`: поток, которому нечего делать (данные не готовы), встаёт в ожидание и просыпается по сигналу при изменении разделяемого состояния; условие ожидания проверяется только в цикле `while`.
- Демонстрируется предотвращение deadlock: единый порядок захвата нескольких ресурсов плюс работа с тайм-аутом захвата, с явной ссылкой на то, что сама диагностика deadlock через `jstack` остаётся за ДЗ 7.
- Проводится нагрузочное тестирование несколькими потоками и сравнивается производительность синхронизированного и несинхронизированного вариантов — с измерением времени операций перевода между счетами.
- Демо запускается изолированно через `--app.hw=hw04`.
- Пишется отчёт `Домашнее задание 4 (дедлайн 21.09.2026)/README.md` по чек-листу самопроверки.

**Пункты чек-листа самопроверки текста ДЗ 4, которые закрывает это изменение:**

1. Реализована система `DataCollector` с поддержкой многопоточности.
2. Защищено от гонки данных с использованием синхронизации.
3. Применены методы `wait()`, `notify()`, `notifyAll()` для управления потоками.
4. Устранены проблемы deadlock.
5. Проведено тестирование на корректность работы многопоточных операций.
6. Составлен отчёт с описанием каждого этапа выполнения задания.
7. Ссылка на отчёт прикреплена в личном кабинете — **пункт 7 закрывается вручную студентом**, в код и тесты он не переводится (конвенция из `openspec/config.yaml`).

## Capabilities

### New Capabilities
- `dz04-synchronized-coordination`: потокобезопасное разделяемое состояние на мониторе объекта — сбор и учёт элементов без гонок данных, кооперация потоков через `wait()`/`notify()`/`notifyAll()`, предотвращение взаимных блокировок и измерение влияния синхронизации на производительность.

### Modified Capabilities

_Пусто — это первое изменение, задающее контракт синхронизации; существующих спецификаций в проекте нет (`openspec/specs/` пуст)._

## Impact

- **Новый код**: `app/src/main/java/ru/tsu/tpm/vacancyparser/hw04/synchronization/**` — `DataCollector`, `Item`, доменный тип «счёт/перевод», сервис нагрузочного теста, `ThreadSynchronizationDemo` (`ApplicationRunner` с `@ConditionalOnProperty(name = "app.hw", havingValue = "hw04")`); `app/src/test/java/ru/tsu/tpm/vacancyparser/hw04/synchronization/**` — юнит-тесты на инварианты и на взаимодействие потоков.
- **Новые зависимости**: нет — используются только `synchronized`, `wait()`, `notify()`, `notifyAll()`, `java.util.concurrent.locks` (`tryLock` с тайм-аутом) и JUnit 5, уже подключённые в `app/pom.xml` ДЗ 1.
- **Новый артефакт**: `Домашнее задание 4 (дедлайн 21.09.2026)/README.md`.
- **Связь с соседними ДЗ**: ДЗ 5 (`ReentrantLock`/`Condition`) строит `BoundedBuffer` как более гибкую замену монитору и явно сравнивается с решением этого ДЗ — здесь фиксируется «базовая линия» на `synchronized`. ДЗ 6 (`volatile`/атомарные переменные) продолжает тему безопасной публикации и объясняет, почему одного `volatile` для счётчика недостаточно — контракт инварианта счётчика, заданный здесь, становится эталоном для сравнения. ДЗ 7 (`deadlock`/`livelock`/`starvation`) не дублируется: здесь только предотвращение через порядок захвата и тайм-ауты, там — намеренное воспроизведение и диагностика через `jstack`.
- **Совместно используемая инфраструктура**: пакет `ru.tsu.tpm.vacancyparser.common` из ДЗ 1 (консольный вывод, замер времени на `System.nanoTime()`) расширяется, а не дублируется в `hw04`.
- **Вне scope**: H2/JPA и домен парсера вакансий (Итоговое ДЗ, дедлайн 08.11.2026); `ReentrantLock`/`Condition`/`Semaphore` (ДЗ 5); `volatile`/`AtomicInteger`/`AtomicReference` (ДЗ 6); собственный `ExecutorService` (ДЗ 8).
