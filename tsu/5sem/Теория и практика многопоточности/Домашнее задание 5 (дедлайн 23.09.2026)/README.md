## 2. Этапы выполнения

### Этап 1. Потокобезопасный буфер на `ReentrantLock` и `Condition`

`BoundedBuffer<T>` хранит элементы в `ArrayDeque` (FIFO), ёмкость задаётся при создании и
проверяется: значение меньше единицы отвергается исключением аргумента, а не даёт нерабочий объект.

Доступ защищён явной блокировкой, и каждая операция построена по одной схеме:

```java
lock.lock();
try {
    // ожидание и работа с состоянием
} finally {
    lock.unlock();
}
```

### Этап 2. Явный захват и освобождение: `lock()` / `unlock()`

У монитора синхронизация неявна — забыть её нельзя. Явная блокировка такой защиты не даёт: любой
`return` или исключение на пути выхода оставит её захваченной, и буфер станет мёртвым до перезапуска
процесса. Поэтому `unlock()` стоит в `finally` **во всех** операциях, включая ветви с ожиданием,
тайм-аутом и прерыванием. Проверяется это поведением: после отказа внутри критической секции
(`LockReleaseTest`) следующая операция завершается, а не виснет.

### Этап 3. Два условия ожидания и оповещение по назначению

`condition-not-full`, `condition-not-empty`. Ожидание — только в цикле, с ограничением по времени:

```java
while (storage.size() == capacity && !closed) {
    long remaining = deadline - System.nanoTime();
    if (remaining <= 0) {
        return false;
    }
    awaitOn(notFull, remaining);
}
```

Оповещение адресное: добавленный элемент будит ожидающих **извлечения**, освободившееся место —
ожидающих **добавления**. При завершении работы применяется `signalAll()`: состояние изменилось для
всех ожидающих сразу, и у события нет одного адресата.

### Этап 4. Producer'ы и consumer'ы

Задачи `BufferProducer` и `BufferConsumer` запускаются по общему затвору старта (иначе нагрузка была
бы последовательной) и дожидаются завершения: сначала producer'ы, затем буфер закрывается, и
consumer'ы выходят по признаку закрытия. Все извлечённые элементы сохраняются — по ним проверяются
инварианты и распределение по потокам.

### Этап 5. Тестирование и производительность

Основной инвариант проверяется на ёмкости **1** (максимальное переключение состояний «пуст» ↔ «полон»)
и повторяется десять раз. Отдельно — «красный» прогон на заведомо неверной реализации, чтобы
убедиться в чувствительности теста. Затем — сравнение с мониторным эквивалентом на одинаковой
нагрузке, 5 замеров каждого механизма.

## 4. Объяснение применённых механизмов

### 4.1. Почему явный `lock()`/`unlock()` вместо монитора

Монитор проще и безопаснее по умолчанию: синхронизация неявна, снять её забыть нельзя, `try/finally`
не нужен. Явная блокировка этой защиты лишена — зато даёт то, чего у монитора нет:

```java
lock.lock();
try {
    // ...
} finally {
    lock.unlock();
}
```

Что именно даёт явная форма (и что видно в выводе): **два независимых условия** и **тайм-аут
ожидания**. Фактическая цена такой гибкости — дисциплина: `unlock()` обязан стоять на каждом пути
выхода, и проверяется это в `LockReleaseTest` (после отказа внутри секции буфер остаётся живым).

### 4.2. Почему условий **два**, и что ломается при одном

У монитора **одно** множество ожидающих. Разбудить «правильного» ожидающего на нём нельзя: остаётся
`notifyAll()`, который будит всех, и каждая сторона просыпается, чтобы перепроверить своё условие — а
если оно ложно, заснуть снова. Это не теория, а измеренная величина в выводе демонстрации:

```text
    два условия: после одного take освободилось ОДНО место → прошёл 1 из 3 ожидающих producer'ов, впустую проснулись: 0
    одно условие (монитор): после одного take проснулись все 3 ожидающих, впустую проснулись: 2
```

Что ломается при одном условии, если заменить `notifyAll()` на `notify()`: сигнал достаётся
**произвольному** ожидающему, а не тому, чьё условие стало истинным. Ожидающего добавления может
разбудить добавление, и он заснёт снова, а ожидающий извлечения не получит сигнала — при переполнении
буфера прогресс останавливается. Это проверено «красным» прогоном: реализация, которая после
добавления оповещает условие добавления вместо условия извлечения, **не проходит** инвариантный тест
(`SensitivityTest`), а корректная с тем же прогоном проходит.

То, что `signal()` действительно адресный, видно по числу: один освободившийся слот разбудил **одного**
ожидающего добавления, и он единственный продолжил работу — при трёх ждущих.

### 4.3. Почему проверка условия идёт в цикле `while`

```java
while (storage.size() == capacity && !closed) {
    awaitOn(notFull, remaining);
}
```

`await()` возвращает управление без гарантии, что условие стало истинным. Причины те же, что и в ДЗ 4
для `wait()`, и не зависят от типа блокировки:

- **окно между проверкой и засыпанием**: `await()` атомарно отпускает блокировку и только потом
  паркует поток; в этот момент состояние может измениться, и сигнал уйдёт в пустоту;
- **пробуждение «не от того события»**: уведомление не говорит, какое условие стало истинным, поэтому
  проснувшийся обязан перепроверить своё.

Со `if` это классический lost wakeup: поток просыпается один раз, не находит условия и продолжает
работу так, будто ожидание завершилось успешно. Статическая проверка по исходникам (задание просит
привести найденные совпадения):

```bash
grep -rn "if.*await(" app/src/main/java/ru/tsu/tpm/vacancyparser/hw05 app/src/test/java/ru/tsu/tpm/vacancyparser/hw05
grep -rn "if.*wait("  app/src/main/java/ru/tsu/tpm/vacancyparser/hw05 app/src/test/java/ru/tsu/tpm/vacancyparser/hw05
```

Обе команды дают **ноль совпадений**. Для `wait()` это было не так сразу: хелпер ожидания в
`MonitorBuffer` назывался `await(...)`, и строка `if (!awaitOn(remaining))` (проверка **результата**
ожидания, а не ожидание под `if`) попадала в вывод первой команды ложным срабатыванием. Хелпер
переименован в `awaitOn` — так же, как в `BoundedBuffer`, — чтобы проверка читалась однозначно: сам
`wait()` вызывается только изнутри него, а он — только из цикла `while`.

### 4.4. Блокировка отпускается до `await()`

Её отпускает сам `await()` — атомарно, вместе с переходом в ожидание. Это единственная причина, по
которой буфер работает при ёмкости 1: пока producer ждёт места, consumer обязан иметь возможность
взять блокировку и забрать элемент. В выводе это видно на этапе 2, а в тестах проверено отдельно:
ожидающий добавления с заполненным буфером не мешает извлечению (`ConditionsTest.waitingReleasesTheLock`).

Обратная ошибка — обернуть ожидание во внешнюю блокировку или захватить блокировку после `await()` —
приводит к тому, что буфер блокируется намертво: единственная блокировка занята ожидающим.

## 5. `signal()` против `signalAll()`: когда что и чем оборачивается ошибка

| Ситуация | Что применять | Почему |
|---|---|---|
| Добавлен один элемент | `signal()` | Работу может получить **один** ожидающий извлечения |
| Освободилось одно место | `signal()` | Работу может получить **один** ожидающий добавления |
| Работа окончена, буфер закрывается | `signalAll()` | Состояние изменилось **для всех** ожидающих; адресата нет |

Ошибка выбора в любую сторону измерима:

- **`signalAll()` на горячем пути** — платит лишними пробуждениями. Фактическое измерение из этапа 3:
  после одного `take()` с одним условием проснулись все 3 ожидающих, **2 из них впустую**; с двумя
  условиями — **0**. Нагрузочный прогон этапа 1 (8000 элементов, ёмкость 1) даёт то же расхождение на
  длинной дистанции.
- **`signal()` вместо `signalAll()` при завершении** — теряет сигнал: часть ожидающих не узнает, что
  работа окончена, и останется в ожидании. Поэтому `close()` оповещает оба условия через `signalAll()`,
  и в выводе видно, что из ожидания вышли **все 4** потребителя, а не один: `после close() вышли из
  ожидания и завершились: 4 из 4`.

Отдельно стоит отметить ограничение, которое видно в тестах: `signal()` адресный **по условию**, а не
**по потоку**. Если на одном условии ждут несколько потоков, сигнал достанется произвольному из них;
гарантий «именно этот поток проснётся» нет. В `InterruptHandlingTest` из-за этого приходится сначала
дождаться полного выхода прерванного потока из очереди ожидающих, и только потом класть элемент —
иначе сигнал достаётся уходящему потоку, а не выжившему.

## 6. Обработка прерывания

Три ошибки, каждая из которых реальна, и все три закрыты:

1. **Забыть `unlock()` при прерывании.** `await()` — единственное место, где блокировка захвачена и
   может быть не отпущена: исключение выходит наружу, и без `finally` блокировка остаётся захваченной
   навсегда. Проверено: после прерывания буфер пригоден (см. ниже).
2. **Проглотить `InterruptedException`.** Поймать и продолжить — значит сбросить признак прерывания, и
   поток, который обязан завершиться, продолжит работу.
3. **Восстановить признак до повторного входа в ожидание.** При выставленном признаке следующий
   `await()` прервётся немедленно, и поток закрутится в бесконечном прерывании вместо ожидания.
   Поэтому признак восстанавливается **после** выхода из ожидания, и работа на этом завершается.

Фактический вывод этапа 5:

```text
    прерванный producer завершился: жив = false, причина остановки: ожидание прервано
    признак прерывания восстановлен: true
    буфер после прерывания пригоден: размер = 1, извлекается «заполнил»
```

Проверяется и обратное: `InterruptFlagPreservedTest` (роль которого играет
`InterruptHandlingTest.interruptFlagIsPreserved`) **упал бы**, если бы обработчик вернул управление без
восстановления признака — тест читает `Thread.currentThread().isInterrupted()` сразу после отказа и
требует `true`.

| `ReentrantLock + Condition`, среднее | 26.495 | 32.403 | 32.385 |
| `synchronized + wait/notify`, среднее | 34.908 | 30.239 | 28.359 |
| Вывод о разнице | в разбросе | в разбросе | в разбросе |

Полные значения прогонов канонического запуска (все пять, а не только лучший):

| Механизм | Прогоны, мс | Среднее | Минимум | Максимум |
|---|---|---|---|---|
| `ReentrantLock + Condition` | 39.027 / 27.600 / 19.005 / 23.847 / 22.998 | 26.495 | 19.005 | 39.027 |
| `synchronized + wait/notify` | 33.386 / 29.813 / 24.706 / 42.520 / 44.118 | 34.908 | 24.706 | 44.118 |

**Вывод по времени:** интервалы `[19.005, 39.027]` и `[24.706, 44.118]` пересекаются, поэтому
демонстрация печатает «разница укладывается в разброс повторов, то есть по времени они равноценны».
Так же и в двух других прогонах. Это честный результат: **по времени выполнения оба механизма
равноценны** — выполняется одна и та же работа, и накладные расходы на синхронизацию теряются в
разбросе от планировщика. Различаются они не скоростью, а тем, что позволяют выразить (см. раздел 8),
и числом впустых пробуждений (0 против 2 на коротком сценарии).

## 8. Выводы о преимуществах и недостатках явной блокировки

Каждый вывод опирается на измерение или пример из вывода.

**Явная блокировка `ReentrantLock` + `Condition` выигрывает там, где нужна выразительность:**

- **несколько независимых условий.** Два условия дают **0** впустых пробуждений против **2** у
  монитора на одном и том же событии — и это именно то, чего на мониторе сделать нельзя в принципе;
- **тайм-аут и попытка без ожидания.** `offer(item, 150 мс)` на заполненном буфере возвращает `false`
  за отведённое время; у `synchronized` такой возможности нет вовсе;
- **равномерное распределение работы.** Адресное оповещение обслуживает ожидающих по очереди: 1999 /
  2000 / 2000 / 2001 против наблюдённого у монитора `[694, 0, 138, 1168]`;
- **предсказуемая обработка прерывания.** Явная точка `await()` и явный `finally` делают политику
  видимой: прерывание прекращает операцию, признак восстанавливается, буфер остаётся живым.

**Недостатки явной блокировки:**

- **дисциплина вместо гарантии.** Забытый `unlock()` — мёртвый буфер, и компилятор об этом не скажет.
  У монитора такая ошибка невозможна; это его главное достоинство;
- **больше кода на ту же работу**: `lock`/`try`/`finally` вокруг каждой операции вместо одного слова
  `synchronized`;
- **по времени выигрыша нет.** Измерено: 26.495 мс против 34.908 мс при перекрывающихся интервалах —
  равноценно. Заявления вида «`ReentrantLock` быстрее» этим замером не подтверждаются.

**Где монитор остаётся предпочтительнее** (и это тоже вывод, а не уступка):

- **одно условие ожидания** — буфер целиком или счётчик из ДЗ 4: `synchronized`-метод короче и не
  оставляет места для ошибки с освобождением;
- **короткие критические секции без ожидания** — защита счётчика, множества ключей, пары балансов
  (ровно то, что делает `DataCollector` из ДЗ 4): гибкость `Condition` там не нужна и не окупается;
- **когда важнее всего «нельзя забыть»** — синхронизация неявна и снимается при выходе из метода, в
  том числе при исключении.

**Связь с ДЗ 4.** Мониторный эквивалент (`MonitorBuffer`) написан намеренно: он проходит **тот же**
набор инвариантных проверок и даёт **тот же** результат по извлечённым элементам, отличается только
механизм. Без этой базы сравнение производительности было бы сравнением с самим собой.

## 9. Наблюдение о `Semaphore` из темы задания

Тема задания — «Блокировка доступа к ресурсам. **Semaphore**, ReentrantLock и Condition», но
`Semaphore` не упоминается ни в описании работ (пункты 1–5), ни в чек-листе самопроверки: из шести
проверяемых позиций ни одна к нему не относится. Поэтому он здесь **не реализован** — не из
небрежности, а потому что вводить код вне критериев задания значит размывать отчёт и рисковать без
выигрыша в оценке.

Где семафор действительно понадобился бы — и понадобится в этом курсе:

- **ДЗ 8 и Итоговое ДЗ**: ограничение числа одновременно работающих потоков при обращении к внешним
  ресурсам (HTTP, база). Семафор с permits = N — прямой инструмент; условие «не больше N одновременно»
  через `Condition` пришлось бы писать руками;
- **пул соединений/задач** — классический счётчик разрешений;
- **там, где нужно ограничить не доступ к данным, а параллелизм операции**, — а именно этой задачи в
  ДЗ 5 нет: здесь ограничивается объём буфера, а не число работающих потоков.

### Примечание о числах и о двух дефектах, найденных по ходу

Все времена и значения счётчиков — **фактические**, полученные запусками на этой машине (OpenJDK 27,
4 producer'а и 4 consumer'а). На другом оборудовании числа будут другими: поэтому в вывод попадают
число потоков, ёмкость и число элементов, а выводы сформулированы как «на этой машине».

Два дефекта, которые нашлись уже после того, как код заработал:

1. **Счётчик впустую проснувшихся считал успешные пробуждения.** Инкремент стоял до повторной проверки
   условия, поэтому адресный сигнал, разбудивший именно того, кому стало доступно место, тоже
   засчитывался как «впустую» — в демонстрации выходило `1` там, где правильно `0`. Дефект был виден
   только в выводе демонстрации (тесты его не ловили, потому что не проверяли числа). Исправлено:
   пробуждение считается пустым, только если условие **после** него всё ещё ложно. Сейчас вывод даёт
   `0` против `2` — то есть ровно то различие, ради которого два условия и вводятся.
2. **Нестабильный тест в ДЗ 2.** При прогоне всей сборки под нагрузкой иногда падал
   `LifecycleObservationServiceTest.repeatedRunsProduceIdenticalStateSets`: запас в 400 мс на сон был
   слишком мал, и наблюдатель не успевал застать `TIMED_WAITING`. Это дефект теста, а не кода; запас
   увеличен (1.2 с сна, 4 с на фазу), после чего шесть прогонов подряд дают 269 тестов без падений.
