## Что подготовлено

Пакет `hw14.loom` — четыре этапа демонстрации и отчёт с фактическими замерами:

1. **Виртуальные потоки базово.** 200 страниц вакансий с локального сайта-заглушки грузятся
   синхронным HTTP, каждая — в своём виртуальном потоке
   (`Thread.ofVirtual().name("hw14-vt-", 0)` + `Executors.newThreadPerTaskExecutor`). В журнале
   видно имя потока и его carrier (`ForkJoinPool-1-worker-N`), а `Thread.isVirtual()` подтверждает,
   что поток действительно виртуальный.
2. **Сравнение с платформенным пулом.** Тот же объём работы через `newFixedThreadPool(16)`:
   **738.5 мс против 131.1 мс** у виртуальных потоков (в 5.6 раза быстрее), пик одновременных задач
   16 против 200, потоков ОС +16 против +0.
3. **Pinning.** Одинаковые блокирующие операции под `synchronized` и `ReentrantLock`:
   `synchronized` пришпиливает поток к carrier — **487.6 мс, одновременно не больше 12 задач,
   0 смен carrier'а**; `ReentrantLock` отпускает carrier — **62.1 мс, все 96 задач одновременно**.
4. **Масштабирование.** 10 000 задач по 50 мс ожидания: **124.9 мс** на виртуальных потоках против
   **2544.4 мс** на платформенном пуле из 200 потоков (в 20.4 раза).

Дополнительно: настройки `app.hw14.*` (страницы, задержка, размеры пулов, число задач) меняются
аргументами запуска без правки кода; 19 JUnit-тестов проверяют корректность результатов, отсутствие
потерь, «виртуальность» потоков, отмену по таймауту и инварианты pinning.

### Запуск

```bash
cd "Теория и практика многопоточности/app"
mvn spring-boot:run -Dspring-boot.run.arguments="--app.hw=hw14 --server.port=0"

# или из готового jar
mvn -DskipTests package
java -jar target/vacancy-parser.jar --app.hw=hw14 --server.port=0
```

Настройки (`app.hw14.*`) переопределяются аргументами, например
`--app.hw14.pages=400 --app.hw14.fixed-pool-size=8 --app.hw14.scaling-tasks=5000`.
