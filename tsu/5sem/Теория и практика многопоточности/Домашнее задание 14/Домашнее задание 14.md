## Что подготовлено

Пакет `hw14.loom` — шесть этапов демонстрации и отчёт с фактическими замерами:

1. **Виртуальные потоки базово.** 200 страниц вакансий с локального сайта-заглушки грузятся
   синхронным HTTP, каждая — в своём виртуальном потоке
   (`Thread.ofVirtual().name("hw14-vt-", 0)` + `Executors.newThreadPerTaskExecutor`). В журнале
   видно имя потока и его carrier (`ForkJoinPool-1-worker-N`), а `Thread.isVirtual()` подтверждает,
   что поток действительно виртуальный.
2. **Сравнение с платформенным пулом.** Тот же объём работы через `newFixedThreadPool(16)`:
   **699.5 мс против 103.1 мс** у виртуальных потоков (в 6.8 раза быстрее), пик одновременных задач
   16 против 200, потоков ОС +16 против +0.
3. **Pinning.** Одинаковые блокирующие операции под `synchronized` и `ReentrantLock`:
   `synchronized` пришпиливает поток к carrier — **543.6 мс, одновременно не больше 12 задач,
   0 смен carrier'а**; `ReentrantLock` отпускает carrier — **61.1 мс, все 96 задач одновременно**.
4. **Масштабирование.** 10 000 задач по 50 мс ожидания: **75.2 мс** на виртуальных потоках против
   **2512.6 мс** на платформенном пуле из 200 потоков (в 33.4 раза).
5. **«Поток на задачу».** Те же 10 000 задач, каждая печатает имя своего потока и ждёт 1 мс:
   `Thread.ofVirtual().start(...)` — **65.3 мс, запуск 48.5 мс, пик 7983 задачи, CPU 520 мс**;
   `new Thread(...).start()` — **425.4 мс, запуск 424.3 мс, пик 49 потоков, CPU 1290 мс**.
   Отдельная серия прогонов на 1 000 / 5 000 / 10 000 задач показывает линейный рост цены потока ОС.
6. **StructuredTaskScope.** Группа из 10 000 виртуальных подзадач под управлением скоупа:
   успешный `join` (**319.2 мс**, все 10 000 с результатом); падение одной подзадачи —
   `ShutdownOnFailure` отменяет остальные (**137.9 мс**, отменено 9999, причина
   `IllegalStateException`); таймаут через `joinUntil` + `shutdown` (**268.9 мс**, отменено 10 000);
   `ShutdownOnSuccess` — первый успешный источник отменяет два дубля (**152.8 мс**).

Дополнительно: настройки `app.hw14.*` (страницы, задержка, размеры пулов, число задач, срок и
параметры скоупа) меняются аргументами запуска без правки кода; 32 JUnit-теста проверяют
корректность результатов, отсутствие потерь, «виртуальность» потоков, отмену по таймауту,
инварианты pinning, сходимость счётчиков `StructuredTaskScope` и обработку исключений.

### Запуск

```bash
cd "Теория и практика многопоточности/app"
mvn spring-boot:run -Dspring-boot.run.arguments="--app.hw=hw14 --server.port=0"

# или из готового jar (флаг preview обязателен: StructuredTaskScope — preview-API)
mvn -DskipTests package
java --enable-preview -jar target/vacancy-parser.jar --app.hw=hw14 --server.port=0
```

Настройки (`app.hw14.*`) переопределяются аргументами, например
`--app.hw14.pages=400 --app.hw14.fixed-pool-size=8 --app.hw14.scaling-tasks=5000`
или `--app.hw14.swarm-tasks=5000 --app.hw14.structured-timeout-millis=500`.

### Проверка

```bash
cd app
mvn test -Dtest='ru.tsu.tpm.vacancyparser.hw14.**'   # 32 теста
mvn test                                            # весь проект: 577 тестов
```
