1. Что требовалось и что сделано

Текст задания: реализовать многопоточную систему кэширования или событий, используя потокобезопасные коллекции и шаблоны из java.util.concurrent (система уведомлений, логирование событий, обработка событий пользователей). Отчёт с результатами.

Реализованы обе части, потому что в парсере вакансий они естественно связаны: кэш ускоряет повторные обращения к данным, а шина событий уведомляет подписчиков о том, что с кэшем происходит.

Что Где
Карточка вакансии (значение кэша) model.VacancyCard
Кэш: ConcurrentHashMap + TTL + ёмкость cache.VacancyCache
Запись кэша с версией cache.CacheEntry
Ключ истечения для DelayQueue cache.ExpiringKey
Счётчики кэша cache.CacheStats
Типы и запись события events.EventType, events.VacancyEvent
Шина событий events.VacancyEventBus
Рейтинг на ConcurrentSkipListMap ranking.SalaryRanking
Замеры «конкурентная vs синхронизированная» benchmark.ConcurrentBenchmarks
Строки отчёта report.ConcurrentReport
Демонстрация ConcurrentCollectionsDemo, запуск --app.hw=hw12
Настройки app.hw12.* config.Hw12Properties

Какая коллекция зачем:

Коллекция Роль
ConcurrentHashMap основное хранилище кэша и счётчики по типам событий: чтения без блокировки
DelayQueue срок жизни записей: poll(timeout) будит уборщик ровно к моменту истечения
ConcurrentLinkedDeque порядок вставки записей для вытеснения по ёмкости; журнал последних событий
LinkedBlockingQueue очередь публикации событий между производителями и диспетчером
CopyOnWriteArrayList подписчики (читаются на каждом событии, меняются редко) и группы рейтинга
ConcurrentSkipListMap рейтинг по зарплате: топ-N без сортировки на чтении
LongAdder / AtomicLong счётчики: сравнение на замерах

2. Этапы выполнения

Этап 1. Конкурентная загрузка кэша

8 потоков-клиентов делают по 2000 обращений к 200 ключам. Источник «дорогой»: загрузка значения моделируется паузой 1 мс. Ключевая проверка — однократная загрузка: пока один поток загружает значение, остальные ждут только по этому ключу, а не по всему кэшу.

Этап 1. Конкурентная загрузка кэша: ConcurrentHashMap + compute
    обращений 16000 за 278.115 мс (57530 оп/с), потоков 8
    загрузчик вызван для 200 ключей из 200, максимум вызовов на ключ: 1 (однократная загрузка: да)
    попаданий 15800, промахов 200, загрузок 200, вытеснений 0, истечений 0, записей 200, доля попаданий 98.8%

Механика: getOrLoad выполняет проверку и вставку внутри ConcurrentHashMap.compute. Блокировка берётся на бин ключа, поэтому 200 разных ключей загружаются параллельно, а 16 000 обращений к одному ключу дают ровно одну загрузку. Обычная связка «get → проверка → put» дала бы несколько загрузок одного и того же значения: между проверкой и записью есть окно (тот же дефект разбирался в ДЗ 6 на BrokenSingletonCache).

Этап 2. Срок жизни: DelayQueue + уборщик

Отдельный кэш ёмкостью 10 и сроком жизни 300 мс, чтобы счётчики относились только к этому сценарию:

Этап 2. Истечение срока жизни: DelayQueue + поток-уборщик
    положено 5 записей со сроком жизни 300 мс
    видимых записей после срока: 0, физически удалено уборщиком: 5 (ожидалось 5, успех: да)
    ёмкость 10, записей осталось: 0

Важная деталь — номер версии записи. Пока ключ истечения лежал в DelayQueue, запись могли перезаписать новой (со свежим сроком). Удаление «по имени» выбросило бы актуальные данные; поэтому уборщик удаляет запись только если её sequence совпадает с версией ключа. Кроме того, peek проверяет срок сам: истёкшая запись не отдаётся даже до физического удаления.

Этап 3. Ёмкость: вытеснение по порядку вставки

Этап 3. Вытеснение по ёмкости: ConcurrentLinkedDeque порядка вставки
    добавлено 340 записей при ёмкости 128
    вытеснений: 212, записей в кэше: 128 (предел соблюдён: да)
    вытесняется ровно разница: 340 − 128 = 212

ConcurrentLinkedDeque хранит порядок вставки. При превышении ёмкости из головы берётся самый старый ключ; entries.remove(key, entry) удаляет запись, только если она всё ещё та (а не перезаписанная параллельно). Счётчик вытеснений совпал с разницей 340 − 128 — значит, ни одна запись не «потерялась» и ни одна не вытеснена дважды.

Этап 4. Система событий

Три подписчика, один поток-диспетчер, события от кэша и от этапов 2–3:

Этап 4. Система событий: LinkedBlockingQueue + CopyOnWriteArrayList + ConcurrentHashMap
    событий опубликовано 16962, доставлено 16962, отклонено 0, потеряно 0
    доставка завершена: да, сбойных подписчиков: 0, подписчиков: 3
    получили: подписчик-1=16962, подписчик-2=16962, подписчик-3=16962
    одинаковый порядок событий у всех подписчиков: да (рассылает один поток-диспетчер)
    счётчики по типам: попадание: 15800; промах: 200; загрузка: 200; вытеснение: 212; истечение срока: 205; сохранение: 345
    журнал последних событий: 100 из предела 100, самое свежее: #16962 вытеснение evict-211 (time-boxed-task)

Свойства, которые здесь подтверждены числами:

  • ни одно событие не потеряно: опубликовано = доставлено = 16 962;
  • все подписчики видят одинаковый порядок: у всех троих последовательности совпадают, потому что рассылает один поток-диспетчер;
  • счётчики по типам сходятся с логикой: 15 800 попаданий + 200 промахов = 16 000 обращений этапа 1; 200 загрузок; 345 сохранений (5 временных + 340 вытесняемых);
  • журнал ограничен: 100 последних событий при 16 962 опубликованных, новые первыми;
  • сбой подписчика не ломает рассылку (проверено тестом: исключение ловится, остальные получают события, счётчик subscriberFailures растёт).

Этап 5. Рейтинг на ConcurrentSkipListMap

Этап 5. Рейтинг по зарплате: ConcurrentSkipListMap + CopyOnWriteArrayList

    топ-5 по зарплате:
      206916 ₽: evict-99
      ...

Сортированная конкурентная карта позволяет получить топ через descendingMap() без сортировки всего списка: O(N) на вывод вместо O(M log M). Значение — CopyOnWriteArrayList идентификаторов: у многих вакансий зарплата совпадает, а читается группа чаще, чем меняется.

Нагрузка «как у кэша»: 90 % чтений, 10 % записей, 8 потоков, 1000 общих ключей, 50 000 операций на поток, лучшее из двух прогонов.

Этап 6. Замеры коллекций (90% чтений, 10% записей; лучшее из двух прогонов)

    ConcurrentHashMap быстрее synchronizedMap(HashMap) в 2.82× (7687803 против 2721346 оп/с)

Выводы:

  • Collections.synchronizedMap сериализует каждую операцию, включая чтения; ConcurrentHashMap блокирует только запись в конкретный бин, а чтения идут без блокировки. На смеси 90/10 это даёт 2.8× (в отдельном прогоне — до 4.5×; число зависит от планировщика и прогрева JIT).
  • AtomicLong обновляет одну ячейку и под конкуренцией упирается в CAS-конфликты; LongAdder раскладывает счёт по ячейкам и складывает их при чтении — 2.0× на 8 потоках. Плата — sum() не является мгновенно точным: пока идут инкременты, значение может отставать. Для счётчиков статистики это приемлемо, для денег — нет.
  • Итоговые значения счётчиков совпали с ожидаемыми (400 000), размеры карт — 800 записей при 1000 ключах и 10 % записей: потерь нет ни в одном варианте, разница только в скорости.

5. Наблюдения и грабли

  • compute вместо get + put. Пара «проверить и записать» не атомарна: два потока могут одновременно не найти значение и загрузить его дважды. compute держит блокировку бина и даёт однократную загрузку — это проверено тестом с 16 потоками на одном ключе.
  • Версия записи в DelayQueue. Ключ истечения ссылается на версию записи; иначе уборщик мог бы удалить уже перезаписанное (свежее) значение.
  • peek проверяет TTL сам. Физическое удаление происходит в уборщике, но отдавать просроченные данные нельзя ни на миллисекунду.
  • Один диспетчер событий. Он сохраняет единый порядок для всех подписчиков ценой последовательной рассылки. Параллельная рассылка была бы быстрее, но порядок стал бы разным у разных подписчиков, а счётчики — недетерминированными.
  • CopyOnWriteArrayList уместен только для редкозаписываемых списков. Каждая запись копирует массив; список подписчиков меняется один раз на старте, поэтому это дешёвый выбор. Для очереди событий он был бы катастрофой — там LinkedBlockingQueue.
  • LongAdder для статистики, AtomicLong для инвариантов. sum() у LongAdder не мгновенный снимок; если значение должно быть точным в конкретный момент (счётчик свободных мест, деньги), нужен AtomicLong или блокировка.
  • Ограниченный журнал. ConcurrentLinkedDeque + обрезка до предела: без предела журнал событий вырос бы до размера всей нагрузки (16 962 записи за 0.3 с — это ещё немного, но в проде это утечка).

Все числа — фактические замеры на машине с 12 ядрами (OpenJDK 21.0.13). Замеры коллекций шумят: в разных прогонах ConcurrentHashMap оказывался быстрее synchronizedMap в 2.8–4.5×, LongAdder быстрее AtomicLong в 2.0–4.9×. Поэтому в таблицу попадает лучшее из двух прогонов, а выводы сформулированы по знаку и порядку величины, а не по третьему знаку после запятой.
