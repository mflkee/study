## 1. Основы потоков

- **Процесс** — изолированное адресное пространство; **поток** — единица исполнения внутри процесса,
  разделяет память процесса (heap), но имеет свой стек и программный счётчик.
- Способы создать поток: `extends Thread`, `implements Runnable`, `Callable` + `FutureTask`,
  `ExecutorService.submit(...)`.
- `start()` создаёт новый поток и вызывает `run()`; прямой вызов `run()` — это обычный вызов метода
  в текущем потоке (классическая ловушка).
- **Демон-поток** (`setDaemon(true)`) не удерживает JVM от завершения; обычный (user) поток удерживает.
- `Thread.currentThread()`, `getName()/setName()`, `getPriority()` (1–10, только подсказка
  планировщику, а не гарантия).
- **Планировщик** не гарантирует порядок и равномерность: `Thread.yield()` — лишь подсказка.

## 2. Жизненный цикл потока

Состояния `Thread.State`: `NEW → RUNNABLE → (BLOCKED | WAITING | TIMED_WAITING) → TERMINATED`.

| Состояние | Когда |
|---|---|
| `NEW` | создан, `start()` не вызван |
| `RUNNABLE` | выполняется или готов к выполнению (включая ожидание CPU) |
| `BLOCKED` | ждёт монитор (`synchronized`) |
| `WAITING` | `wait()`, `join()` без таймаута, `park()` — без срока |
| `TIMED_WAITING` | `sleep(ms)`, `wait(ms)`, `join(ms)`, `parkNanos` |
| `TERMINATED` | `run()` завершён (в т.ч. через исключение) |

- `sleep()` **не отпускает** монитор, `wait()` — **отпускает** и требует владения монитором.
- `interrupt()` не убивает поток, а выставляет флаг; `sleep/wait/join` бросают
  `InterruptedException` и **сбрасывают** флаг. `Thread.interrupted()` сбрасывает флаг,
  `isInterrupted()` — нет.
- `join()` — дождаться завершения другого потока.

## 3. Параллелизм vs параллельность (concurrency vs parallelism)

- **Concurrency (конкурентность)** — несколько задач *одновременно в процессе выполнения*
  (могут выполняться на одном ядре, переключаясь). **Parallelism** — одновременное *исполнение*
  на разных ядрах.
- Конкурентность — про структуру программы, параллельность — про физическое исполнение.
- `parallelStream()`/`ForkJoinPool.commonPool` дают параллельность, но:
  общий пул делят все, размер = `Runtime.availableProcessors() - 1`;
  на IO-задачах и на маленьких объёмах параллельный стрим **медленнее** (оверхед разбиения
  и слияния), а `forEach` с общим состоянием — источник гонок.
- `parallelStream` не гарантирует порядок (если он нужен — `forEachOrdered`).

## 4. Синхронизация потоков

- **Гонка (race condition)** — результат зависит от порядка доступа к общему изменяемому состоянию.
- `synchronized` (метод/блок) — взаимное исключение + **видимость** (happens-before на выходе
  из монитора). Блокировка — на объекте-мониторе; у `static` метода — на `Class`.
- **Атомарность** `i++` не гарантируется: это чтение-изменение-запись (3 операции).
- **Happens-before:** запись до выхода из `synchronized` видна тому, кто после этого вошёл
  в тот же монитор; `volatile`-запись → `volatile`-чтение; `Thread.start()` → всё в новом потоке;
  всё в потоке → `join()` вернулся.
- **Потерянное пробуждение (lost wakeup):** `wait()` обязателен в цикле `while (!условие) wait();`
- **Ложные пробуждения** (`spurious wakeup`) — тоже причина для цикла.
- Взаимная блокировка при вложенных `synchronized` — см. тему 7.

## 5. Блокировки: Semaphore, ReentrantLock, Condition

- **`ReentrantLock`** — те же гарантии, что `synchronized`, плюс: `tryLock()`, `tryLock(timeout)`,
  `lockInterruptibly()`, честность (`new ReentrantLock(true)`), несколько `Condition`.
- **Правило:** `lock()` в `try`, `unlock()` в `finally`; число `lock()` = число `unlock()`.
- **`Condition`** — `await()`/`signal()`/`signalAll()` вместо `wait()`/`notify()`; один лок — много
  условий (например, «не пусто» и «не полно» в ограниченном буфере) → меньше ложных пробуждений.
- **`Semaphore`** — счётчик разрешений: `acquire()`/`release()`; бинарный семафор (1) ≈ мьютекс,
  но **не реентерабелен** и не привязан к владельцу.
- **`ReadWriteLock`** — много читателей или один писатель.
- **Спин-лок** (`ReentrantLock` без парковки / `AtomicInteger` CAS) выгоден только на очень
  коротких критических секциях.
- Инвариант буфера: `0 ≤ size ≤ capacity`; `notFull.await()` в цикле, `notEmpty.await()` в цикле.

## 6. volatile и atomic

- **`volatile`** — гарантии **видимости** и запрет переупорядочивания, но **не атомарности**:
  `volatile int i; i++` — по-прежнему гонка.
- **JMM**: без синхронизации поток может никогда не увидеть чужую запись (кэш ядра, регистры,
  переупорядочивание компилятором/CPU).
- **`AtomicInteger`/`AtomicLong`/`AtomicReference`** — CAS-цикл: `compareAndSet(expected, new)`.
- **ABA-проблема** — значение вернулось к прежнему; лечится `AtomicStampedReference` (версия).
- `LongAdder` — быстрее `AtomicLong` при высокой конкуренции (полосы), но `sum()` не атомарен.
- **Правило:** `volatile` — для флагов и «опубликования» готового объекта; `Atomic*` — для счётчиков;
  `synchronized`/`Lock` — для составных инвариантов.

## 7. Deadlock, Livelock, Starvation

- **Deadlock:** потоки ждут ресурсы друг друга по кругу. **4 условия Коффмана** (все одновременно):
  1) взаимное исключение, 2) удержание и ожидание, 3) отсутствие принудительного отъёма,
  4) циклическое ожидание.
- **Профилактика:** упорядочить захват блокировок (единый порядок), `tryLock(timeout)` с откатом,
  один глобальный лок, уменьшить время удержания, не вызывать чужой код под локом.
- **Livelock:** потоки не блокированы, но бесконечно «уступают» друг другу (живы, но прогресса нет).
- **Starvation:** поток не получает ресурс из-за приоритетов/нечестной блокировки.
- **Диагностика:** `jstack <pid>` → `Found one Java-level deadlock`, `ThreadMXBean.findDeadlockedThreads()`;
  в дампе — `waiting to lock`, `locked`.
- **`Thread.stop()`** — запрещён (оставляет объекты в несогласованном состоянии); остановка —
  флаг + `interrupt()`.

## Типовые вопросы (с ответами)

1. **Чем `start()` отличается от `run()`?** `start()` создаёт новый поток; `run()` — обычный вызов.
2. **Что делает `sleep()` с монитором?** Не отпускает (в отличие от `wait()`).
3. **Можно ли вызвать `wait()` без `synchronized`?** Нет — `IllegalMonitorStateException`.
4. **Почему `wait()` в цикле?** Ложные пробуждения и потерянные сигналы.
5. **`volatile` делает `i++` атомарным?** Нет, только видимость.
6. **Что такое happens-before?** Отношение, гарантирующее видимость записей между потоками.
7. **Разница `synchronized` и `ReentrantLock`?** `tryLock`, таймаут, честность, несколько `Condition`,
   прерываемый захват; но нужен `finally` с `unlock()`.
8. **Реентерабельность?** Поток может повторно захватить удерживаемый им же лок (`ReentrantLock`,
   `synchronized`); семафор — нет.
9. **`Semaphore(2)` — что это?** Не более двух потоков одновременно в критической секции.
10. **Что произойдёт при `interrupt()` во время `sleep()`?** `InterruptedException`, флаг сброшен.
11. **Чем `BLOCKED` отличается от `WAITING`?** `BLOCKED` — ждёт монитор; `WAITING` — ждёт сигнала
    без таймаута (`wait/join/park`).
12. **Что такое daemon-поток?** Не мешает завершению JVM.
13. **Почему `parallelStream` может быть медленнее?** Оверхед разбиения/слияния, маленький объём,
    IO, общий `commonPool`.
14. **Размер `ForkJoinPool.commonPool`?** `availableProcessors() - 1` (минимум 1).
15. **Что такое CAS?** Атомарное «сравнить и установить» без блокировки.
16. **ABA-проблема?** Значение вернулось к исходному; лечится версионным атомиком.
17. **Условия deadlock?** Четыре условия Коффмана одновременно.
18. **Как избежать deadlock?** Единый порядок захвата, `tryLock` с таймаутом, один лок.
19. **Livelock vs starvation?** Livelock — бесконечные взаимные уступки; starvation — поток
    не получает ресурс.
20. **Как найти deadlock в работающей JVM?** `jstack`, `ThreadMXBean`, визуальные профилировщики.
21. **`notify()` vs `notifyAll()`?** `notify` будит один (непредсказуемо какой) поток; `notifyAll` —
    всех, обычно безопаснее.
22. **Где хранится монитор для `static synchronized`?** На объекте `Class`.
23. **Что даёт `AtomicLong` без блокировки?** Атомарные операции через CAS, без парковки потока.
24. **Почему `Thread.stop()` опасен?** Освобождает мониторы в произвольный момент, ломает инварианты.
25. **Что такое ложное пробуждение?** `wait()` может вернуться без `notify` — поэтому цикл.

## Вопросы 26–50 (вторая часть тренажёра)

26. **Что произойдёт, если два потока одновременно вызовут `i++` на общем `int i` без синхронизации?**
    Потеря обновлений: операция не атомарна (чтение → инкремент → запись), возможны значения меньше ожидаемого.

27. **Достаточно ли `volatile` для счётчика?** Нет. Видимость обеспечена, атомарность — нет; нужен `AtomicInteger` или лок.

28. **Где может «залипнуть» поток в состоянии `BLOCKED`?** На входе в `synchronized`-блок/метод, пока монитор занят другим потоком.

29. **`tryLock()` без таймаута и с таймаутом — в чём разница?** Первый сразу возвращает `false`, если лок занят; второй ждёт указанное время.

30. **Почему `unlock()` обязателен в `finally`?** Иначе при исключении лок останется захваченным и заблокирует других.

31. **Что такое честная блокировка (`fair=true`)?** Потоки получают лок в порядке очереди; медленнее, но без starvation.

32. **Сколько условий нужно для ограниченного буфера?** Два: «не пусто» и «не полно» (иначе `notifyAll` и лишние пробуждения).

33. **Чем `Semaphore` отличается от мьютекса?** Семафор считает разрешения (N), не привязан к владельцу и не реентерабелен.

34. **`CountDownLatch` vs `CyclicBarrier`?** Latch одноразовый (ждём N событий), Barrier переиспользуемый (N потоков встречаются в точке).

35. **Что делает `Executors.newFixedThreadPool(n)`?** Пул из n потоков с неограниченной очередью задач.

36. **Почему `newCachedThreadPool` опасен?** Неограниченное число потоков (SynchronousQueue), при наплыве задач — исчерпание ресурсов.

37. **Как правильно остановить пул?** `shutdown()` (дать доделать), затем `awaitTermination`, при необходимости `shutdownNow()` (прерывает).

38. **Что будет, если задача в пуле бросит исключение?** В `execute` — уйдёт в `UncaughtExceptionHandler`; в `submit` — спрячется в `Future.get()` как `ExecutionException`.

39. **Чем `invokeAll` отличается от `invokeAny`?** `invokeAll` ждёт все задачи и возвращает список `Future`; `invokeAny` — первый успешный результат, остальные отменяются.

40. **Что такое `CompletableFuture.thenCombine`?** Объединяет два независимых результата в один, когда оба готовы.

41. **`thenApply` vs `thenCompose`?** `thenApply` — преобразование значения; `thenCompose` — «сплющивание» вложенного `CompletableFuture`.

42. **Как `CompletableFuture` обрабатывает ошибку?** `exceptionally` (значение по умолчанию), `handle` (и результат, и ошибка), `whenComplete` (побочный эффект, не меняет результат).

43. **Почему `ForkJoinPool` эффективнее пула фиксированного размера на рекурсивных задачах?** Work-stealing: простаивающий поток забирает подзадачи у занятого.

44. **Что такое `RecursiveTask` vs `RecursiveAction`?** `RecursiveTask` возвращает результат, `RecursiveAction` — нет.

45. **Когда разбивать задачу на батчи бессмысленно?** Когда порог слишком мал: накладные расходы на разбиение больше выигрыша.

46. **Что такое `BlockingQueue` и зачем `put/take`?** Очередь с блокировкой: `put` ждёт места, `take` — элемента; основа producer-consumer.

47. **`ArrayBlockingQueue` vs `LinkedBlockingQueue`?** Первая — фиксированная ёмкость и один лок; вторая — опционально ограниченная, два лока (быстрее при конкуренции).

48. **Как корректно завершить consumer'ов?** «Отравленная пилюля» (спец-элемент) или `interrupt()` + обработка `InterruptedException`.

49. **Что такое `ConcurrentHashMap` и чем лучше `Collections.synchronizedMap`?** Сегментные/CAS-блокировки: параллельные чтения и запись в разные бакеты без общего лока.

50. **Почему `ConcurrentHashMap` не допускает `null`?** Неоднозначность `get() == null` (нет ключа или значение null) в конкурентной среде.

## Мини-шпаргалка «что выбрать»

| Задача | Инструмент |
|---|---|
| Флаг «остановиться» | `volatile boolean` |
| Счётчик | `AtomicInteger` / `LongAdder` |
| Составной инвариант | `synchronized` / `ReentrantLock` |
| Ограничить параллелизм | `Semaphore` |
| Много читателей | `ReadWriteLock` |
| Очередь задач | `BlockingQueue` + пул |
| Рекурсивное разбиение | `ForkJoinPool` + `RecursiveTask` |
| Асинхронные цепочки | `CompletableFuture` |
| Ждать N событий | `CountDownLatch` |
| Периодический запуск | `ScheduledExecutorService` |
